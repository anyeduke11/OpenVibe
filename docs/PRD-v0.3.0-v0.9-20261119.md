## 第 0 章 · 一句话与目标

> **v0.2.6 修的是「规则同步的能力面对齐」；v0.3.0 开的是「把这些规则送进多个 agent 的手、并把 agent 的产出再收回来」。**

| 目标              | 内容                                                                                                                                                                       | 北极星（机器可判）                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **G1 定位升级**   | 把 OpenVibe 从「规则/上下文工作台」升级为「**多 Agent 中台**」：本机指挥国内外多个 AI coding agent 并行完成 vibecoding 任务，且**每个 agent 拿到的规则一致、可证、可回流** | 中台闭环圈数 **OM5** 增长；派发前规则一致性拦截率 **OM6** 可复算   |
| **G2 功能面补齐** | 按四条调研线的横向矩阵，逐条判定「补 / 不补（附理由）」；补齐的落成 FR                                                                                                     | 每条判定有结论；「不补」项有书面理由；「补」项有 FR 编号与验收标准 |
| **G3 实验定案**   | 用第一性原理（重建命题）与消融实验（静态消融 + 真机探针 + 场景对照）**筛掉**看起来合理但不该做的功能                                                                       | 消融实验判据全部可复算；被筛掉的条目写进观察池并附否证触发器       |

**次序不可换**：G2 的范围由 G1 的定位边界圈定，G3 的实验结果决定 G2 的**批次取舍**。⇒ **先立边界（P7–P10），再定候选，再跑实验，最后排批次。**

## 第 1 章 · 定位变更与范围界定

### 1.1 旧定位与新定位的差别（一句话）

|            | 旧定位（v0.1–v0.2.6）                     | 新定位（v0.3.0）                                                         |
| ---------- | ----------------------------------------- | ------------------------------------------------------------------------ |
| 回答的问题 | 「怎么把规则/知识标准化并分发到 AI 助手」 | 「怎么让多个 AI agent **按同一套规则**并行干活，且干完的收获能沉淀回来」 |
| 主角       | 用户 + 单个 AI 助手                       | 用户 + **多个 AI agent**                                                 |
| 核心链路   | 库 → 组包 → 注入 → diff/verify → 回流     | 库 → 组包 → 注入 → **派发 → 执行 → 汇聚验证 → 回流**                     |
| 价值主张   | 规则资产的可控分发                        | **规则资产的可控分发 × 多 agent 的可控编排**（复合，竞品无人占据）       |

**新定位不是替换旧定位，而是「加一条腿」**：分发线（既有）继续存在且是前提——**没有可靠注入，中台派发出去的 agent 就是裸奔的**。

| ------------ | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |

## 第 2 章 · 第一性原理重建（中台卷）

> 本章延续 [`analysis-2026-10-02-first-principles.md`](./analysis-2026-10-02-first-principles.md) 第 3 章的方法：**把每个设计决策拆到它成立所需的最小前提，逐条检验前提今天是否还成立**。P1–P6 是既有卷（分发线），P7–P10 是本文新增（编排线；P10 为跨机卷）。

### 2.1 这个系统在中台形态下实际在做什么（重新定义）

> **OpenVibe 是「人类意图 → 项目上下文」的编译器（既有定义 P-旧），在中台形态下新增一层：它同时是「规则 → agent 行为的执行闸门」。**

拆开说，一个中台要回答四个不同的问题：

| 问题                   | 谁回答              | 失败的样子                                   |
| ---------------------- | ------------------- | -------------------------------------------- |
| **该做什么任务？**     | 用户 / 规划者       | 派错活、拆错任务                             |
| **谁来做？**           | 中台（派发层）      | 派给不该派的 agent、重复派活、抢活           |
| **按什么规则做？**     | **OpenVibe 既有层** | agent 拿到的是过期规则、错的规则、根本没注入 |
| **做完的东西对不对？** | 验证层              | 错误合入主干、漂移扩散到所有助手             |

**关键判断**：第四个问题（做完对不对）是竞品的真空档，而前三个问题已高度同质化。⇒ **中台化的价值锚在「按什么规则做」与「做完对不对」两问，不在「谁来做」**。这就是第 1 章 B4 的来源。

### 2.2 四条新命题

#### P7 · 多 agent 的价值来自「规则一致性被强制」，不是「并发数」

- **前提检验**：竞品报告 §2.1.10 记录了 shogun 作者 2026-08 公开**解散自己的 10-agent 编队**、转向单 agent + 判断回路沉淀（后继项目 kagemusha：纠正→原则→长期规则）。⇒ 「更多 agent = 更好价值」的前提**已被一批实践者证伪**。
- **反向证据**：竞品矩阵（§3.1）显示编排 6 项全部 ✅ 的只有 gastown，而它同时是概念复杂度最高的项目、2025-12 才创建、成熟度待观察。⇒ 并发能力强 ≠ 价值高。
- **命题**：多 agent 场景下，**唯一随 agent 数量放大而变得更危险的东西是「规则不一致」**——一个 agent 用了新规则、另一个还在用旧规则，产出就无法合并，编排的边际收益被漂移吃掉。
- **推论（决定性）**：中台的**第一性动作**不是「启动 agent」，而是「**确认目标 agent 拿到的规则与主干一致**」。⇒ 派发前必须过注入状态闸（FR-3.0-3）；漂移未清时**拒绝派发**是可接受的产品行为。
- **否证触发器**：若真机探针（L1）显示「注入状态检查」在派发流程中无法低成本实现（误判率高、耗时不可接受），本命题的工程形态需重设计（但命题本身仍成立——此时应改做「派发时同步注入」而非放弃闸门）。

#### P8 · 指挥的最小充分集是「四件必选 + 能力协商」，不是「全特性统一」

- **前提检验**：竞品报告 §2.2.3 的旗标映射表显示，12 个 agent 的 headless / resume / JSON 输出旗标**各不相同**（`-p` / `exec` / `run`；`--resume` / `-S` / `--session` / `exec resume`；`stream-json` / `--json` / `--format json`）。若要求全特性统一，就要维护 N 套特化集成。
- **交集事实**：八对象交集只有四件——① 单命令无头执行 ② JSON 行级事件流 ③ 按会话 ID 续跑 ④ 退出码语义。**hooks / sandbox 档位 / 原生 subagent 只有部分 agent 有**。
- **命题**：中台的 adapter 契约必须**分层**：四件为必选（不满足即该 agent 不入注册表），其余为**能力协商**（探测到才启用，缺失时降级而非报错）。
- **推论**：⇒ adapter 实现成本与 agent 数量**线性但廉价**（每家一个旗标映射 + 一个 JSON 事件归一器）；⇒ 国产 agent 与国际 agent **同规格接入**，无主次之分（这对「指挥国内外 agent」的定位是硬要求）。
- **否证触发器**：若某 agent 的 JSON 事件流无法归一到统一 schema 且其文本输出也无法解析出可判定的完成/失败信号，则该 agent 降级为「黑盒档」（只支持 fire-and-forget），并在注册表标注。

#### P9 · 派发产出的价值在「回流」，不在「派发」

- **前提检验**：既有第一性原理 §3.3 第 3 条明写「**不做双向同步**」——助手产出的是**使用**，不是**标准**；把使用混进标准会污染信号。⇒ 派发产出**不能自动入库**，但**可以**成为候选。
- **既有机制可复用**：M10 提取链已具备「脱敏正文 → 候选草稿 → 人工确认 → 落库 → 来源反链」的完整闭环（`docs/specs/v023-d-ai-extract.md`），且有 AI 提取总闸、逐项目同意、次数预算、九键台账。
- **命题**：派发闭环的最后一环不是「合并代码」，而是「**产出变成下一次的规则输入**」。中台每完成一次派发，应当**至少留下一条可复用的候选**（术语/提示词/技巧/复盘要点），否则多 agent 只是把活干完了，知识没有复利。
- **推论**：⇒ 派发事件的 JSONL 流是 M10 提取链的**天然输入源**（比人工写开发日志更结构化）；⇒ 回流**仍走 pending 队列**（C-3），不自动入库。
- **否证触发器**：若派发事件的语义密度不足以产出有价值的候选（例如 agent 输出全是代码、无可沉淀知识），则回流腿降级为「只记录会话元数据」，不强制产出候选——**不为了指标而造假**。

#### P10 · 跨机的价值不在「连得上」，在「证明各机同源」——而 OpenVibe 的内容指纹正是为此而生

- **前提检验（连接不是难点）**：跨机品类是空档（竞品 §2.4.1：七组关键词实搜零命中），而已有项目的跨机做法**高度一致**——都是「共享一个双方都能访问的存储 + 各自轮询」：dsh-superagent 监听 GitHub/飞书（每 2 秒一趟 pass）、happy 走 relay 中继、amux 走 Tailscale HTTPS、gastown 走 DoltHub 仓。⇒ **「能不能连上」已被解决，且不需要破监听端口**。
- **前提检验（连上不等于有价值）**：这些项目解决的是「怎么把活送到另一台机器」，**没有一家解决「各机跑的是不是同一套规则」**。而多机场景里这件事的严重性与单机完全不同：单机漂移是「文件被改了」，多机漂移是**「A 机按新规则产出、B 机按旧规则产出，合并冲突发生在语义层而非文本层」**——这种冲突不会被 Git 检出，只会在产品上线后暴露。
- **既有工具的适配性检验**：OpenVibe 的 `pack.lock.json` 已经记录**包版本 + 内容指纹**，`verify` 已经能做「包 vs lock vs 磁盘」三方一致性。⇒ **跨机同源证明不需要新算法，只需要让各机发布自己的 lock 并做交叉比对**——这是既有机制的横向延伸，不是新建设。
- **命题**：跨机中台的第一性能力是**「同源证明 + 拒绝不同源」**——各机在被派活之前，先出示自己的规则指纹；中台（或人）比对，不一致则拒绝派发或要求先同步。⇒ 这与 P7 在单机场景是**同一条命题的放大版**：P7 说「一个 agent 拿到的规则要与主干一致」，P10 说「**所有机**拿到的规则要与主干一致」。
- **推论**：① 跨机派发的闸门 = P7 的闸门 + 指纹比对，**不是新的一套闸**；② 跨机共享的最小充分集 = **标准包（含指纹）+ 任务卡 + 结果证据**三样，代码与工作区不出本机（B5）；③ 派发工件的形态必须**幂等且可重放**（dsh-superagent 的 Trigger 不可变原则：接受两次只产生一个任务）。
- **否证触发器**：若实测显示「各机规则漂移在跨机场景下并不比单机更常见」（例如各机本来就由同一人维护、极少改动规则），则 P10 的价值主张不成立 ⇒ **跨机线降级为「纯任务搬运」，不做同源证明**——那时它就退化成 dsh-superagent 的一个子集，OpenVibe 没有理由做。

### 2.3 边界声明：中台形态下这个系统不该做什么

在既有四条（§3.3：不做云端账号体系 / 不做 AI 自动改用户资产 / 不做双向同步 / 不做全量覆盖默认）之外，新增四条：

5. **不建通用 agent 编排引擎**。编排范式无标准（竞品报告 §2.3.2：LangGraph 图状态 / CrewAI crew+flow / AutoGen 对话 / OpenAI handoff / Swarm 并行 五种互不兼容），自建引擎必输且必被生态抛弃。⇒ 只做**最小派发**：单任务 + 少量并行 + 人工确认。
6. **不建内容市场 / 不做组织级分发**。既有定位（非目标）+ 竞品教训（内容库是 anthropics/skills、skills-manager 的地盘）。
7. **不建模型网关**。模型路由交给 `claude-code-router`（38,230★，国产生态最全）——正交互补，不正面做。
8. **不做容器沙箱运行时**。各 coding agent 自带 sandbox 档位（Claude Code OS sandbox / Codex 3 档 / Qwen sandbox）+ git worktree 已够；E2B/Firecracker 级的 microVM 池是云端形态的重方案。

**跨机形态专属的四条（2026-11-19 追加）**：

9. **不做 A 机开端口远程控制 B 机**。跨机接缝在共享工件面，不在机器间控制通道（竞品 §2.4.2 结论 A：无一竞品这样做）。⇒ **OpenVibe 零新增监听端口，「只听本地」的硬承诺一字不改**。
10. **不做跨机联邦声誉经济**。gastown 的 Wasteland（认领他镇工作、赚可携声誉）是多租户协作形态，与 B2 单用户冲突。
11. **不做身份跨源映射 / 不做跨机账号体系**。dsh-superagent 文档明确把「跨 Source 的身份映射」判为 prompt 文本而非领域概念；OpenVibe 无账号体系 ⇒ **跨机以「同一使用者的多台机器」为前提**（C-4）。
12. **不共享代码与工作区**。跨机只共享标准包（含指纹）、任务卡与结果证据；代码、依赖、凭据留在各自本机（B5）。

### 4.2 关键判定的理由（展开三条最可能被质疑的）

**C-05 为什么最高优先？** 它是 P7 的直接工程形态，也是竞品矩阵中**唯一全场空白**的一格（16 个编排项目对「注入后漂移检测」全 ❌）。更重要的是：**它让 OpenVibe 的既有核心资产第一次进入指挥链**——否则「中台」只是又一个编排器，而 OpenVibe 的既有差异化（pack/diff/verify/回流）在中台形态下变成「不相干的历史包袱」。

**C-26（通用编排引擎）为什么不做？** 三条理由叠加：① 编排范式无标准，五种主流范式互不兼容（竞品 §2.3.2）⇒ 自建必被生态抛弃；② 编排 6 项已同质化（竞品 §3.1）⇒ 后进者只能拼成本；③ 既有 M5 流程模板 + 项目阶段模型已覆盖「人在流程里」的部分需求 ⇒ 自建引擎与 M5 重叠。

**C-27（自动合并）为什么不做？** 它与 C-3 冲突：既有 M8 纪律「**agent 的判断不可作为事实源**」在代码层同样成立。gastown 的 Bors 式二分合并建立在「有 CI 门禁 + 人可追责」之上；OpenVibe 的对应物应是「**验证门禁自动跑、合并由人执行**」——把 C-06 做成「自动验证 + 人工合并」而非「自动合并」。

## 第 5 章 · 消融实验：把范围从「看起来合理」收缩到「承重」

### 5.3 L2 · 场景对照实验（消融的「真身」）

> L0 是静态推理，L2 是**真实验**：用 OpenVibe 自身做受试品，跑 A/B 对照。

**实验设计**：取本仓 3 个真实任务（例：① 加一个 CLI 子命令 + 补测试 ② 修一个跨平台 bug ③ 写一份 spec）。每个任务跑两轮：

| 轮次       | 配置                                                                      | 度量                                                       |
| ---------- | ------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **对照轮** | 单 agent + 人工喂规则（当前 OpenVibe 形态：`sync` 注入 + 人工贴给 agent） | 完成率 · 返工轮数 · 规则违背次数 · 墙钟时长 · 人工介入次数 |
| **实验轮** | 中台派发 + 派发前规则闸 + 汇聚验证门禁                                    | 同上                                                       |
| **消融轮** | 实验轮 − C-05（去掉派发前规则闸）                                         | 同上（**预期：规则违背次数显著上升、返工轮数上升**）       |
| **消融轮** | 实验轮 − C-06/C-11（去掉汇聚验证门禁，人工直接合并）                      | 同上（**预期：错误合入主干次数上升**）                     |

**判据（用于最终定案）**：

| 指标                                       | 支持保留                     | 支持去掉     | 无法判定           |
| ------------------------------------------ | ---------------------------- | ------------ | ------------------ |
| 规则违背次数（agent 产出违反规则库的次数） | 实验轮 − 消融轮差异 **≥ 2×** | 差异 < 1.2×  | 介于               |
| 错误合入次数（验证门禁拦下的错误数）       | 门禁拦下 **≥ 1 次**          | 0 次         | —                  |
| 人工介入次数                               | 实验轮 **不高于**对照轮      | 实验轮更高   | 介于（差异不显著） |
| 墙钟时长                                   | 实验轮 **短于**对照轮        | 无差异或更长 | 介于（差异不显著） |

> **显著性口径**：3 个任务中须有 **≥2 个任务同向重现**，单任务上的差异只作观察、不作定案。

**决策规则**：

1. 若消融轮（C-05 去掉）相对实验轮**规则违背次数无显著上升** ⇒ **C-05 不承重**，本 PRD 的核心命题 P7 被证伪 ⇒ 整条中台线降级为观察池，**不做**。
2. 若实验轮相对对照轮**人工介入次数更高** ⇒ 中台在单人场景是负收益 ⇒ 收缩为「**单 agent、单任务的最小派发 + 验证 + 回流**」，砍掉多 agent 并行与批量编排。**派发通道必须保留**——没有它，验证门禁无对象可验、回流无输入源，链路会直接回落到既有 M8/M10 形态。
3. 若 L1 探针在 ≥3 个 agent 上失败 ⇒ 中台形态无法成立（无法统一指挥）⇒ 退化为「单一 agent 深度集成」。

> **条款分类**：第 1 条是**自毁条款**（触发即整条中台线不做、本 PRD 作废）；第 2、3 条是**降级条款**（触发后范围收缩，其余部分继续有效，按收缩后的范围重新验收）。二者不得混称。

### 5.4 L3 · 跨机对照实验（2026-11-19 追加）

> 验证 P10 的核心主张：**跨机的价值在「同源证明」，不在「连得上」**。
>
> **前置未定项（V-6 开工前须裁定）**：① 共享工件面的**载体形态**（Git 仓 / 局域网共享目录 / 云同步盘）——三者对「零监听端口」的满足程度不同，本文不预设；② 两机同时取件的**并发互斥机制**（本文按 FR-3.0-9 的「文件系统原子占位」验证，若载体不支持则需重选载体）。

**实验设计**：本机 + 另一台机器（可用一台虚拟机/另一台开发机模拟），同一个真实任务（例：给本仓加一个 CLI 子命令并补测试），跑三轮：

| 轮次       | 配置                                                   | 目的                     |
| ---------- | ------------------------------------------------------ | ------------------------ |
| **对照轮** | B 机**不装**标准包（或装旧版），A 机直接派活           | 基线：无同源保障         |
| **实验轮** | 两机都装同一标准包，**派发前做指纹比对**，不一致则拒绝 | P10 的正向验证           |
| **消融轮** | 实验轮 − C-32（去掉指纹比对，只看版本号）              | 检验「同源证明」是否承重 |

**判据**：

| 指标                             | 支持保留 C-32                | 支持去掉         |
| -------------------------------- | ---------------------------- | ---------------- |
| 产出的规则违背次数               | 实验轮 − 消融轮差异 **≥ 2×** | 差异 < 1.2×      |
| 任务完成率                       | 实验轮 **显著高于**对照轮    | 无差异           |
| 语义级合并冲突数（不是文本冲突） | 对照轮出现 ≥1 次、实验轮为 0 | 两轮都有或都没有 |

> **显著性口径**：同一任务至少跑 3 轮，差异须**跨轮同向重现**才计入。

**决策规则**：

4. 若消融轮与实验轮的**规则违背次数无显著差异** ⇒ **C-32 不承重** ⇒ 跨机线降级为「纯任务搬运」，**不做同源证明**，跨机功能并入观察池 O13。
5. 若对照轮与实验轮**完成率与违背次数均无差异** ⇒ 跨机场景在单人多机下**没有增量价值** ⇒ **整个跨机线（V-6…V-8）取消**，本文第 1.4 节与 P10 随之作废。
6. 若两机规则漂移在实践中**极少发生**（各机规则变更频率 < 每周 1 次） ⇒ 同源证明的触发场景稀缺 ⇒ 降级为「低频手工核对」而非闸门。

> **条款分类**：第 5 条是跨机线的**自毁条款**——触发即取消 V-6…V-9，§1.4 与 P10 作废，此时应老实承认「跨机不是单人场景的刚需」；第 4、6 条是跨机线的**降级条款**——触发后只收缩跨机形态，单机线不受影响。
