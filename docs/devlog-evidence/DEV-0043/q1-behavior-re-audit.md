## R1 · 换包之后，`clean` 会不会删「只有旧包注入过」的文件

- **链上原话（m6b v1.3 ②，我标 C 级）**：§6.10 换包语义由「整体重写、旧包独有文件脱离登记」改为「合并、旧条目留档并**仍由 `clean` 一并退场**」。
- **代码实况**：`packages/core/src/inject/lock.ts:39-41`
  ```ts
  // 包更新后消失的旧文件：MVP 不清理（P1 update 向导处理），哈希留档备查（m6b §6.2）
  for (const entry of input.oldLock?.files ?? []) {
    if (!planPaths.has(entry.path)) files.push({ ...entry })
  }
  ```
  旧条目被原样推进新 lock，`managed` 位继承 ⇒ `planRetirement` 会把它们当受管项分类 ⇒ 内容未被改动的，`clean` **照删**。
- **注意一处措辞张力**：同一行代码注释写的是「**MVP 不清理**」。两句其实不矛盾（`sync` 不清理，`clean` 会退场），但注释只说了一半，后来人读注释会以为旧条目永远留在盘上。**这条要么改注释要么改口径**，不能两头都留着。
- **今天有没有被测**：**留档**被测（`lock.test.ts` 有 8 处 `oldLock` 相关）；**跨包退场这一半没被命名**——`clean.test.ts` 里搜「换包 / 旧包 / 合并留档」= 0 命中。也就是说这条 B 级口径的**后果侧无回归保护**。
- **要不要留**：留 ⇒ 用户换包后跑一次 `clean` 能把旧包残留一次清干净（我认为这是对的行为，也是"退场"这个词的自然含义）；撤 ⇒ `clean` 只管当前包，旧包独有文件变成**必须手工删**的孤儿，且与 §6.3 `ABSENT` 行「计入已自行退场」不冲突但语义变窄。

## R2 · 一个文件都没删，也照样删 `pack.lock.json`、退出码 0

- **链上原话（m6b v1.4 ④，我标 C 级，理由写的是「不改既有正常路径行为」）**：FR-6.5 补判据 **`driftKept === 0` 即删 lock**，而非「本次 unlink 数 > 0」。
- **代码实况**：`apps/cli/src/commands/clean.ts`
  ```ts
  const lockCleared = driftKept === 0          // 只在确认前算一次，抢锁与尾部 unlink 共用
  ...
  let cleaned = lockCleared
  if (cleaned) { try { unlinkSync(lockPath) } catch { ... } }
  ```
  抢锁条件同样是 `plan.removals.length > 0 || lockCleared` ⇒ **零删除的一轮也会真删盘**（删的就是那个 lock）。
- **它为什么存在（实现里的原话）**：判据若写成「删过东西」，用户手工删光注入文件后 `clean` 会永久停在「保留 lock」，`diff` 长报全量缺失且没有任何命令能收尾。
- **今天有没有被测**：**两档都有名**——`CLI-CLEAN-06b`（全部 ABSENT ⇒ 照样删 lock，`clean.test.ts:451`）、`CLI-CLEAN-06d`（全 FOREIGN、文件都在盘上 ⇒ 不动一个文件也照删 lock，`:483`）。
- **要不要留**：这是四里我**最想留住**的一条，它让 `clean` 可收尾；但要点在于**全 FOREIGN 那一档**：lock 说这些文件归包管、盘上却是用户自己的内容（`managed !== true`），我们**删掉 lock 等于承认"这些文件从此是你的"**。这个语义值得 owner 明确点头，而不是被我藏在一条 C 级登记里。

## R3 · `hints` 是 `--json` 的**必带**键

- **链上原话（m6b v1.5，我标 C 级，原话「形状口径澄清 + **一个附加键**，不改任何既有键名与退出码」）**：FR-6.10 的六键是下限不是闭集，`hints` 定为必带。
- **代码实况**：`apps/cli/src/index.ts` 的 `printer.result({ report, summary: { ok, ...s, hints, exitCode } })` ⇒ `summary.hints` 恒在（空时是 `[]`）。
- **同句自我否定这件事**：「不改任何既有键名与形状」与「一个附加键」写在同一对括号里。**形状变化的定义就是键集合变化**，这句话不构成 B 的反证。
- **今天有没有被测**：有。`clean.test.ts:744` 钉 `Object.hasOwn(env.summary, 'hints') === true`，`:745` 钉其内容；`CLI-CLEAN-12b` 钉 dry-run 那条腿。
- **要不要留**：留（去掉它，机器读者只能拿到"退了 8 个"却拿不到"为什么零写入"）。这条的问题是**标签**，不是内容。

## R4 · 「必带解释」从 1 条腿扩到 3 条，并把文案原文钉进契约

- **链上归属（`5a22800`，我标「v1.5 二次自纠，**不另计次**」）**：FR-6.10 现文把承重腿写成**三条**——交互取消 / `--dry-run`（「以上为计划，零写入零删除」）/ 陈旧锁接管（「接管了残留写盘锁 pid …」），且**把提示文案原文钉进契约**。
- **代码实况**：三句字面量分别只存在于 `clean.ts`（dry-run hint、cancel hint、takeover hint）与 `sync.ts` 的同族 hint。
- **今天有没有被测（这条是四处里唯一有缺口的）**：
  | 腿 | 断言 | 强度 |
  |---|---|---|
  | `--dry-run` | `CLI-CLEAN-12b`（`clean.test.ts:824`） | 钉该句在场 ✓ |
  | 交互取消 | `clean.test.ts:274` `toContain('未删除')` | **只钉了三个字**，整句可改 |
  | 陈旧锁接管 | **本行原写「`grep 接管 apps/cli/test/*.ts` = 0 命中」，2026-09-26 落地时否证**：该 grep 实际命中 `apps/cli/test/sync-lock.test.ts` 的 `CLI-LOCK-02`（它钉的是 **`sync`** 侧文案「接管了残留注入锁（pid …）」）。成立的是窄一截：**`clean` 侧**那条（`clean.ts` 的「接管了残留写盘锁 pid …」）在 `clean.test.ts` 里 0 命中 ⇒ 零覆盖只属 `clean`，不属 `sync` | **`clean` 腿零覆盖 / `sync` 腿钉整句前缀** |
- **后果**：契约要求「必须解释」，但 **`clean` 的接管腿**没有回归保护，改文案或改逻辑都不会红；取消那一腿只有半句的保护。而「文案原文钉进契约」意味着**以后改这句措辞就是一次 B 级改动**——今天没人想担这个。（本行两处 ASCII 引号随手换成中文引号，与本仓文档口径一致。）
- **要不要留**：这是四处里唯一一条**我建议改方向而不是改标签**的：要么补齐两腿的断言（把契约做实体），要么把契约从"文案原文"降为"必须给出可读理由"（不锁字句），后者更便宜也更符合 `§13-8` 的精神。
