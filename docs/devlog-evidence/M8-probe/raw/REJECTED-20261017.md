## 保留它们而不删除的理由

删掉会让「第一轮跑过、但结论无效」这件事**从记录里消失**，
下一轮又有人以为没跑过 —— 而真实情况是**跑过、但量错了对象**。
这两件事的分量完全不同：前者是没做，后者是做了但无效，处置方式也不一样。

## 一句话结论（这就是它们全部的价值）

**三份都答「支持」，但那份「支持」指的是「bash 能跟随软链、能执行 755 脚本」，
而不是「Trae／CodeBuddy 的 skill 机制能跟随软链、能执行脚本」。**

## 错在哪：把被测对象换掉了

Q3 与 Q4 问的是**平台**的行为。三份报告的取证动作却是：

```
cat ~/.trae/skills/openvibe-probe/references/answers.md
cat ~/.codebuddy/skills/openvibe-probe/references/answers.md
~/.agents/skills/openvibe-probe/scripts/probe.sh
```

这三条的**每一条都会成功，与 Trae／CodeBuddy 无关**：

- 前两条走的是**操作系统的**软链解析 —— 任何 macOS shell 都会跟随软链，
  它测的是内核的 `readlink`，不是平台的 skill 扫描器；
- 第三条直接执行的是**真源路径**（`~/.agents/…`），根本没经过平台那一层。

⇒ **绕过平台的测量，结构上就回答不了关于平台的问题。**
它不是「测得不够仔细」，是**测的不是那台机器**。

⚠️ 更隐蔽的一点：脚本 stdout 里的 `path=` 字段显示真源路径，
这件事**既可能是**「agent 自己 bash 调的」（无效），
**也可能是**「平台跟随了软链后执行」（Q4 的**正面证据**）。
两者在输出里长得一模一样 —— 所以新版的校验器
**不单独**拿 `path=` 判成败，只把它登记下来供人工过目，
真正的判别式是「有没有客户端自证」＋「有没有绕过平台的 shell 取证」。
