# 走查过程中暴露并处理的两处「排序不确定性」（同一类缺陷，均为夹具侧改，产品侧不动）
① step 3 选夹具按「列表前 N 条」（terms?size=3 / flow-templates items[0]）时，两遍包指纹不同
   （c589c05a6bea vs 8f469b8774ef，bundle 9175B vs 11907B）。
   根因：packages/core/src/repos/terms.ts:211 `ORDER BY updated_at DESC`、
         packages/core/src/repos/flows.ts:112 `ORDER BY builtin DESC, updated_at DESC`——
         63 条术语 / 3 条流程同毫秒批量播种，updated_at 全等，平局无兜底，返回序随 DB 物理序漂移。
         同一次走查里两次独立起服务即实测到 flow-templates 首条从「Spec 驱动流」变「个人轻量流」。
   处理：改按 zh / name 精确取，指纹立即稳定。
② step 7 造 1.0.1 时对 `prompts?size=50` 过滤结果的 `[0]` 做 PATCH，两遍 1.0.1 指纹不同
   （151bc9602509 vs efd400441eee）。
   根因与 ① 同源：`.cursorrules` 与 `CLAUDE.md` 两条由 step 2 同一毫秒导入，列表返回序不定，
   `[0]` 在两个 DB 上指向不同提示词 → 被改写的正文不同。1.0.0 之所以稳定，只是因为它不经过这条选取。
   处理：改 `find(p=>p.title==="CLAUDE.md")`，②随即消失（本文件两遍即修复后所测）。
定性：与 DEV-0017 同型（毫秒时间戳 + 无确定兜底）。T8 应给 repos 列表查询统一加 `, id` 尾部兜底，
      并加一条 CI 守卫：ORDER BY 以时间戳列结尾即 fail（见 DEV-0018 风险②）。
