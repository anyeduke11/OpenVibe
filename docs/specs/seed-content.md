## 1. 目标与用户价值

新用户 `openvibe serve` 之后 3 分钟内看到**已经可用的价值**：100+ 词条的术语库可检索、3 套流程模板可直接建项目、20 条精选提示词可直接复制/组包——不需要先录入任何东西。

## 3. 文件与 Schema

### 3.1 位置与加载

`content/seed/{terms.json, flow-templates.json, prompts.json}`，随包分发；首启导入逻辑见 design.md §15（幂等：seed 登记表按 bundle contentHash 去重）。三文件均带 `{ "schemaVersion": 1, "items": [...] }` 包裹。

### 3.2 terms.json item schema

即 m3 §3 的 Term 字段（id 由导入时生成，文件内不写 id）；`source` 恒为 `"openvibe-seed"`，`status` 恒为 `"active"`。

**质量门槛**：每条 zh、en 至少一项；definition ≥ 20 字（中文）；≥ 60% 条目带 example；aliases 覆盖常见缩写与误写；标签取自受控词表（见 §5）。

### 3.3 flow-templates.json item schema

即 m5 §3 的 FlowTemplate（builtin=true, kind 见各模板）。**三套模板的完整阶段定义如下（评审冻结对象）**：

**① 个人轻量流（light，3 阶段）**

| 阶段 | 检查清单 | 产物 |
|------|----------|------|
| 1 启动 | 需求一句话写清；标准包已注入（`openvibe diff` clean）；建 DEV_LOG.md | 需求便签 |
| 2 开发 | 分小步提交；每轮改动后测试通过；下班前追加 DEV 日志 | 代码 + DEV_LOG |
| 3 复盘 | 检查清单全勾；写 CHECK 报告；新词/新坑回流入库（术语/提示词草稿） | CHECK_LOG |

**② Spec 驱动流（spec_driven，7 阶段，裁剪自 spec-kit/BMAD 思路——PRD 3.2-M5）**

| 阶段 | 检查清单 | 产物 |
|------|----------|------|
| 1 需求澄清 | 五问齐备（谁/现状/期望/为何现在/完成标准）；假设显式标注 | 需求纪要 |
| 2 PRD | 目标可衡量；边界（In/Out）明确；成功指标有数 | PRD.md |
| 3 Spec 规格 | 输入输出/边界/验收标准逐条可测 | specs/ |
| 4 计划 | 任务拆分有依赖序；工作量有量级 | tasks.md |
| 5 实现 | 按任务序执行；每任务完成即验证；DEV_LOG 同步 | 代码 + 测试 |
| 6 审查 | 逻辑一致性/批判性/第一性原理三维过一遍（PRD 附录 D 方法） | 审查记录 |
| 7 复盘 | CHECK 报告；回流候选确认入库 | CHECK_LOG + 新资产 |

**③ 复盘流（retro，4 阶段，独立项目级复盘用）**

| 阶段 | 检查清单 | 产物 |
|------|----------|------|
| 1 收集 | 日志/指标/会话摘录齐备 | 素材清单 |
| 2 分析 | 问题按维度归类（重复性/达成度/合规性/引用可靠性，对齐全局 CHECK 规范） | 问题清单 |
| 3 决议 | 每问题有处理方式（修/缓/记录）；P0/P1/P2 定级 | 行动项 |
| 4 回流 | 术语/提示词/模板改进已入库或建草稿 | 资产增量 |

### 3.4 prompts.json item schema

即 m1 §3 的 Prompt 字段（id 导入时生成；status 恒 active）。

**构成要求**：≥ 6 条 `useAs=rule`（行为规则，组包即用）；其余为 reference（任务型）；平台标记覆盖至少 claude-code / cursor / generic 各 ≥ 4 条（codebuddy / trae / minicode 等新增平台按内容酌情标记，不作数量门槛——多数提示词本就平台无关，generic 已覆盖）；≥ 8 条含 `{{变量}}`；单条 content ≤ 2KB。

**主题清单（20 条的范围锚点，撰写时逐条对应）**：代码审查请求 / 重构引导 / 测试生成 / Bug 最小复现 / 提交信息生成 / 上下文装载（project onboarding）/ 规则遵守强化（anti-drift）/ 文档抽取 / SQL 生成约束 / API 设计评审 / 正则编写 / 类型补全 / 性能剖析引导 / 依赖升级评估 / 安全自查 / 前端组件规格 / 数据建模引导 / 日志规范化 / 错误处理范式 / 复盘报告生成。

## 4. 功能需求（FR）

1. **FR-1 自动加载**：首启（DB 空）按 terms → flow-templates → prompts 顺序导入；任一文件解析失败 → 跳过该文件、记 warning、不阻塞启动。
2. **FR-2 幂等**：seed 登记表存各 bundle contentHash；内容未变不重导；内容变更且用户未改过对应种子数据 → 升级导入（新增条目并入，不覆盖用户编辑）；用户改过 → 跳过该文件并提示。
3. **FR-3 手动重播**：设置页「重新导入种子」按钮 → 同 FR-2 规则。
4. **FR-4 校验脚本**：`pnpm seed:check` 校验三文件 schema + 数量门槛（terms ≥100 / 模板 =3 且阶段定义与本文 §3.3 一致 / prompts =20 且构成达标），进 CI。

## 5. 受控标签词表（种子内容统一使用）

`基础概念 / 方法论 / 工具平台 / 质量工程 / 协作流程 / 风险陷阱 / 提示工程 / 数据与存储`。自建词条不受限；种子词条必须取自此表（保证首屏筛选体验一致）。

## 6. 边界与异常

1. 词条 definition 含 Markdown 表格符 → 按 m3 §6.5 转义规则处理（校验脚本同查）。
2. 模板阶段名在 JSON 内重复 → 校验脚本报错（m5 §6.2 的孤儿化只兜底运行期）。
3. 种子 prompts 的 folderPath 统一 `/精选`；tags 含「精选」。
4. 升级导入遇 id 类冲突（理论上无 id）→ 忽略 id 以内容为准。

## 7. 验收标准（pass/fail）

1. `pnpm seed:check` 在三文件全量合入后退出码 0；删掉任意 5 条词条后退出码非 0（门槛生效）。
2. 首启后 terms ≥100 / 模板 3 / prompts 20（SQLite 计数）；三文件内容修改后重启 → 未编辑的种子按升级规则并入新词条。
3. 3 套模板的阶段数分别为 3/7/4，阶段名与 §3.3 表逐字一致（脚本断言，防漂移）。
4. 抽查任一词条：definition ≥20 字、标签在受控词表内。
