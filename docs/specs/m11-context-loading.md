## 1. 目标与用户价值

- 用户组包时看到的是**一个包有多大**（字节、token 估算），看不到的是**「AI 到底读了多少」**。探针 A 实测：同一渲染链，规则数 8／32／128 时主文档分别是 **3,534／13,250／52,186 B**；换成索引臂恒 **≈336 B**；128 条时主文档单独 **≈20,498 tokens**（PRD §1.2 组 A，E0）。也就是说主文档随条数**线性膨胀**，而膨胀的那部分**未必被读到**。
- 第二层价值是**可降级**。今天六个平台的产物**必须逐字节相同**地随规则条数一起变大 ⇒ 规则一多，要么包大到不能用，要么用户就不敢多写规则。分层加载要解决的不是「省字节」，而是**「让规则条数与主文档大小解耦」**。
- ⚠️ **本 spec 不承诺收益**（PRD 第 10 章第一风险）：探针 A 只证「能省多少」，**不证「省了就有用」**。真收益取决于 **U10**（六个平台是否真的会读主文档指向的二级文件）。U10 未跑之前，本 spec 的正确结论可能是「不做」（见 §6.3）。
- 明确不做的一件事：**不做「按需加载」这个交互概念**。本文件规定的是**协议**（谁读什么、读不到时怎么降级），不是给用户一个「加载/不加载」的开关。开关会把「哪些平台能降级」这件事变成用户的责任，而那是我们的责任。

## 4. 数据与核心概念

- **`LoadPlan`（一次注入的加载计划）**：回答「某平台这一次**必读**什么、**引用**什么」。形状是 `{ required: File[], referenced: File[] }` —— `required` 是主文档本身（必读，无它就什么都没有），`referenced` 是主文档里以指针形式指向、按需再取的文件。
- **三层**（PRD §4.3）：
  - **L0 必读主文档**：marker ＋ 标题 ＋ **一节索引**（每条引用只占一行：文件名、条数、为什么值得读）。
  - **L1 索引指向的已有二级文件**：`TERMS.md` / `CHECKLIST.md` / `SKILLS.md` / `PLAYBOOKS.md` —— **今天已经是这个形状**（§3-9），本文件不新造。
  - **L2 新增的规则与参考全文**：提议 `RULES.md` / `REFS.md` —— **今天内联在主文档里的那两块**（§3-1）。
- **能力位（capability）**：每个 adapter 声明它**是否具备「按引用再取」的能力**。⚠️ **声明不了 ⇒ 默认 false ⇒ 保持今天的全内联**。这条是 K8（未知）不变成回归的唯一办法（PRD §4.3）。
- **降级（degrade）**：能力位为 false 时，**同一条规则全文写进主文档**（今天的形态）。⇒ **降级的产物必须与今天逐字节相同**（这是 E-6 的硬约束）。
- **「未知」与「否」是同一件事**：K8 的证据等级是 **E2（未验证假设）** ⇒ 在拿到 U10 结论前，**所有平台一律按 false 处理**。这不是保守，是因为「声称能降级」而实际读不到，比「不降级」坏得多（用户会以为规则生效了）。

## 5. 功能需求

### FR-1 · 分层加载协议（三层，逐层定死）

1. L0 主文档的形态固定为：**marker ＋ 标题 ＋ 一节索引**。索引的每一行必须包含「文件名 ＋ 条数 ＋ 一句话为什么值得读」三要素 —— 缺任何一项即不合规（FR-6.1 的判据）。
2. L1 保持今天的样子（`TERMS.md` / `CHECKLIST.md` / `SKILLS.md` / `PLAYBOOKS.md`），**一字不改**。
3. L2 是**新增**的两个文件：`RULES.md`（规则全文）与 `REFS.md`（参考全文）。⚠️ **L2 的文件名单在 D-v25-1 裁定前是提议**（PRD §4.3 的原文即「提议」）；本 spec 沿用该提议，不自行改名。
4. L0 索引与 L2 文件之间是**单向引用**：L0 指向 L2，L2 **不指回** L0（避免循环引用与「读 L2 又要读 L0」的歧义）。
5. **每条规则/参考只允许出现在一个地方**：要么在 L2（被引用），要么在 L0（内联）。禁止两处都有（会造成「同一规则两个版本」）。

### FR-2 · `LoadPlan` 的语义接口

1. 接口形状：`planMainFiles(pack, capability) → { required: File[], referenced: File[] }`。**能力位是入参** ⇒ 同一个包在不同能力位下产出不同的计划，这是特性不是缺陷。
2. **能力未知 ⇒ 必须退化为全内联**（PRD §4.2 的原文约束）。退化路径**不依赖任何错误处理** —— 是分支，不是 catch。
3. `required` **恒非空**且恒含主文档本身 ⇒ 「没有 required」是 bug，不是合法状态。
4. `referenced` 的顺序**确定**（码点序，与既有 `order-determinism.test.ts` 同口径）⇒ 同一包两次组装产出的 `files[]` 清单逐位相同。

### FR-3 · adapter 能力位

1. 能力位声明在 `packages/adapters/src`（能力位的唯一出处），形状是一个**布尔**（或三态：`true` / `false` / **未声明**）。⚠️ **未声明与 `false` 同义**（FR-2.2 的后果）。
2. **不新增平台**：能力位挂在**既有六个** adapter 上，不新增第七个（E-5：`ADAPTER_IDS_P1` 的三个预留值 `windsurf`／`gemini`／`copilot` 仍只占位不实现）。
3. 能力位**不改变任何既有 adapter 的默认行为** ⇒ 全部默认为 `false` ⇒ 今天的产物不变（这是 E-6 的前提）。
4. ⚠️ **能力位不得引入 core → adapters 的依赖**（E-1：`packages/core/src` 对 `@openvibe/adapters` 命中必须仍为 0）⇒ 能力位只能经**既有允许面**传入（如 `registry.ts` 的 `planMainFiles` 注入点），不得让 core 反向 import adapters。

### FR-4 · 单文件越阈告警（K1 的后半句）

1. `sizeEstimate` 增加**单文件**维度的告警：当**任一文件**的字节或 token 估算越阈 ⇒ 给出**指名**的告警（哪个文件、多大、阈值多少）。
2. **只提示不阻断**（与既有 `SIZE_WARN_THRESHOLD` 的处置一致：不阻断导出）。
3. 阈值**复用**既有常量，不新设第二个数字（避免两个阈值各说各话）。
4. 该告警**不参与**任何阻断判定，也不进 manifest（承 `context-density.md` FR-5.3 的既有钉法）。

### FR-5 · 扩展能力的保留（E-1…E-6 逐条可判）

1. **E-6（硬约束）**：能力位为 `false` 的 adapter，其产物与**今天逐字节相同** ⇒ 落为一条对照用例（`IT-L2-06`），**先红后绿**。
2. **E-1**：`packages/core/src` 对 `@openvibe/adapters` 命中 **0**（一条 grep 即可判）。
3. **E-2**：新增第 7 个主文件 ⇒ 既有六者 sha **集合逐一相等**（已有回归位可复用，见 §3-7）。
4. **E-3**：新路径是**纯追加**，指纹随之变（不是静默覆盖）。
5. **E-4**：未登记 id 被 `PackManifestSchema` 拒绝（`invalid_value`）—— 已有 schema 断言，补一条显式用例。
6. **E-5**：`ADAPTER_IDS_P1` 的三个预留值仍在。
7. ⚠️ **E-6 不成立则本 spec 不通过**（PRD §4.4 末句）：任何分层设计若使任一既有平台的产物无法降级回今天的样子，该设计不通过。

### FR-6 · A 级变更的流程要求（D-v25-1）

1. 若 **D-v25-1** 裁「做」⇒ 走 A 级红线（PRD 第 8 章）：owner 裁定 → PRD 附录编号 → **`schemaVersion + 1`** → **先改 golden 再改实现**。
2. **特性位默认关** ⇒ 未显式开启时，产物与今天一致（与 FR-3.3 同一条纪律的另一种表述）。
3. ⚠️ **D-v25-1 与 D-v25-4 同批处理**（PRD 第 8 章 D-v25-4 行：「避免两次改字节」）⇒ 本 spec **不单独规定**反例指针的落点（那是 S5 的范围）。

### FR-7 · 不放松既有防线

1. 六个平台的**既有产物形态**（除新增 L2 外）不变；`TERMS.md` / `CHECKLIST.md` / `SKILLS.md` / `PLAYBOOKS.md` 四份一字不改。
2. `pack-contract.ts` 的段常量与 marker **不新增、不改名**（L2 是**新文件**，不是新段）。
3. 空集合不产文件的纪律保持（§3-8）⇒ **选了空的 L2 集合 ⇒ 不产 `RULES.md` / `REFS.md`**。
4. ⚠️ **不引第三方依赖**（PRD §4.2 末句：不引状态机库／ORM／事件溯源／向量检索）。

## 6. 边界与异常

### 6.1 索引行本身的格式

索引行是**协议的一部分**，不是自由文本。三要素缺一即判不合规 —— 理由：主文档是 AI 的入口，索引行缺了「为什么值得读」，模型就只会**机械跟随**而不会**按需取** ⇒ 分层就退化成「把内容搬走」，没解决问题。

### 6.2 能力位与「读不到」

能力位为 `true` 但目标平台**实际读不到** L2（路径不对、权限不够、平台不跟随引用）⇒ 用户得到一个**缺规则的包**，且没有任何信号。
⇒ 这是 **U10** 要回答的问题（§6.3），不是实现期能靠测试发现的 ⇒ **U10 未跑前，能力位一律不得置 `true`**。

### 6.3 「收益未证 ⇒ 可能不做」是本 spec 的合法结论

PRD 第 10 章第一风险：「把能省字节当成有用」。探针 A 的对照臂是**设计模拟**，证的是「能省多少」，**不证「改了就没问题」**（PRD §1.2 组 A 的推理边界）。
⇒ **U10 的结论若为「多数平台不读二级文件」⇒ S1 的正确结论是不做**，而不是「把指针去掉假装没问题」。
⇒ 本 spec 因此把「不做」写进 §6.3 而非只写「怎么做」。

### 6.4 L2 为空集合

选了空的规则集 ⇒ **不产 `RULES.md`**（承 §3-8 的既有纪律）。⚠️ 此时 L0 的索引里**也不得出现指向它的行**（否则主文档指向一个不存在的文件 ⇒ 模型按需取时得到「文件不存在」，比全内联更糟）。

### 6.5 降级路径必须与今天同形

能力位为 `false` ⇒ L0 内联全文。⚠️ 「内联」与「引用」两种形态的**主文档不能同时出现同一条规则**（FR-1.5）。

### 6.6 与 `context-density.md` 的分工

那份 spec 管**包总量与归因**；本文件管**单文件越阈**与**分层协议**。两者都碰 `sizeEstimate`，但**不共用一个字段**：本文件的单文件告警是**告警**（指名文件），那份的 `density` 是**读数**（分子÷分母）。⚠️ **不得**把单文件告警塞进 `density` 的结构里（会把「读数」变成「读数＋告警」的混合体）。

### 6.7 与 `m6-standard-pack.md` 的分工

那份 spec 是**包契约与 A 级变更流程**的总出处。本文件不另立流程，只引用（FR-6）。

### 7.1 未验证面（负向登记，不得读成已通过）

- **① 各平台是否真读二级文件（U10）**：**未跑**。K8 的证据等级是 E2（未验证假设）。本 spec 的全部降级设计都建立在「能力位默认 false ⇒ 行为不变」之上，而**能力位何时可以置 true** 完全取决于 U10 ⇒ **U10 未跑前能力位一律 false**。
- **② 索引化后模型行为是否退化（U11）**：**未跑**（需真实 provider）。⚠️ 「字节省了」与「模型仍照做」是两件事，后者没证据。
- **③ 主文档膨胀曲线的真实形态**：探针 A 的对照臂是**设计模拟**（PRD §1.2 组 A）⇒ 真实索引臂的字节与「模型会不会跟」都未测。
- **④ 单文件越阈的阈值是否合理**：`SIZE_WARN_THRESHOLD = 12_000` 是**包总量**阈值，本文件把它挪用到单文件维度 ⇒ 该值对单文件是否合适**未校准**（FR-4.3 要求复用它 ⇒ 这是**已知的不精确**，不是遗漏）。
- **⑤ 真实平台（Trae／Cursor／Claude Code 等）的引用跟随行为**：合成 adapter 与真机行为不是一回事（PRD §1.2 组 F 的推理边界）。
- **⑥ L2 文件的命名**：`RULES.md` / `REFS.md` 是 PRD §4.3 的**提议**，D-v25-1 未裁前不锁定。

### 8.2 待裁清单（不代 owner 裁）

| #   | 待裁                                                                                        | 我的倾向与理由                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | **D-v25-1**：L2 化改变四根主文件字节、`files[]` 清单与指纹 —— 做还是不做？                  | 倾向**先不做**，等 U10。理由：U10 若为「多数平台不读二级文件」，L2 化只换来「包变小」而模型读不到规则 ⇒ 净损失（PRD §10 章第一风险）。 |
| ②   | **L2 文件名**：`RULES.md` / `REFS.md`（PRD §4.3 的提议）还是别的名字？                      | 沿用提议，不另造名。理由：改名不带来任何能力，而每改一次名就要重跑 golden（字节变）⇒ 徒增 A 级变更次数。                               |
| ③   | **索引行三要素是否够**：文件名＋条数＋一句理由，还是再加「怎么用」（如「定义 X 的术语」）？ | 倾向**够**。三要素已能让模型判断「要不要取」；加第四项会让主文档重新膨胀（那正是本文件要治的病）。                                     |
| ④   | **能力位是布尔还是三态**（`true` / `false` / 未声明）？                                     | 倾向**三态显式**。理由：布尔会把「未声明」与「声明为 false」混在一起 ⇒ 复核时看不出「这个平台是测过的还是默认的」。                    |
| ⑤   | **单文件越阈阈值**是否复用 `SIZE_WARN_THRESHOLD = 12_000`（FR-4.3 要求复用），还是另设？    | 倾向**复用**（本文件已按此写）。理由：两个阈值各说各话是典型的静默腐化；但须登记「该值对单文件未校准」（§7.1④）。                      |
