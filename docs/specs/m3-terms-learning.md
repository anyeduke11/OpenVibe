## 1. 目标与用户价值

**一句话**：术语库从「能查到词」变成「照着能学会」—— 按领域分区、按难度递进，并主动告诉你「你这个项目该掌握哪些词」。

owner 的原话是「术语库是用来学习专业开发术语的，现在看不懂这个术语」。这句话里的**「看不懂」不是排版问题，是内容层次问题**：

| 现状 | 证据 |
|---|---|
| 109 条自建词条的定义**平均只有 53 字**，且大量是行话 | `content/seed/terms.json` 实测：definition 平均长度 53 |
| 例如「层级 / Z-Index」的定义里直接出现「层叠上下文」「包含块」「脱离文档流」 | 库内实测原文 |
| 新手读完**更糊** —— 用五个没懂的词解释一个没懂的词 | 同上 |
| 页面是**纯表格**（术语 / English / 别名 / 定义 / 状态 / 层级） | `TermsTable.tsx:92-100` 实测表头 |

参考站 vibe-hub.org 的解法有三招，本 spec 全部采纳：**① 按领域分区**（前端 146 / 后端 73 / AI 43 / Git 15 / 产品 25 / 测试 14 / 技术栈 20 / 设计风格 24）；**② 卡片式呈现**（每张卡先给一句「大白话场景句」，再给术语定义）；**③ 大白话反查**（用「登录弹窗」也能搜到「Modal」）。

2. **它自带 skill 约定**（`packages/coding-agent#skills`：能力包 ＋ 按需加载 ＋ 渐进披露）。
   ⚠️ **这一条直接解开 M8-A 的死结**：`m8-agent-bridge.md:51` 登记「M8-A 核心形态取决于 Trae/CodeBuddy 的 skill 发现约定，而该约定**运行半边未经真机核验**」，因此 `m8-skill-bridge.md` 连 spec 都写不出来。**Pi 的 skill 约定是公开、可读、有源码的** ⇒ M8-A 不必再等那两个未核验的平台约定，可以把 Pi 作为**第一个可核验的落点**。

3. **它刻意「什么都不做」的部分恰好是我们要做的。** 官方明列未内置：无 sub-agents、无 permission popups、无 plan mode、无后台 bash、无内置 todo。
   ⇒ 这不是「Pi 缺功能」，而是**「Pi 把这些留给 extension」**，extension 是 TypeScript 模块，有 tools/commands/events 权限。**我们要做的语义层正是这个形状。**

**⚠️ 本 spec 对 Pi 的使用边界（三条硬约束）**：

| # | 约束 | 为什么 |

## 4. 功能需求（FR）

### FR-1 数据模型：新增三列

**FR-1.1** `terms` 表新增：

```sql
-- 0008_terms_learning.sql
ALTER TABLE terms ADD COLUMN level TEXT NOT NULL DEFAULT 'L2' CHECK (level IN ('L1','L2','L3'));
ALTER TABLE terms ADD COLUMN starter INTEGER NOT NULL DEFAULT 0 CHECK (starter IN (0,1));
ALTER TABLE terms ADD COLUMN domain TEXT;   -- 刻意可空且**不加 CHECK**，见 FR-1.5
```

⚠️ **`domain` 是本轮补上的第三列**，v0.3 的「两列」是写规格时漏掉的一列：FR-3 立了「领域」这个
维度并要求前端显示领域 chip，但表里没有列能存它，`term-domain-map.json` 也只是 tag→领域的
映射表、落不到词条上。owner 2026-10-18 裁定：**加第三列 `domain`（可空）**。理由与 FR-3.2
同源 —— `tags[0]` 是用户可增删的自由标签，删一次标签领域就跟着变，按领域做的筛选与分区将
不可复现；把三维都落成列，筛选才有稳定谓词。

**FR-1.5** ⚠️ **`level`/`starter` 带 CHECK，`domain` 刻意不带** —— 这是有代价的取舍：
`level`/`starter` 的词表由本仓自产（`content/seed/term-levels.json`），写入前已收敛，CHECK 是
廉价护栏；`domain` 的词表来自 vibe-hub 上游的 `tags[0]`，是**外部可漂移**的数据，而 SQLite
**不能 `ALTER` 一个 CHECK 约束**，给它加 CHECK 等于把「上游加一个领域」变成「本仓重建表复制
数据换名」（FR-9.2 扩 `kind` 付的正是这份代价）。改为在 **API 写入边界**由 Zod 的
`z.enum(TERM_DOMAINS)` 收口，读侧 `TermOut.domain` 宽容返回原字符串、界面归入「未归类」；
未归类是合法状态（用户自建词条、上游新领域），故**可空且无默认值**。

**FR-1.2** 取值闭集，**必须是 Zod enum + 常量单一出处**（`packages/shared/src/constants.ts`）：

```
TERM_LEVELS = ['L1', 'L2', 'L3'] as const
```

- `level`：`L1` 入门 / `L2` 进阶 / `L3` 深入
- `starter`：`0` 非入门必需 / `1` 入门必需

**FR-1.3** ⚠️ **默认值给 `L2` / `0`，不是「空」**。理由：库里有用户自建词条（`source='manual'`），它们没有分类依据；给 `L2`/`0` 意味着「按中位处理」，而给 `NULL` 会让每个读取点都要写一遍 `?? 兜底` —— 而**默认值写进 DDL** 只需一处。（这一条是刻意的取舍，不是遗漏。）

**FR-1.4** `TermOut` 增加 `level: 'L1'|'L2'|'L3'`、`starter: boolean`（**DB 的 0/1 在 repo 边界转成 boolean**，不让 `0/1` 泄漏到 API 与前端）与 `domain: string | null`。

⚠️ 读写两侧**刻意不对称**：写入侧 `TermCreateInput.domain` 是 `z.enum(TERM_DOMAINS)`（收口），
读出侧 `TermOut.domain` 是 `z.string().nullable()`（宽容）。理由见 FR-1.5 —— 列上没有 DB CHECK，
读到词表外的值就原样返回，**不得在这里抛**，否则上游新增一个领域会让整个词库列表 500。

**判级**：**B 级**（响应形状 additive 变化，与 m3 v1.1 加 `pinyin` 同级）。

### FR-2 难度与「入门必需」两个维度（**441 条已全部判定**）

**FR-2.1 判定口径**（已用于本次全部判定，是判据的一部分）：

**难度** = 一个刚开始 vibe coding 的中文用户理解这个词条的**认知负担**。

| 档 | 判据 | 例 |
|---|---|---|
| `L1` | 不需任何前置知识，见到即懂 | 按钮、链接、输入框、保存、撤销、部署 |
| `L2` | 需要一点编程或用 AI 工具的常识，不需要系统知识 | 组件、状态、接口、分支、依赖 |
| `L3` | 需要系统知识或工程经验，通常还牵涉边界与陷阱 | 层叠上下文、包含块、幂等、熔断器、租约 |

⚠️ **反模式（本次实测踩到并已规避）**：不按中文名的术语化程度判。`URL` 对新手是 L1（就是个地址），`XML 站点地图` 名字唬人但定义说清了「给机器读的 URL 清单」，判 L1/L2 而非 L3。**以定义文本的实际认知负担为准**。

**入门必需** = 刚接触 vibe coding 的人，在**第一个真实项目**里会不会用到、且不懂会实际卡住。

⚠️ 与难度**独立**：允许 `L1+N`（简单但非必需，如圆角、分页）与 `L3+Y`（难但绕不开，如依赖、增量提交）。

**FR-2.2 分布实测**（441 条全部判定完毕，如实登记不掩饰偏斜）：

| 来源 | L1 | L2 | L3 | 入门必需 Y | N |
|---|---|---|---|---|---|
| vibe-hub 332 条 | 150 | 148 | 34 | 108 | 224 |
| 自建 109 条 | 12 | 86 | 11 | 26 | 83 |
| **合计 441 条** | **162** | **234** | **45** | **134** | **307** |

⚠️ **两批的口径差异是真实的，不是 bug**：vibe-hub 那批以前端组件为主（大量「按钮/输入框/卡片」类 L1）；自建那批集中在方法论/协作/打包分发（大量 L2）。两批混在一张表里按难度排序，**分布会显得很偏**，所以 FR-4 明确要求分区**在难度之前**。

⚠️ **判定过程中抓到的一个坑（写在这里防复发）**：首轮分类只覆盖了 **289/332** 条，43 条漏判。根因不在判定，在**导出**——`sqlite3` 直接导出时 `definition` 字段里的换行把一条记录拆成多行，那 43 条被拆散后混在空行里。子 agent 如实报告了「输入 332 行、实际 289 条」，**但没有把「少 43 条」与「输入文件有问题」关联起来**。
⇒ 通法：导出时 `replace(definition, char(10), ' ')`，且**导出后必须用 `SELECT id` 与判定产物做 `diff`**（§9 有现成命令）。**只核对行数会漏掉这一类** —— 行数是对的（332），错的是行与条目的对应关系。

**FR-2.3** 判定产物落 `content/seed/term-levels.json`，**不进 seed 主体**。理由：seed 主体是词条内容，难度是派生标注；分开落盘后词条更新不动标注。

⚠️⚠️ **v0.3 原文写的键是 `trm_xxx`，那是错的，本版订正。** `terms.id` 由 DB 侧的 `newId('term')`
**运行时生成**（`packages/core/src/repos/terms.ts` 的 `create()`），换机器重装种子会重新生成
全部 441 个 id ⇒ 以 id 为键的映射在首次导入时**全部落空**，且落空方式是「静默不匹配」，不报错。
改用 **`zh` ＋ `en` 自然键**，它正是 seed 通道既有的定位方式（`findByNaturalKey(zh, en)` 用
`WHERE zh IS ? AND en IS ?`，`IS` 形参可正确命中 `en` 为 NULL 的词条）。

实测口径（**用 `quote()` 而非裸 `||` 拼接** —— `zh || char(31) || en` 遇 NULL 结果即 NULL，
`COUNT(DISTINCT)` 会把 43 条静默漏掉，这正是 v0.3 §2 记的那个「导出坑」的同族）：

```
SELECT COUNT(*) 总数, COUNT(DISTINCT quote(zh)||char(31)||quote(en)) 唯一自然键 FROM terms;
→ 441 | 441   ⇒ 441 个自然键全部唯一，回填不会一条顶掉另一条
```

⚠️ **43 条 vibe-hub 词条的 `en` 是 NULL**（API、CDN、CORS 这类纯缩写词条），故数据文件里
`en` 字段**必须允许 `null`**，不能用「缺字段即空串」代替 —— 两者在 `WHERE en IS ?` 下不等价。

⚠️ 落盘形状与既有四个 seed bundle 一致：`{schemaVersion: 1, items: [{zh, en, level, starter}]}`。
**不用「拼一个分隔符当键」的对象形状** —— zh/en 里出现分隔符就会静默错配，且这种错配在
`diff` 行数上完全看不出来。

⚠️ **回填不走 `update()`**：那条路径写 `seed_hash = NULL`，而 NULL 的语义是「用户改过这条词条」
⇒ 下次 `terms.json` 升级时这条会被整条跳过并 warning。用它给 441 条落标，等于一次性冻结整个
词库的种子升级通道且不留痕迹。故另开 `TermsRepo.setLearning()`，它也**不碰 `updated_at`**
（回填不该把词条顶到 `list()` 的最前面）。

**判级**：C 级（纯数据）。

#### FR-6.2 基线层：确定性打分（**永远可用，Pi 不在也必须能跑**）

```
score(term, project) =
    2.0 × 术语/别名 在 checklist 文本中直接命中
  + 1.5 × 术语 标签 与 项目领域(由阶段名+技能推导) 重合
  + 1.0 × 术语 与 项目绑定的 Skill 名称/描述 有词面重合
  + 0.5 × starter = 1（入门必需整体上浮，避免推荐结果全是冷门深水区）
  - 2.0 × starter = 0 且 score < 阈值（冷门且弱相关 → 压下去）
```

⚠️ **这一层不依赖任何外部进程**。它是本功能的**下限保障**：没装 Pi、没配 API Key、Pi 起不来 —— 三种情况下术语推荐仍然工作，只是没有语义增强。

##### ⚠️ FR-6.2.1 项目领域的推导口径（**v0.6 · P3 落地时定 · 未经 owner 认可，见 §8 第 10 条**）

上式括注里的「项目领域（由阶段名+技能推导）」在 v0.5 之前**只有这一句**。P3 实测后发现那条字面读法**在真实数据上恒为空**，已改写：

| 项 | v0.5 的字面读法 | v0.6 的落地口径 |
|---|---|---|
| 项目领域怎么来 | 在阶段名里**找**领域词 | **反推**：凡是词面（zh/en/别名）**出现在阶段名或绑定 Skill 的 name/description 里**的词条，取它们的 `domain` 的并集 |
| 为什么改 | 实测本仓内置 **9 个流程模板的全部阶段名**，`TERM_DOMAINS` 八个词面的出现次数是 **0** —— 那条推导恒为空集 | 阶段名的真实作用是**它自己常常就是一个术语**（实测命中：`PRD`、`复盘`、`推送`、`验收标准`），所以领域要靠「阶段名命中了哪个词条」反推 |
| 「标签与项目领域重合」的重合对象 | 词条的 `tags` | 词条的 **`domain`**。⚠️ 实测 441 条里 **109 条的 `domain` 不在 `tags` 里**（`domain` 独立于 `tags`，两者不是同一维度），按 `tags` 取会让这 109 条永远拿不到 1.5 |

**skill 侧**：项目 `standard_pack_id` 绑定的标准包 → `selection.skillIds` → skill 的 name/description，走同一套反推。

⚠️ **包未绑定时该源为空集，且不回退到「全部已装 Skill」** —— 实测本机有 438 条已装 skill 且 `installed_targets` 全为空，回退等于让这 438 条全变成候选，「项目绑定的 Skill」这条约束就名存实亡。判据「包未绑定时不得回退」已落。

##### ⚠️ FR-6.2 末项惩罚是**死逻辑**（v0.6 实测登记，待 owner 处置）

`- 2.0 × starter = 0 且 score < 阈值` 这一项**改不了任何结论**：它减的是**已经低于门槛**的分，减完还是低于门槛。它只影响出参里那个 `score` 字段的观感，不影响进不进推荐列表。

⇒ 落地时**照公式实现了**（不改 spec 的意思），但登记为待裁：要么删掉，要么改成有实际判别力的形式（例如「starter=0 **且没有任何命中理由**时减 2.0」—— 那才会真的压掉「只有领域重合、没有任何原文命中」的词条）。**本轮未改，须 owner 裁定。**

#### FR-6.3 增强层：Pi 语义匹配（**可关、可缺、失败必须降级**）

owner v0.2 裁定「AI 能力使用 pi.dev 进行二次开发实现」，落在推荐链路上是：**把「词面命中」升级为「语义命中」**。

**FR-6.3.1 接入方式（择一，开工时定）**：

| 方式 | 形态 | 取舍 |
|---|---|---|
| **A · RPC 进程**（**建议**） | 起一个 `pi` 子进程，走 stdin/stdout 的 JSON 协议 | ✅ 服务端（Node/fastify）能自然嵌入；✅ 不进依赖树；✅ Pi 挂了只影响这一层 |
| B · SDK | 直接 `import` Pi 的 SDK | 类型最友好，但把 Pi 变成**硬依赖** —— 违反 §2.4 硬约束 1 |
| C · Print/JSON | `pi -p "..."` 一次性调用 | 最简单，但无会话、无流式，批量场景慢 |

⚠️ **A 的关键前提**：**Pi 必须是可选依赖**（不在 `package.json` 必需项里），由设置页的「AI 能力」节探测其可用性（FR-8）。

**FR-6.3.2 调用形态**：给 Pi 的输入是**脱敏后的项目画像**（项目名 ＋ 阶段名 ＋ checklist 文本 ＋ Skill 名），输出是**候选术语 id 列表 ＋ 各自的一句理由**。

⚠️ **必须用结构化输出**（要求 Pi 返回 JSON，并做 schema 校验），**不解析自然语言里「提到了哪些词」** —— 后者不可测、不可复算。

**FR-6.3.3 ⚠️ 降级矩阵（本条是 FR-6.3 的核心，不是补充）**：

| 情况 | 行为 | 用户可见 |
|---|---|---|
| AI 总开关关 | 只跑基线层 | 区块显示「未启用 AI 增强」 |
| Pi 未安装 / 不在 PATH | 只跑基线层 | 同上，并给「如何安装」提示 |
| Pi 进程起不来 | 只跑基线层 | 同上 |
| Pi 调超时（初始 30s） | 只跑基线层 | 同上 |
| Pi 返回不合法 JSON | 只跑基线层 | 同上 |
| Pi 返回合法但候选全被门槛滤掉 | **显示「AI 也没找到该学的」** | 必须如实显示，不能静默退回基线结果假装是 AI 的结论 |

⚠️ **最后一行是本条最容易被写错的地方**：降级时**不能把基线结果包装成 AI 的输出**。用户看到「AI 推荐」就必须真的是 AI 给的，否则这个功能一旦出错就再也修不好信任。

**FR-6.3.4 合并规则**：AI 候选与基线候选**取并集**，AI 命中的**排在前面**并标 AI 标记；两者都过同一个门槛与上限（FR-6.4）。

#### FR-6.4 门槛与可解释（**两层共用，不可分层放宽**）

⚠️ 本条的**验收判据是「误报率」不是「召回率」**：一个术语推荐错了，用户就再也不信这个功能了。因此：

- **绝对分数门槛**（初始 `score ≥ 3.0`），达不到就**不推荐**；
- **单项目推荐上限 12 条**（一屏能读完）；
- **每条推荐必须显示「为什么推给你」**（命中了哪句 checklist / 哪个 Skill，或 AI 给的理由）—— 否则用户无法判断该不该信；
- ⚠️ **AI 层不给门槛豁免**。AI 说「这个项目该学熔断器」，若基线分数不足门槛，**要么两条都不进，要么显式标注「AI 推荐 · 确定性匹配不足」**。**不允许静默放行**。

#### FR-6.5 写侧：AI 产出**一律走既有回流通道**

⚠️ 本条是为了防「AI 直接改库」。AI 生成的**场景句**、AI 建议的**词条修订**，**都不许直接写 `terms` 表**：

- 走既有 `POST /api/agent/ingest` 回流通道；
- 受 `agentWriteEnabled` 总闸约束（**默认关**，DEV-0128 已落地）；
- 进「待确认回流」列表，**人工确认后才落库**。

**判级**：**B 级**（新服务 ＋ 新端点 `GET /api/projects/:id/term-recommendations`）。

### FR-7 误报控制与隐私

**FR-7.1** 基线层推荐**只读**、**本地计算**、**不出网**。

⚠️ **启用 Pi 增强后本条要改写**：请求会**出网到用户自己配置的 provider**。因此：

| 项 | 规则 |
|---|---|
| 出网范围 | **仅到用户自己配置的 provider**，产品**不设中间代理**、不代管密钥 |
| 发送内容 | **脱敏后的项目画像**（FR-6.3.2），**不含** `local_path`、任务正文、文件内容 |
| 必须显式告知 | 设置页 AI 节必须写明「启用后项目名称与阶段清单会发送给你配置的模型服务商」 |
| 可撤回 | 关掉总开关即**完全停止**出网（不是「不再展示结果」） |

**FR-7.2** ⚠️ **`projects.local_path` 不得进入任何发往 Pi 的内容，也不得进入推荐结果的可解释文案**。它含用户本机目录（如 `/Users/duke/...`）—— 发出去等于泄露本机结构。只用 `name` 与 `stages_snapshot` 的业务文本。

**FR-7.3** 新端点归入**遥测白名单**的处理须登记 —— 只读端点，不上报内容。

**FR-7.4** ⚠️ **Pi 自身的遥测默认须关**。Pi 有自己的 model/provider 配置；本 spec 不改 Pi 行为，但设置页的 AI 节须提示用户「如需完全无遥测，请在 Pi 侧关闭」。**这是知情义务，不是代管义务。**

### FR-8 设置页「AI 能力」节（owner v0.2 裁定：**配置开关做在设置页**）

**FR-8.1 落点**：**与既有「助手桥接」节并列，成为新的一节**。

⚠️ **不做成「助手桥接」节的子项**，也不挂进第 7 区「可读性与设计系统」。理由与 DEV-0128 同款：**归属说谎比代码风格问题更严重** —— AI 能力属 M8/M3-T，不属「可读性」，也不是 agent 回流的下游。
⇒ 独立文件 `apps/web/src/components/settings/AiCapabilitySection.tsx`，挂载点由 `SettingsPage.tsx` 负责（与 `AgentSettingsSection` 同样处理）。

**FR-8.2 开关清单**：

| 键 | 默认 | 作用 |
|---|---|---|
| `aiEnabled` | **`false`** | **AI 能力总开关**。关 ⇒ 全部 AI 能力停用且**不出网** |
| `aiEngine` | `'auto'` | 引擎选择：`auto`（探测 Pi）｜ `off` ｜ `pi-rpc` |

| `aiModel` | `''` | 模型标识 |
| `aiRecommend` | `false` | 「本项目该掌握」的 AI 增强子开关（FR-6.3） |
| `aiScenarioGen` | `false` | 场景句生成子开关（FR-4.2） |

⚠️ **两个子开关默认都关**，且**不能被总开关之外的任何路径单独打开** —— `aiEnabled=false` 时子开关为 `true` 是**无效状态**（读侧一律以总开关为准）。

**FR-8.3 配置链路**：**沿用既有 `AppMetaRepo`，不改迁移**（与 DEV-0128 的 `agentWriteEnabled` 同款）。

- 新增键进 `APP_META_KEYS`（单一出处）；
- 新增端点 `GET/POST /api/settings/ai-capability`；
- ⚠️ **不新建 settings 表**，也不把 Pi 的检测逻辑塞进 repo 层 —— **repo 只存值，探测在服务层**。

**FR-8.4 ⚠️ API Key 不得进 `app_meta`**。`app_meta` 是跨进程 KV，设置页会读它回显。密钥落那里等于把密钥变成「一个可回显的设置项」。
⇒ **密钥不进产品**：Pi 侧已有的 provider 配置就是密钥归属处，OpenVibe 只记 `aiProvider`/`aiModel` 这类**非敏感标识**。
⚠️ 若 owner 要求产品代管密钥，那是**另一项设计**（涉及加密存储与脱敏回显），**不在本 spec**，届时须单独裁。

**FR-8.5 可用性探测必须可见**：AI 节要显示 Pi 的当前状态（**未安装 / 已安装 / 版本**）与最近一次调用结果（成功 / 失败原因）。
⚠️ **不给一个「已启用」却不知道能不能用的开关** —— 那是最坏的形态：用户以为在用，实际每次都静默降级（FR-6.3.3）。

**FR-8.6 默认关必须在界面上写明**，与 `AgentSettingsSection` 现有做法同款（`defaultOffNote`）。

**判级**：**B 级**（新设置节 ＋ 新端点 ＋ 六个 `app_meta` 键）。

### FR-9 AI 调用留痕：**让不可复算的东西可追责**

⚠️ 本条要解决的问题：**基线层是纯函数，AI 层不是**。同一项目两次跑，AI 给的候选可能不同。后果很具体：今天断言「推荐里必须有『幂等』」，明天模型换个说法就红了 —— **这不是回归，是噪声**，但没人分得清。

**FR-9.1 每次 AI 调用落一条台账事件**，记录**足以事后复盘的最小集**：

| 字段 | 内容 | 为什么 |
|---|---|---|
| `kind` | ⚠️ **需新增一类 kind**，见 FR-9.2 | 与 `cli_agent_command_run` 同族（都是「AI 侧发生了一次调用」） |
| 模型标识 | `aiModel` ＋ `aiProvider` | 换模型导致输出变化时，唯一能解释的是这个 |
| 输入摘要 | 画像的**指纹**（hash），**不含原文** | 见 FR-9.3 |
| 输出统计 | 返回候选数、过门槛数、被丢弃数 | 「为什么一条都没进」要能回答 |
| 结果 | `ok` / `timeout` / `bad_json` / `error` ＋ 失败原因 | FR-6.3.3 降级矩阵的六种情况要能对账 |
| 耗时 | 毫秒 | 超时调优的依据 |

- **FR-9.1-b** `payload_json` **允许键**（闭集，超出即测试红，与 m8 FR-5.1 同一守卫同款写法）：`ai_recommend_call` → `aiModel` / `aiProvider` / `inputHash` / `candidateCount` / `passedCount` / `droppedCount` / `result` / `failureReason` / `durationMs`。（`inputHash` 是画像指纹；`result` 是枚举 `ok|timeout|bad_json|error`）

⚠️ **为什么上表不够、还要这一行**：FR-9.1 的表说的是「记什么」，不是「键叫什么」。而台账 payload 的守卫是**键闭集**判据（`AGENT_PAYLOAD_SHAPE` 派生 `AGENT_PAYLOAD_KEYS`），它要拿**规格原文**逐字比对才算双向。若规格只给中文描述，守卫就只能单向断「实现 ⊆ 描述」，**规格多写一个键就永远抓不住** —— 那正是 `agentPayload.test.ts` 里那条守卫当初要防的「规格漂移」。⇒ 这一行是**为了让守卫有可解析的规格面**，不是重复表述。

**FR-9.2 ⚠️ 新增 kind 是**双源同步的契约变更**，不是加一行常量**。

实测依据（`packages/core/src/db/migrations/0007_local_events_and_agent_bridge.sql:14-24`）：

- `local_events.kind` 有 **SQLite `CHECK (kind IN (...))`** 硬约束；
- 该文件注释明写「**必须与 `packages/shared/src/constants.ts` 的 `LOCAL_EVENT_KINDS` 逐字相同**，由 core-db 同族测试解析本文件比对」。

⇒ **三处必须同改，且缺一处就有测试红**：`LOCAL_EVENT_KINDS`（18 → 19）＋ `AGENT_PAYLOAD_SHAPE` 新条目 ＋ **新迁移 `0010`** 重建表（⚠️ SQLite **不能 `ALTER` 一个 CHECK 约束**，必须建新表复制数据再换名）。
⇒ 本条判级因此**从 C 级升到 B 级**，不再按「纯埋点」处理。

**FR-9.3 ⚠️ 留痕不等于把内容存下来**。`payload_json` **只存指纹与计数，不存项目画像原文、更不存 checklist 文本**。
理由：台账是本地长期留存，落进去就等于**长期保存项目内容** —— 那与 FR-7.2「`local_path` 不得外流」是同一条纪律的本地版本。用户清项目不代表同意把内容复制进另一张表。

**FR-9.4 推荐结果以基线层为稳定输出**。AI 只做**排序加权与补充**，不做唯一来源。
⚠️ 理由：**回归测试只对确定性输出成立**。若页面主列表完全由 AI 决定，就等于给功能装了一个永久 flaky 的测试。

**判级**：**B 级**（台账 kind 扩项 ＋ 新迁移 ＋ payload 形状）。

### FR-10 Pi 版本与能力闸：**方案不能被上游静默打断**

⚠️ 本 spec 的 P4 **全部押在 Pi 的两条性质上**：**可嵌入**（FR-6.3.1） ＋ **MIT**（§2.4）。Pi 已发到 1.0 且在快速迭代（pi.dev 顶部公告：「Pi 1.0 ＋ Pi Durable」）。任一条变了，P4 都要重评 —— **而重评的成本远高于提前发现**。

**FR-10.1 协议闸**：`LICENSE` 非 MIT ⇒ **P4 停工**（不是「评估后再说」）。MIT 是本方案敢依赖第三方代码做二次开发的唯一依据。

**FR-10.2 能力闸**：AI 节要显示 **Pi 版本号**，并对**已知不兼容的大版本**给出显式提示。
⚠️ **不硬编码 Pi 的版本号**（它会变，硬编码即过期）。只维护一个「**已核验可用的版本区间**」的常量，超出区间就提示重验。

**FR-10.3 升级即重验**：Pi 大版本升级后，**P4 的 9 支 AI 判据必须全跑一遍**才算通过。
⚠️ 依赖外部进程的判据（AI-M3T-01/02/03）在本机没装 Pi 时会**永远绿** —— 所以这三条必须**同时跑「装了真 Pi」与「没装」两种形态**，只跑一种等于没跑。

**FR-10.4 探测失败不得静默**：探测 Pi 时若进程起不来、超时、版本解析不了，AI 节要显示**失败原因**，不得显示成「未安装」（两者处置不同：前者是 Pi 坏了，后者是没装）。

**判级**：**C 级**（一个常量 ＋ 一处探测 ＋ 一处显示）。

## 9. 复算命令

```bash
# 数据底账（§2 的 441 条分布）
sqlite3 ~/.openvibe/data/openvibe.db \
  "SELECT source, status, COUNT(*) FROM terms GROUP BY source, status;"
#   → openvibe-seed|active|109 · vibe-hub|active|332

# 领域分布（FR-3.1 词表的实测来源）
sqlite3 ~/.openvibe/data/openvibe.db \
  "SELECT json_extract(tags,'\$[0]') d, COUNT(*) FROM terms WHERE source='vibe-hub' GROUP BY d ORDER BY 2 DESC;"
#   → 前端 140 / 后端 69 / AI 30 / 产品 25 / 设计风格 24 / 技术栈 19 / Git 15 / 测试 10

# 分类覆盖（FR-2.3，441 条必须齐）
node -e "console.log(require('./content/seed/term-levels.json').items.length)"   # → 441

# 自然键唯一性（⚠️ 必须用 quote()：裸 || 拼接遇 NULL 即 NULL，会静默少算 43 条）
sqlite3 ~/.openvibe/data/openvibe.db \
  "SELECT COUNT(*) 总数, COUNT(DISTINCT quote(zh)||char(31)||quote(en)) 唯一自然键 FROM terms;"
#   → 441 | 441

# 漏判自证：自然键集合必须与库内完全相同
# ⚠️ 两边必须用**同一种序列化**：`quote()` 出单引号、`JSON.stringify` 出双引号，
#    直接混用会全线不匹配且看不出原因。故统一走 JSON 数组（json_array 遇 NULL 记 null）。
sqlite3 ~/.openvibe/data/openvibe.db "SELECT json_array(zh, en) FROM terms ORDER BY 1;" | sort > /tmp/db.txt
node -e "const i=require('./content/seed/term-levels.json').items; console.log(i.map(x=>JSON.stringify([x.zh,x.en])).join('\n'))" | sort > /tmp/lvl.txt
diff /tmp/db.txt /tmp/lvl.txt && echo '✅ 441 条自然键完全一致'
```

⚠️ **导出命令必须处理内嵌换行**。本次实测踩到：`sqlite3` 直接导出时，`definition` 里的换行会把一条记录**拆成多行**，导致 43 条被误判为「漏分类」（实测 332 行里只有 289 条真条目）。
⇒ 复算一律用 `replace(definition, char(10), ' ')`，或导出后 `grep -v '^$'` 再核对。**这一条写在这里就是为了不让下一个人重踩。**

## 10. 与 M8-A 的关系：**先对照，不先动手**

⚠️ **Pi 的 skill 约定顺带解开了 M8-A，但这超出本 spec 范围**，且「**解开**」两个字有陷阱。

**FR-10A.1 M8-A 卡住的真实原因**（引 `m8-agent-bridge.md` §2 Out 行原文）：

> 它的核心形态取决于 Trae/CodeBuddy 的 skill 发现约定（目录/格式），而该约定**运行半边本轮未经真机核验**……形态三问（**复制 vs symlink** · 第二把锁的 `clean` 边界 · **`minicode` 归属**）未闭合。

**FR-10A.2 ⚠️ Pi 提供的是一个「可核验的落点」，不是那三个问题的答案**。

Pi 的 skill 约定能回答「目录/格式」，但那三问里：

| 三问 | Pi 能不能顺带解决 | 为什么 |
|---|---|---|
| **复制 vs symlink** | ❌ **不能** | Pi 语境下的答案**可能与 Trae/CodeBuddy 不同** ⇒ 拿 Pi 的答案去回答 Trae 的问题**本身就是错的** |
| 第二把锁的 `clean` 边界 | ❌ 不能 | 与 Pi 无关，不会被顺带解决 |
| `minicode` 归属 | ❌ 不能 | 同上 |

⇒ **Pi 把「约定不可读」变成「约定可读」，但没有把「三问未闭合」变成「三问已闭合」。** 这两件事差别很大，混淆它会直接产出一个错的 M8-A。

**FR-10A.3 因此本 spec 的立场**：**先产一页对照表，不先写 spec**。

对照表要能回答：「照 Pi 做，`m8-agent-bridge.md` 的哪几条要改？M8-A 是**适配 Pi**还是**重写**？」—— **这是 owner 的判断，不是实现细节**。
