## 1. 目标与用户价值

**一句话**：术语库从「能查到词」变成「照着能学会」—— 按领域分区、按难度递进，并主动告诉你「你这个项目该掌握哪些词」。

owner 的原话是「术语库是用来学习专业开发术语的，现在看不懂这个术语」。这句话里的**「看不懂」不是排版问题，是内容层次问题**：

| 现状 | 证据 |
|---|---|
| 109 条自建词条的定义**平均只有 53 字**，且大量是行话 | `content/seed/terms.json` 实测：definition 平均长度 53 |
| 例如「层级 / Z-Index」的定义里直接出现「层叠上下文」「包含块」「脱离文档流」 | 库内实测原文 |
| 新手读完**更糊** —— 用五个没懂的词解释一个没懂的词 | 同上 |
| 页面是**纯表格**（术语 / English / 别名 / 定义 / 状态 / 层级） | `TermsTable.tsx:92-100` 实测表头 |

参考站 vibe-hub.org 的解法有三招，本 spec 全部采纳：**① 按领域分区**（前端 146 / 后端 73 / AI 43 / Git 15 / 产品 25 / 测试 14 / 技术栈 20 / 设计风格 24）；**② 卡片式呈现**（每张卡先给一句「大白话场景句」，再给术语定义）；**③ 大白话反查**（用「登录弹窗」也能搜到「Modal」）。

## 4. 功能需求（FR）

### FR-1 数据模型：新增两列

**FR-1.1** `terms` 表新增：

```sql
-- 0008_terms_learning.sql
ALTER TABLE terms ADD COLUMN level TEXT NOT NULL DEFAULT 'L2';
ALTER TABLE terms ADD COLUMN starter INTEGER NOT NULL DEFAULT 0;
```

**FR-1.2** 取值闭集，**必须是 Zod enum + 常量单一出处**（`packages/shared/src/constants.ts`）：

```
TERM_LEVELS = ['L1', 'L2', 'L3'] as const
```

- `level`：`L1` 入门 / `L2` 进阶 / `L3` 深入
- `starter`：`0` 非入门必需 / `1` 入门必需

**FR-1.3** ⚠️ **默认值给 `L2` / `0`，不是「空」**。理由：库里有用户自建词条（`source='manual'`），它们没有分类依据；给 `L2`/`0` 意味着「按中位处理」，而给 `NULL` 会让每个读取点都要写一遍 `?? 兜底` —— 而**默认值写进 DDL** 只需一处。（这一条是刻意的取舍，不是遗漏。）

**FR-1.4** `TermOut` 增加 `level: 'L1'|'L2'|'L3'` 与 `starter: boolean`（**DB 的 0/1 在 repo 边界转成 boolean**，不让 `0/1` 泄漏到 API 与前端）。

**判级**：**B 级**（响应形状 additive 变化，与 m3 v1.1 加 `pinyin` 同级）。

### FR-2 难度与「入门必需」两个维度（**441 条已全部判定**）

**FR-2.1 判定口径**（已用于本次全部判定，是判据的一部分）：

**难度** = 一个刚开始 vibe coding 的中文用户理解这个词条的**认知负担**。

| 档 | 判据 | 例 |
|---|---|---|
| `L1` | 不需任何前置知识，见到即懂 | 按钮、链接、输入框、保存、撤销、部署 |
| `L2` | 需要一点编程或用 AI 工具的常识，不需要系统知识 | 组件、状态、接口、分支、依赖 |
| `L3` | 需要系统知识或工程经验，通常还牵涉边界与陷阱 | 层叠上下文、包含块、幂等、熔断器、租约 |

⚠️ **反模式（本次实测踩到并已规避）**：不按中文名的术语化程度判。`URL` 对新手是 L1（就是个地址），`XML 站点地图` 名字唬人但定义说清了「给机器读的 URL 清单」，判 L1/L2 而非 L3。**以定义文本的实际认知负担为准**。

**入门必需** = 刚接触 vibe coding 的人，在**第一个真实项目**里会不会用到、且不懂会实际卡住。

⚠️ 与难度**独立**：允许 `L1+N`（简单但非必需，如圆角、分页）与 `L3+Y`（难但绕不开，如依赖、增量提交）。

**FR-2.2 分布实测**（441 条全部判定完毕，如实登记不掩饰偏斜）：

| 来源 | L1 | L2 | L3 | 入门必需 Y | N |
|---|---|---|---|---|---|
| vibe-hub 332 条 | 150 | 148 | 34 | 108 | 224 |
| 自建 109 条 | 12 | 86 | 11 | 26 | 83 |
| **合计 441 条** | **162** | **234** | **45** | **134** | **307** |

⚠️ **两批的口径差异是真实的，不是 bug**：vibe-hub 那批以前端组件为主（大量「按钮/输入框/卡片」类 L1）；自建那批集中在方法论/协作/打包分发（大量 L2）。两批混在一张表里按难度排序，**分布会显得很偏**，所以 FR-4 明确要求分区**在难度之前**。

⚠️ **判定过程中抓到的一个坑（写在这里防复发）**：首轮分类只覆盖了 **289/332** 条，43 条漏判。根因不在判定，在**导出**——`sqlite3` 直接导出时 `definition` 字段里的换行把一条记录拆成多行，那 43 条被拆散后混在空行里。子 agent 如实报告了「输入 332 行、实际 289 条」，**但没有把「少 43 条」与「输入文件有问题」关联起来**。
⇒ 通法：导出时 `replace(definition, char(10), ' ')`，且**导出后必须用 `SELECT id` 与判定产物做 `diff`**（§9 有现成命令）。**只核对行数会漏掉这一类** —— 行数是对的（332），错的是行与条目的对应关系。

**FR-2.3** 判定产物落 `content/seed/term-levels.json`（441 条 `id → {level, starter}`），**不进 seed 主体**。理由：seed 主体是词条内容，难度是派生标注；分开落盘后词条更新不动标注。

**判级**：C 级（纯数据）。

**FR-4.2 卡片三段式**（对着 owner「看不懂」这条直接设计）：

| 段 | 内容 | 为什么 |
|---|---|---|
| ① **大白话场景句** | 一句「你什么时候会用到它」，用**不含术语本身**的话写 | 参考站的核心解法。定义里全是行话，先给一个能懂的场景再给定义 |
| ② 术语定义 | 折叠（默认收起） | 卡片高度可控；想深究再展开 |
| ③ 相关词 ＋ 入库动作 | 双向关联 chip ＋ 「加入选集」 | 复用既有选集 → TERMS.md 链路，不新建通道 |

⚠️ **① 是本 spec 唯一「要写新内容」的地方**，工作量集中在 441 条的**场景句**上。**这是新增内容，不是重新生成定义** —— 定义保持原样（那是 vibe-hub 与自建作者写的），只加一句场景引导。

**FR-4.3** ⚠️ **保留表格视图**（现有「表格 / 学习路线」二选一里，「表格」那一路改造成真正的表格视图）。理由：441 条要**成批选入 TERMS.md**，表格的密集多选比卡片高效。强行只留卡片会让选集这件事变难用。

**FR-4.4** 空态与边界：筛选后 0 条要给「当前筛选没命中」并能一键清除（复用既有 `AssetNoResults`）。

**判级**：C 级。

### FR-5 搜索：从「查到词」到「查到意思」

**FR-5.1** 搜索命中面**保持现状**（中文子串 / 英文 / 别名），**不扩大** —— m3 FR-4 已实现且有专门的中文降级用例（两字词走降级匹配）。

**FR-5.2** 新增：**搜不到术语时，回退搜场景句**。用户搜「登录弹窗」应该能找到「Modal」—— 参考站的「大白话反查」。实现上是在搜索时一并匹配场景句文本，**命中后高亮场景句**。

⚠️ 已知边界：场景句是自由文本，中文子串匹配会有噪声（如搜「表单」命中大量无关句）。**处置**：命中场景句的结果**排在术语名命中之后**，不与精确命中混排。

**判级**：C 级。

### FR-6 多源推荐：「这个项目该掌握哪些术语」（owner 要求**真接真实数据**）

**FR-6.1 数据源**（全部取自本地库，**不调外部 API**）：

| 源 | 取什么 | 实测可用性 |
|---|---|---|
| 项目流程阶段 | `projects.stages_snapshot` 的 `checklist[].text` | ✅ 实测有 7 个阶段、17 条 checklist |
| 提示词库 | `prompts.tags` + `folder_path` | ✅ 实测 21 条 |
| Skill | `skills` 表的 name/description | ✅ 实测 438 条 |
| 项目标准包 | `standard_pack_id` 及其内容 | ⚠️ 实测当前项目**未绑定**（列为可选源） |
| 术语自身 | `tags` / `aliases` / 定义 | ✅ 441 条 |

**FR-6.2 匹配算法（确定性，无 LLM）**：

三段式打分，每段都有可解释的权重：

```
score(term, project) =
    2.0 × 术语/别名 在 checklist 文本中直接命中
  + 1.5 × 术语 标签 与 项目领域(由阶段名+技能推导) 重合
  + 1.0 × 术语 与 项目绑定的 Skill 名称/描述 有词面重合
  + 0.5 × starter = 1（入门必需整体上浮，避免推荐结果全是冷门深水区）
  - 2.0 × starter = 0 且 score < 阈值（冷门且弱相关 → 压下去）
```

**FR-6.3 关键约束：宁可少推，不可乱推。**

⚠️ 本条的**验收判据是「误报率」不是「召回率」**：一个术语推荐错了，用户就再也不信这个功能了。因此：
- 设置**绝对分数门槛**（初始 `score ≥ 3.0`），达不到就**不推荐**；
- 单项目推荐条数**上限 12 条**（一屏能读完）；
- 每条推荐**必须显示「为什么推给你」**（命中了哪句 checklist / 哪个 Skill），否则用户无法判断该不该信。

**FR-6.4 呈现**：术语库页顶部一个「本项目该掌握」区块 + 项目详情页一个入口。**两处共用同一份服务**（`termRecommendationService`），不在前端各算一遍。

**判级**：**B 级**（新服务 ＋ 新端点 `GET /api/projects/:id/term-recommendations`）。

### FR-7 误报控制与隐私

| **P1 数据** | FR-1 两列 ＋ FR-2 难度/必需度 ＋ FR-3 领域映射 ＋ 回填 441 条 | 数据层单测；`/terms` 页面不变但接口多两个字段 |
| **P2 呈现** | FR-4 卡片分区 ＋ FR-5 场景句搜索 | 真机看效果 |
| **P3 推荐** | FR-6 推荐服务 ＋ FR-7 边界 | **误报率抽检**（见 §7） |

⚠️ **P2 依赖 P1 的场景句内容**（441 条场景句是新增内容，工作量最大）⇒ 若要早看效果，可先做 P1 ＋ P3（推荐列表不需要场景句也能算）。

### 6.2 风险登记

| 风险 | 说明 | 处置 |
|---|---|---|
| **场景句质量不齐** | 441 条人工写，水平必有差。写得差的场景句**比没有更糟** | 只对 `starter=1` 的 **134 条**先写场景句（实测 108+26）；`N` 的先留空，卡片走「定义直出」形态。**宁可部分覆盖，不要全库注水** |
| **难度分类主观** | 两批词库难度分布差异极大（§2.4） | 口径已写进 FR-2.1，可复核；争议项留理由 |
| **推荐误报** | 关键词匹配天然有噪声 | FR-6.3 的门槛 ＋ 可解释文案 ＋ 抽检 |
| **两批词库风格割裂** | vibe-hub 有英文名与子分类，自建那批粒度粗 | 分区按领域，领域内不强制统一子分类 |
| **重建产物需重启服务** | DEV-0119 实测：`fastifyStatic` 的 `wildcard:false` 在注册期枚举路由 | 验证前记得重启；**这是既有坑，不是本 spec 引入** |

## 7. 验收判据（**全部是能红的**）

| ID | 判据 | 怎么证明它能红 |
|---|---|---|
| **WEB-M3T-01** | 两列有默认值 | 建一条无 `level` 的词条，读回必须是 `L2`/`false`，不是 `undefined` |
| **WEB-M3T-02** | `TERM_LEVELS` 是单一出处 | 前端出现字面量 `'L3'` 即红（**须先剥注释再扫**，与 `design-tokens.test.ts` 同款纪律） |
| **WEB-M3T-03** | 441 条**全部**有非默认值 | 变异腿：把某条的 `level` 改回 `'L2'`，覆盖数应减少 1 |
| **WEB-M3T-04** | 领域归一无遗漏 | 自建那批每条都要有领域；变异腿：删掉一条的映射，覆盖数应减少 1 |
| **WEB-M3T-05** | 推荐带可解释文案 | 断言每条推荐都有非空的「为什么」；变异腿：去掉该字段 ⇒ 红 |
| **WEB-M3T-06** | 推荐遵守门槛与上限 | 构造 score 低于门槛的输入 ⇒ 推荐条数必须为 0（**这条最容易被写成永真，构造必须真能压到门槛以下**） |
| **WEB-M3T-07** | 推荐不含本机路径 | 断言结果文本里**不出现** `projects.local_path` 的值 |
| **WEB-M3T-08** | 表格视图仍在 | 卡片视图下仍能进入表格视图并多选（TERMS.md 链路未断） |
| **WEB-M3T-09** | 场景句搜索排后 | 同时命中术语名与场景句时，术语名命中在前 |

⚠️ **WEB-M3T-06 是本 spec 最容易造假的一条**：`score` 若用固定夹具，取值天然高于门槛 ⇒ 恒真。**必须构造一条真的低于门槛的输入**并自证它低于门槛，否则这条判据等于没写。

## 8. ⚠️ 本 spec 尚未闭合的待裁

| # | 待裁 | 为什么需要 owner |
|---|---|---|
| 1 | **难度与「入门必需」是否要两个独立维度** | 实测两批词库的口径差异极大（§2.4）；合并成一个字段会让筛选条变短但信息丢失。owner 已选「人工分类全部」，但**未裁维度数** |
| 2 | **场景句写 134 条还是全 441 条** | 建议只写 `starter=1` 的 134 条（§6.2）。全量 441 条质量风险高、工作量大 |

| 4 | **是否给 vibe-hub 词条补场景句** | 那批词条是外部来源，改动它们等于修改第三方内容（且 `source='vibe-hub'` 的溯源语义要保留） |

## 9. 复算命令

```bash
# 数据底账（§2 的 441 条分布）
sqlite3 ~/.openvibe/data/openvibe.db \
  "SELECT source, status, COUNT(*) FROM terms GROUP BY source, status;"
#   → openvibe-seed|active|109 · vibe-hub|active|332

# 领域分布（FR-3.1 词表的实测来源）
sqlite3 ~/.openvibe/data/openvibe.db \
  "SELECT json_extract(tags,'\$[0]') d, COUNT(*) FROM terms WHERE source='vibe-hub' GROUP BY d ORDER BY 2 DESC;"
#   → 前端 140 / 后端 69 / AI 30 / 产品 25 / 设计风格 24 / 技术栈 19 / Git 15 / 测试 10

# 分类覆盖（FR-2.3，441 条必须齐）
node -e "const l=require('./content/seed/term-levels.json');console.log(Object.keys(l).length)"   # → 441

# 漏判自证：id 集合必须与库内完全相同
sqlite3 ~/.openvibe/data/openvibe.db "SELECT id FROM terms;" | grep -v '^$' | sort > /tmp/db.txt
node -e "console.log(Object.keys(require('./content/seed/term-levels.json')).sort().join('\n'))" > /tmp/lvl.txt
diff /tmp/db.txt /tmp/lvl.txt && echo '✅ 441 条 id 完全一致'
```

⚠️ **导出命令必须处理内嵌换行**。本次实测踩到：`sqlite3` 直接导出时，`definition` 里的换行会把一条记录**拆成多行**，导致 43 条被误判为「漏分类」（实测 332 行里只有 289 条真条目）。
⇒ 复算一律用 `replace(definition, char(10), ' ')`，或导出后 `grep -v '^$'` 再核对。**这一条写在这里就是为了不让下一个人重踩。**
