## 1. 目标与用户价值

- **一句话**：把「入口只剩 22 B 余量」这条随时会断的线，换成一个有余量、有归因、有制度的预算面。
- 用户不直接感知这件事，但**用户的第一个动作感知它**：README 第一条命令之后的每一次页面加载都来自这个入口 chunk。J4 的判断（分析文 §0.2）是「一条余量 0.007% 的闸，等于把所有并行会话的提交绑在一根线上」——现测余量确实是 22 B（§3 给复算命令）。
- 三个动作互相咬合，所以住在同一份规格里：**先把数据表搬出入口**（FR-6/FR-7，AD10）→ **再拆 i18n**（FR-1…FR-3，AD7 步 1）→ **把余量变成每笔可见的数字**（FR-4/FR-5，AD7 步 2）。顺序不可换：AD10 是 AD7 的前置，否则拆完 `zh.ts`，`TERM_ROADMAP` 那张 data 表照样被 `shared` 的桶形 re-export 拉回入口。
- 差异化立场：**不削弱任何既有闸**。`bundle:check` 的入口 ≤300 kB／chunk ≤500 kB／单 `<script>` 三条一字不动（PRD §10.5 末段「现有闸一律不放松」）。这条是本规格的立论前提——分析文 §4.8 明确：「要么改门禁，要么换手段——改门禁是**削弱闸**，换手段是**不削弱闸的等价解**」。

**两处与分析文不符**（分析文 §10-8 要求转入任务时重采一次，已执行）：其 §4.12 写「13 个 `export *`」与「135 处引用」，**现测 15 与 121**。本文件用现测值，不用分析文值。

**三个新词（本规格定义）**：

- **命名空间（namespace）**：一份按路由切开的文案模块，如 `i18n/zh/packs.ts`；键形制与 `zh.ts` 完全相同，只是体积与可加载时机不同。
- **类型真源（type source of truth）**：`zh.ts` 保留为**形状定义**所在（`type Dict = typeof zh`），各命名空间文件声明 `satisfies Partial<Dict>`；缺键、错型在**编译期**报错，不引入运行期查找。
- **出口面（export face）**：同一个包内按用途划分的入口（契约面 / 内容面 / 常量面），靠 `package.json` 的 `exports` 子路径暴露，**不是新包**。

## 4. 功能需求（FR）

### FR-1 `zh.ts` 按路由命名空间拆分

- FR-1.1 拆为 8 份：`i18n/zh/{common,library,terms,skills,flows,projects,packs,settings}.ts`。切分依据是**页面归属**，不是词条字母序——一个页面的所有文案进同一个命名空间。
- FR-1.2 页面本来就是 `React.lazy`，所以每个页面 `await import('./i18n/zh/<ns>')` **不新增任何网络往返**（这条是 AD7 的核心论证，必须在实现里以「新增 chunk 数 = 页面数 + 0」的形式可验）。
- FR-1.3 `AppShell`／`Toaster`／`Dialog` 这些**跨页常驻**组件只用 `zh.common`，且 `common` 同步加载（目标体积约 2 kB，实际值由 FR-4 的差值报告给出，不在本文件写死）。
- FR-1.4 52 个引用点全部迁移，**不得留兼容出口**（不留 `export * from './zh'` 之类的全量再导出——那等于把 786 行重新拉回入口）。
- FR-1.5 `zh.ts` 文件保留，但其角色改为**类型真源 + common 的实现**；不得删除（删了就没人定义 `Dict`）。

### FR-2 编译期完整性

- FR-2.1 `type Dict = typeof zh` 是唯一形状源。
- FR-2.2 每个命名空间文件 `export default { ... } satisfies Partial<Dict>`。
- FR-2.3 **反向闸**：`Dict` 里存在、但八个命名空间并集里不存在的键 ⇒ 视为漏拆，必须有一条机判（`UT-I18N-*`）。FR-2.2 的 `satisfies` 只拦「拆出来的键不在 `Dict` 里」，拦不住「`Dict` 里有键没人拆」——这条闸是本规格补的，分析文未提。

### FR-3 `common` 的边界

- FR-3.1 判据：**被 ≥2 个路由命名空间的页面使用的键**才能进 `common`；单页专属键留在该页命名空间。
- FR-3.2 违规形态（必须被测试拒）：把某页专属文案塞进 `common` 以「省事」——这会让 `common` 长成第二个 `zh.ts`，本规格的全部收益归零。

### FR-4 `bundle:check` 差值报告

- FR-4.1 失败信息从「超了 X kB」升级为「**本笔 vs 上一笔的差值 + 归因到文件**」。
- FR-4.2 归因来源用 vite 的 `metafile`／`sourcemap`（`[DEV-0082]` 已在别处用过这个手法，属既有能力，不新引依赖）。
- FR-4.3 **成功时也要报余量一行**（不只失败才报）。判据：故意加 1 kB 文案 ⇒ 报出「+1.0 kB，归因 zh.ts」型信息；余量数字每次可见。
- FR-4.4 三个既有断言（入口 ≤300 kB、chunk ≤500 kB、单 `<script>`）**行为不变**。差值报告是**附加信息**，不是新阈值，更不是放宽。

### FR-5 余量治理规则（写成 DoD 一行）

- FR-5.1 凡新增进入口的依赖或文案，须在本笔登记里报出**实测差值**（kB，到小数一位）。
- FR-5.2 本条是 C 级纪律，落点在 dev-plan §16.10「现有闸不放松」那一节，不进代码。
- FR-5.3 它的作用是把「22 B 事件」变成制度——**FR-4 提供数字，FR-5 要求人报数字**。

### FR-6 `shared` 三出口面

- FR-6.1 三面划分（AD10 原文形态）：
  - `@openvibe/shared` → **契约面**：zod schemas／errors／ids／纯工具（**无数据、无文案**）
  - `@openvibe/shared/content` → **内容面**：`TERM_ROADMAP`／受控词表／`interviewPrompt`／文案模板（可懒加载）
  - `@openvibe/shared/constants` → **常量面**：状态枚举、文件路径常量（单源）
- FR-6.2 **不拆包**：仍是一个 package，靠 `package.json` 的 `exports` 子路径暴露。
- FR-6.3 拆完之后，`import ... from '@openvibe/shared'`（契约面）**不得**能拿到内容面的数据表——这条是 FR-6 的全部收益所在，必须有机判（`BUILD-BUDGET-*`：断言 `TERM_ROADMAP` 不出现在入口 chunk）。
- FR-6.4 **登记在飞的并行改动（重要）**：截至本文件写作时点，工作树的 `packages/shared/src/index.ts` 已把 `TERM_ROADMAP`／`interviewPrompt` 从 `export *` 改成**具名 re-export**，并新建两个未跟踪文件 `packages/shared/src/roadmap.ts`／`packages/shared/src/interview.ts`。现测（复算：`git show HEAD:packages/shared/src/index.ts \| grep -c 'TERM_ROADMAP'` → **0**；`git cat-file -e HEAD:packages/shared/src/roadmap.ts` → **无此对象**）⇒ **HEAD 上这两个符号仍在 `constants.ts` 里，两个新文件尚未入库**。本 FR 的起点因此不是「从零」，而是「承接一个未入库的半步」；落地前必须先确认那一步的归属，否则两个会话会做同一件事。

### FR-7 状态枚举单源

- FR-7.1 现状是**同物两名**：`apps/cli/src/output.ts:13` 的 `SYNC_STATES` 与 `packages/core/src/inject/planner.ts:14` 的 `INJECT_STATUSES`，五值字面完全相同（`NEW`／`IN_SYNC`／`UPDATE`／`CONFLICT`／`DRIFT`；复算：`grep -rn 'SYNC_STATES = \|INJECT_STATUSES = ' apps packages`）。合一到常量面。
- FR-7.2 改名不得改**输出行为**：CLI 的五态表渲染顺序与文案不变（RF0 明确不改 CLI 语义）。
- FR-7.3 必须一起处置的隐式约定：`apps/cli/src/index.ts:405` 有一条注释「键名不叫 `counts`：printer 一见 `counts` 就渲染注入侧的 SYNC_STATES 五态表，clean 是四态」——这是同物两名派生出的**脆弱耦合**。单源之后，这条约定要么由类型消灭，要么显式写成字段名，不许继续靠注释活着。

## 6. 边界与异常

- **6.1 单 `<script>` 断言与懒加载的关系**：懒加载产出的是**运行时动态 chunk**，`index.html` 里仍只有一个 `<script src>`；`bundle-check.ts:42,43` 查的是 html 里的 `<script>` 标签数，不是 `assets/*.js` 的文件数。这条理解必须在实现前确认，否则会把「多 chunk」误读成「拆 script」并自触红线。
- **6.2 首屏时序**：页面组件 `React.lazy` 与其命名空间文案必须**同批解析完**再渲染，否则出现「先英文空框再填中文」的闪动。判据 = 不存在 `undefined` 文案渲染路径（`UT-I18N-*` 的一条反证用例）。
- **6.3 循环依赖**：`zh.ts` 定义 `Dict`，命名空间文件 `satisfies Dict`，而 `common` 又是运行时同步加载面——`zh.ts` 不得反向 import 任何命名空间文件。
- **6.4 构建缓存**：`apps/web/dist/` 是**上一次构建的产物**，本规格现测的 299,978 B 是产物数不是源码数；任何「入口体积」结论都必须在**重新构建后**取，且登记时标明取数的 sha 与构建时间。
- **6.5 未跟踪文件**：FR-6.4 那两个文件此刻 `??` 状态。本规格**不代为 `git add`**（共享工作树内暂存归属须由提交人逐行核账），也不把它们读成已存在的能力。
- **6.6 与分析文 §8.1-10 同族**：那条自陈「工作树新增了四个未入库文件，而对应 spec 未见版本行更新」——FR-6.4 是它的第五处实例，处置方式相同：**如实登记两树差，不静默**。

## 7. 验收标准（pass/fail）

### 7.1 体积（可自动化，`BUILD-BUDGET-*`）

- a **入口回落**：`stat -f%z` 入口 chunk ≤ 285,000 B（即回落 ≥15 kB，取分析文 §7 · Phase 0 表 0-1 行的门禁判据口径；RF0 开工前先跑一次基线复采，以**当次实测**为准写进登记）。
- b **数据表不出现在入口**：入口 chunk 的文本内不含 `TERM_ROADMAP` 的任何字面量特征串（口径由实现选定后写进断言字面量，且选「会变的不进断言字面量」的写法）。
- c **单 script 不变**：`bundle-check.ts:42,43` 两条断言在新产物下仍为「恰好 1 个」。
- d **阈值不动**：`git diff -- scripts/bundle-check.ts` 里 `entryMaxKb`／`chunkMaxKb` 两行**零改动**。

### 7.2 i18n 完整性（可自动化，`UT-I18N-*`）

- e **形状等价**：同一渲染上下文下，拆分前后取到的全部文案键值**逐键相等**（快照断言，覆盖 8 个命名空间）。
- f **缺键编译期红**：造一个变异样本——从某命名空间删一键 ⇒ `typecheck` 失败（FR-2.2）；造 `Dict` 有、并集无 ⇒ 失败（FR-2.3 的反向闸）。
- g **无全量再导出**：`grep -rn "export \* from" apps/web/src/i18n/` → 0 命中（FR-1.4）。
- h **common 边界**：`common` 内每个键至少被 2 个路由页面引用（FR-3.1），违反者测试点名。

### 7.3 门禁报告（可自动化 + 人工腿）

- i **故意溢出报差值**：造一个 +1 kB 的入口新增 ⇒ 报告含「+1.0 kB」量级与归因文件名（FR-4.3 的判据形态）。
- j **成功也报**：正常构建的 stdout 含一行余量数字（人工截图归档即可，判据是**这行存在且带数字**）。

### 7.4 常量单源（可自动化，`UT-I18N-*` 之外的 `BUILD-BUDGET-*` 单源段）

- k `grep -rn "SYNC_STATES = \|INJECT_STATUSES = " apps packages --include='*.ts'` ⇒ 五值字面量的**定义处只剩 1 个**（现测 2 个：`output.ts:13`、`planner.ts:14`）。
- l CLI 五态表输出**逐字节不变**：`sync`／`diff` 的既有快照用例全绿（行为零变化）。
- m `counts` 键名耦合的处置可验：要么类型上不可能（约定被消灭），要么 `clean` 的四态字段有显式名——注释单独活着不算过（FR-7.3）。

### 7.5 人工腿

- n 打开 `/packs`、`/terms`、`/settings` 三页，各截一张图：文案完整、无空框、无二次填充闪动（FR-1.3／6.2）。

### 7.6 未验证面（负向登记，不得读成已通过）

- **Windows / Linux 产物体积**：本规格全部数字取 **macOS + arm64 + 本机 Node** 的单次构建；三平台 CI 的入口体积差**未测**。README「装包形态只在 macOS 复验过」那条局限对本规格同样成立。
- **真实首屏时间**：体积回落不等于 LCP 改善；未跑性能测量，**不得声称「加载变快」**。
- **差值归因的精度**：`metafile` 归因到模块，不保证归因到「一句文案」；FR-4.1 的「归因到文件」以模块文件为粒度，粒度不足时如实报模块名。
