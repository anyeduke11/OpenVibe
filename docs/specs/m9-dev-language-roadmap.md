### 1.3 ⚠️ 一条会推翻「靠术语库撑起语言路线」的实测

```
术语总数 441，标题命中「语言知识点特征」（语法/类型/函数/协程/指针/并发…）的 = 8 条（1%）
「技术栈」33 条实为 OpenVibe 自身架构概念：锁文件 / 归档包 / 扫描根 / 数据目录 / 内容指纹…
```

**含义**：术语库是**工程方法论词条**（幂等、第一性原理、场景句），**不是语言知识点**。可挂接的只有 8 条量级（如「协程」← Go 的 goroutine+channel、「竞态条件」← 共享内存并发）。

⇒ **关联方向只能是「知识点 → 术语」且会很稀**，绝不能反过来指望「用术语库当语言大纲」。语言路线**必须自建知识点全集**，术语只是挂在知识点上的少量概念锚点。这条决定了整个数据模型（§3.1）。

### 1.4 runoob Python3 全量清单（owner 2026-10-18 指示重收后的实测）

**清单落点**：`docs/devlog-evidence/M9-probe/runoob-python3-inventory.json`（84 条，只存标题 ＋ URL，正文一个字未取——§3.2 FR-2）。

**采集与验链**：索引页 `https://www.runoob.com/python3/python3-tutorial.html`，HEAD 等距抽样 20 条 → **20/20 返回 200**。

⚠️ **采集过程踩到的三个坑，已写进证据文件的 `caveats`，因为它们都会静默产出错数据**：

| 坑 | 后果 |
|---|---|
| Python3 页**不存在** `right-column` 分隔符（Python2 页有） | 按它切分一路读到文末，**站点全站导航混进侧栏**，条目数从 84 虚增到 118 |
| 侧栏 `<a>` 的 `title` / `href` **属性顺序不固定** | 按固定顺序写正则只匹配到一半，**44/84** |
| 源 URL 混有绝对地址的全站导航项 | 不显式排除就会把「PHP 教程」当成 Python 知识点收进来 |

**⚠️ 84 条不等于 84 个知识点**。按可复算的分类规则（标题含「模块/库/驱动」或落在第三方名清单 ⇒ 库级）：

| 类别 | 条数 | 占比 | 含义 |
|---|---|---|---|
| **语言知识点** | 44 | **52%** | 基础语法、数据类型、函数、装饰器、生成器、异常、面向对象、命名空间… —— **这才是学习路线的主体** |
| **库级** | 31 | **36%** | logging、pickle、subprocess、queue、re、csv、threading、asyncio ＋ MySQL/MongoDB/Scrapy/selenium/PyQt… |
| 环境与杂项 | 9 | 10% | 教程/简介/环境搭建/Pycharm/VScode/测验/资源 |

**两条对设计有直接影响的发现**：

1. **「高级教程 44 条」比「基础教程 40 条」还多** ⇒ runoob 的「高级」是个杂项筐，不是学习阶段。⇒ **不得把源的章节名当站名**（§3.6 已写死「站数由实测内容决定」，这条是它的实测依据）。

2. **⚠️ 源顺序 ≠ 依赖关系（有直接反例）**：
   ```
   侧栏位次：Python3 模块 = #28 …… Python logging 模块 = #76   （相隔 48 位）
   ```
   `logging` 明显依赖「模块」与「函数」，而源把它排在与其**平级**的位置。⇒ **§2.3「知识点必须是 DAG 而不是列表」这条决定，被实测数据佐证**，且不是理论洁癖 —— 若照搬源的顺序，`logging` 会排在「模块」前面 48 位，用户会先学日志再学模块。

3. **36% 是库级，它们不构成学习路线的主体**：一个库级条目的前置是「任意语言 ＋ 按需用到」，几乎无序。把它们塞进线性学习路线会稀释路线本身。⇒ **§3.1 的 `lang_topics` 必须有一个 `kind` 维度**（`language` / `library`），界面也分开呈现：路线只走 `language`，`library` 进「按需查阅」区。

## 2. 第一性原理

### 2.1 用户真正的问题不是「去哪学」

五个源都很好学。用户的真实卡点是三问：

1. **我该学什么**（清单）
2. **我学到哪了**（定位）—— ���这是**现状最差**的一问
3. **学这个对我有什么用**（意义）

绝大多数「学习路线」产品只答第 1 问（又一个超链接列表）。**答不出第 2 问，第 1 问就只是信息搬运。**

### 2.2 掌握度的诚实来源只有一个：**行为证据**

三种候选来源的实测判断：

| 来源 | 判断 | 理由 |
|---|---|---|
| **用户自评勾选** | ❌ **不做** | 会退化成 checklist。三天之内全绿，然后失去全部意义 —— 这是所有「已掌握」标记的必然结局 |
| **AI 判断** | ❌ **不做** | 不可复算、不可测；同一段代码两次判断不同，用户无法据行动（与 M3 FR-6.3.3「降级时不得把基线包装成 AI」同源纪律） |
| **行为证据** | ✅ **唯一可做** | 用户**在项目里做过什么**是客观的、可回溯的、本地已有的 |

**行为证据在本仓里已经存在**：项目阶段与 checklist、任务、`dev_log_entries`、`local_events` 台账。P3 已经用其中的 checklist ＋ 阶段名推出「该掌握哪些术语」，并实测出唯一项目推 4 条。

### 2.3 由此得到四个原语

```
① 知识点 DAG      知识点的先后依赖（图，不是列表 —— 「学并发」蕴含「学函数」）
② 掌握度状态      每个知识点 ∈ {未触及 / 在用 / 掌握}，由行为证据推导，非自评
③ 定位            由 ①② 推出「你在第几站」「下一步该学哪三个」
④ 外部出处        每个知识点挂 1~3 条可读链接（只存 URL，不存正文）
```

**①为什么必须是 DAG 而不是列表**：runoob 的目录看起来像线性列表，但「异常处理」在列表第 25 位、在「面向对象」之前，而在 Python 里先学函数才学得出异常。线性序会误导。⇒ 本地维护 `prerequisite` 边，**不用源的顺序当真相**。

### 2.4 与 P3 是同一个原语

```
P3（已落地）：项目 → [checklist/阶段名/skill] → 术语 → 得分 ≥3.0 → 推荐 4 条
本设计：      项目 → [同上证据源]           → 知识点 → 掌握度推导 → 下一步三个
```

差别只有一处：**P3 判「该学哪些术语」，本设计判「已掌握哪些知识点」** —— 后者需要**否定式证据**（学过 vs 没用过），而 P3 只做**肯定式**（出现了就推）。**否定式推断的错误代价更高**（把「正在学」显示成「已掌握」），这是本设计最难的一处，也是 §6 最大的风险。

## 3. 方案设计

### 3.1 数据模型（四张表，均为新建）

```
lang_topics           语言 × 知识点（有向无环图的节点）
  id, lang, slug, title, summary, stage_id, ref_url, ref_title,
  source_kind, source_checked_at,      ← 源停更/改写的取证日期
  kind,                               ← ⚠️ 'language' | 'library'（§1.4 实测 84 条里库级占 36%）
  UNIQUE(lang, slug)

lang_topic_edges      前置依赖（DAG 的边）
  topic_id → prereq_topic_id           ← 两侧都在 lang_topics 内

lang_topic_terms      知识点 ↔ 术语（多对多，**刻意允许稀疏**）
  topic_id → term_id
  ⚠️ 不得反向写入 terms 表：那是 M3 的资产面，本表只做挂接

lang_topic_state      掌握度（推导结果，**可重算、可丢弃**）
  topic_id, project_id, state, evidence_kind, evidence_ref, computed_at
  ⚠️ 存的是**证据**不是分数 —— 分数换算法后要能重算
```

⚠️ **`kind` 维度不是可选项**（§1.4 实测推出）：runoob Python3 的 84 条里 **31 条是库级**（logging / pickle / subprocess / MySQL / Scrapy…）。它们的共同点是**前置关系几乎不存在** —— 一个库级条目的前置是「任意语言 ＋ 某天用到了」，不是「学完 A 才能学 B」。⇒ 把它们混进同一条线性学习路线，会让 36% 的内容变成「学不到就一直卡着」的阻塞点。⇒ `kind='library'` 的条目走「按需查阅」区，不进站、不占进度、不参与 DAG 阻塞判定。

⚠️ **`lang_topic_state` 刻意可丢弃**：它是从证据派生的缓存。若把「当前第几站」也存进去，那是把派生结果当真相 —— 换个判定口径全库都得迁移。**「第几站」必须每次从 `state` 现算。**

### 3.2 外部源的采集（FR-2 的硬约束）

| 项 | 规则 |
|---|---|
| **只存链接不存正文** | runoob 正文有版权；GitHub README 会被上游改写（awesome-python-cn 停更 4 年即证）。**正文一律不入仓** |
| **每条出处必带取证日期** | `source_checked_at`。owner 看到的「4 天前核过」比「某天核过」有用得多 |
| **停更源必须标红** | `awesome-python-cn` 停更 2022-08-29 ⇒ 界面上显式提示「该源已 4 年未更新」，**不静默当作有效来源** |
| **可复算** | 采集脚本须能一条命令复跑并输出差异，判据是「本仓没有一条出处缺 `source_checked_at`」 |

### 3.3 掌握度推导（§2.2 的落地，也是全案最弱的一环）

```
未触及  ← 该知识点的词面在项目活动里 0 次出现
在用    ← 出现过 1~2 次，且其前置全部 ≥ 在用
掌握    ← 出现 ≥ N 次 且 其前置全部「掌握」
```

⚠️ **三个已知的不可靠处，必须在界面上如实说而不是藏**：

1. **同义词漏检** —— 写了 `asyncio.run()` 但从没用过字面词「协程」⇒ 误判「未触及」。**误判方向是把高估变成低估，可接受**；反过来（把「没用过」显示成「会用」）不可接受。
2. **N 的取值无客观依据** —— 取 3 还是 10？这是**产品判断不是技术判断**，见 §6 待裁。
3. **冷门知识永远推不出「掌握」** —— 一个项目永远不会出现「协程」⇒ 用户永远停在「未触及」。**这是本设计的结构性缺陷，不是 bug**，界面上必须显示「本项目未涉及」而不是空白。

⚠️ **判据方向的诚实**：这套推断**天然只认得出「用过」**，认不出「学过但没用过」。**任何声称能回答「我掌握了吗」的表述都是假的** —— 界面文案必须写「本项目用到过」，**不能写「你已掌握」**。这是本 spec 与市面「能力雷达」类产品的根本差别。

### 3.4 术语挂接

- 每个知识点挂 **0~3 条**术语（稀疏是常态，§1.3）
- 界面呈现为「学完这个点，你能读懂这几个词条」→ 链到 `/terms`
- ⚠️ **不做反向写入**：AI 补的知识点若需要新术语，**走 M8 回流通道**进「待确认回流」，人工确认后才落 `terms`

### 3.5 界面

| 落点 | 决定 | 理由 |
|---|---|---|
| 侧栏 | `NAV` 的 `assets` 组，**紧随「术语」之后**，图标 `compass`（待加） | owner 明确要「右侧菜单增加」。它紧邻术语，因为两者互链最密 |
| 语言选择 | 首屏一门语言一个卡片，显示「N 个知识点 / 你在第 M 站」 | 不做语言列表页 —— 那又是一层点击 |
| 主视图 | 左：站列（stage）竖排；右：知识点 DAG 的当前层，带状态三态 | 与 `TERM_ROADMAP` 的站列同形，**视觉机制复用** |
| 空态 | 「本项目未涉及」而非空白（§3.3 第 3 点） | 空白会被读成「功能坏了」 |

⚠️ **V2 设计系统**：本 spec **不新增任何字面色阶**，全部走 `index.css` 的 29 支语义 token；新增的 `tagCls`/状态 chip 形制**须登记进 DESIGN.md**（现状：`.tag` 尚未登记，是本仓已有的待办缺口）。

### 3.6 分站（stage）怎么切

不用源的切法，用**「学完这站能独立做成什么」**：

```
Python：语法基础 → 数据结构 → 函数与模块 → 面向对象 → 异常与文件 →
        并发（协程/goroutine 风格）→ Web 框架 → 数据与部署
```

⚠️ **站数与每站知识点数必须由实测内容决定，本轮不定死** —— 五个源的粒度差异极大（runoob Python 基础 25 篇 vs walter201230 是文章堆）。

## 4. 与现有功能的关联性

### 4.1 ⚠️ 与 `growth-path` 的边界（本设计最容易踩的坑）

| 维度 | `growth-path` F0–F3 | 本设计 |
|---|---|---|
| 判什么 | 用户**会不会用这个产品**（跟随/实践/作者/定标） | 用户**掌握没掌握这个知识点** |
| 粒度 | 模块（`prompts×F0..F3` 向量） | 知识点（441 个节点） |
| 证据 | 产品内行为（建了包、导出了包、跑了流程） | **代码内容里出现了某概念的词面** |
| 状态 | 4 段有严格毕业信号 | 3 态无严格信号，**不可靠度更高** |

⇒ **决定：机制复用、状态不复用。** 复用 `GrowthPage` 的阶段呈现形制与「成长与统计」那组设计语言；**不复用 F0–F3 的向量结构**，也不用它的判据。**不合页**（owner 要的是侧栏新增）。

⚠️ **风险已登记**：两套「阶段」并存，用户会问「我到底是 F1 还是第 3 站」。⇒ 界面上必须**分开命名**（`growth-path` 叫「阶段」，本设计叫「进度」），且两者**不交叉引用、不互相推导**。

### 4.2 复用清单

| 现有物 | 复用方式 | 改动量 |
|---|---|---|
| `TERM_ROADMAP` 站列机制 | 语言路线**用同一套 stage 机制**换数据，不新建组件族 | 小 |
| P3 推荐基线 | 同一证据源（checklist/阶段名/skill）；**新增否定式推断** | 中 |
| `terms` 表 | **只读挂接**，零写入 | 零 |
| 台账 + `ai_recommend_call` | AI 调用留痕 | 零 |
| M8 回流通道 | AI 产出的唯一入口 | 零 |
| 侧栏 `NAV` | 加一项 | 极小 |
| FTS | 知识点标题/摘要入全文索引（仿 `fts_terms`） | 中 |

### 4.3 三处冲突（必须显式处置，不能装作没有）

1. **`level` 字段名撞车** —— `terms.level` 是难度 L1/L2/L3。本设计的「阶段」若也叫 `level`，跨模块读写时必然混淆。⇒ **语言侧一律叫 `stage_id`**。
2. **`status` 语义撞车** —— `terms.status` 是 `draft/active/...`（资产生命周期）。掌握度三态**不是**资产生命周期。⇒ **不塞进 `terms.status`，另立表**。
3. **知识点的授权问题** —— 新表是**资产**吗？若是，它就该进 pack 契约（能导出、能分享）；若不是，它就是本机私有状态。**⚠️ `growth-path` FR-1.5 明确「新字段一律不进 pack 契约」** —— 本设计须**继承这条边界**：知识点**不进 pack**。

## 5. AI native 如何集成（补短板）

### 5.1 分工：AI 补**内容**，不判**状态**

```
判定层（掌握度、下一步）  →  确定性、本地、可复算     ← §2.2 的纪律
内容层（讲解/练习/诊断）  →  AI，语义，不落判定       ← 本节
```

**AI 一旦进入判定层，§2.2 的整条理由就废了。**

### 5.2 四条 AI 能力（全部可关、失败必降级）

| # | 能力 | 形态 | 降级时 |
|---|---|---|---|
| **A1** | **就地问**：贴一段代码/一段报错 → AI 说「你缺的是这几个知识点」 | 发**脱敏后**的片段 + 已判定为「未触及」的候选知识点 | 只显示确定性层给出的「你本项目没用到这些」，**不显示「AI 认为你不会」** |
| **A2** | **按点生成练习**：选中知识点 → 生成一道贴合当前项目栈的题 | 结构化输出，**必须过 schema 校验** | 不生成，列出该知识点的外部出处 |
| **A3** | **把术语翻译成「在你这段代码里它指什么」** | `术语定义 + 代码片段` → 一句绑定 | 退回术语卡片的原定义 |
| **A4** | **按弱点出题**：取掌握度最低的 3 个点各出一题 | 结构化 | 退回「点开知识点看外部出处」 |

⚠️ **四条共同的纪律（照抄 M3 FR-6.3.3，不打折）**：
- **降级时界面不得出现任何 AI 字样** —— 用户看到「AI 推荐」就必须真是 AI 给的，否则信任一次崩掉就修不回来。
- **AI 结果不许绕过判定层** —— 「AI 说这个该学」而确定性层说「已掌握」，必须**显式标注分歧**，不许静默取一边。
- **一条 AI 调用一条台账事件**（`ai_recommend_call`，P5 已就位），**只存指纹与计数，不存原文**。
- **产出走 M8 回流 ＋ 人工确认**，不许直接写表。

### 5.3 AI 不该做的事（写死，防下轮越界）

- ❌ **不许 AI 判定掌握度**（§2.2）
- ❌ **不许 AI 自动改知识点 DAG 的前置边** —— 那会让「路线」随模型版本漂移，且不可复算。AI 可以**建议**，落库须人工
- ❌ **不许把 AI 生成的练习直接当考题判分** —— 判分标准不可复算
- ❌ **不接 LLM API**（owner 长期立场）：语义层走 Pi/AI Agent，产品不直连

### 5.4 依赖次序（硬约束）

⚠️ **P4（Pi 接入）尚未开工**，且它自己还压着三条未裁（Pi 接入方式／是否代管 API Key／M8-A 是否单开）。
⇒ **A1–A4 全部排在 P4 之后**。本设计的确定性层（§3.3）**不依赖 P4 任何一行** —— 这与 M3 的「P1→P3 完全不依赖 Pi」是同一条纪律：**AI 不可用时，路线与进度必须照常工作。**

## 6. 风险与待裁

### 6.1 风险表

| 风险 | 严重度 | 处置 |
|---|---|---|
| **掌握度不可靠** —— 只认得出「用过」，认不出「学过」；同义词漏检；冷门知识永远推不出 | 🔴 **最高** | §3.3 的三处诚实披露 ＋ 文案禁用「你已掌握」；**上线前必须有一次真人走查** |
| **`awesome-python-cn` 停更 4 年** | 🟠 高 | 标红停更日期；停更源不作真相源 |
| **内容漂移** —— 源的目录改版后，路由全部失效且**不报错** | 🟠 高 | 出处必带 `source_checked_at`；采集脚本差异可复算 |
| **版权** —— 若有人提议把教程正文搬进仓 | 🔴 高 | §3.2 FR-2 已写死；须配一条守卫（见 §7 判据） |
| **与 `growth-path` 两套「阶段」并存** | 🟡 中 | 命名分离、互不引用（§4.1） |
| **知识点的授权边界** | 🟡 中 | 已裁定：不进 pack 契约（§4.3 第 3 点） |

### 6.2 待裁（需 owner）

| # | 待裁 | 为什么需要 owner |
|---|---|---|
| 1 | **掌握度的「掌握」阈值 N 取多少** | 产品判断不是技术判断。取小则虚高、取大则永远停在「在用」 |
| 2 | **首个语言做哪门**（Python / Go / 两门同时） | 决定采集与判据的工作量；两门同时会让「跨语言共通知识点」的去重问题立刻变成硬骨头 |
| 3 | **界面上敢不敢显示「未触及」这种负面状态** | 这直接决定产品的诚实度与用户的心理接受度 —— 藏起来就退回 checklist 了 |
| 4 | **是否收录中文之外的内容源** | 影响采集脚本与版权判断 |
| 5 | **知识点是否允许用户自建** | 自建则 DAG 可被污染；不允许则只能改仓库 |

## 7. 验收判据（草案，全部须能红）

| ID | 判据 | 怎么证明它能红 |
|---|---|---|
| **DL-01** | 每条出处都带 `source_checked_at` | 删掉任一行的该列 ⇒ 红 |
| **DL-02** | **正文一个字都没进仓** | 全仓搜教程正文片段 ⇒ 0；且守卫自证：注入一条正文样本必被报出 |
| **DL-03** | 停更源必须显式标记 | 把 `awesome-python-cn` 的停更日期清空 ⇒ 红 |
| **DL-04** | `lang_topics` 前置边**无环** | 构造一条环（a→b→a）⇒ 必被检出 |
| **DL-05** | 掌握度**只认得出「用过」**，判定文案不得出现「你已掌握」 | 全仓搜该文案 ⇒ 0 |
| **DL-06** | 术语挂接**不反向写 `terms` 表** | 变异腿：让挂接动作写 `terms` ⇒ 红 |
| **DL-07** | 冷门知识点显示「本项目未涉及」而非空白 | 构造一个零证据的知识点 ⇒ 必须有文案 |
| **DL-08** | **AI 不可用时确定性层照常工作** | 注入必失败的 runner ⇒ 进度与路线仍出结果，且**界面无 AI 字样** |
| **DL-09** | **AI 结果不得绕过判定层** | 注入「AI 说已掌握、确定性层说未触及」⇒ 必须显式标注分歧 |
| **DL-10** | 知识点**不进 pack 契约** | pack manifest/selection 出现 lang 相关键 ⇒ 红 |
| **DL-11** | 新增页面**零字面色阶** | 复用 `design-tokens.test.ts` 四道闸，不另写 |
| **DL-12** | **库级条目不得进学习路线** | 变异腿：把 `kind='library'` 的条目塞进站列表 ⇒ 红（§1.4 实测 36% 库级，混进去就是 36% 的永久阻塞点） |
| **DL-13** | **清单必须带 `kind` 且可复算** | 删掉任一条目的 `kind` ⇒ 红；并附一条复算：按 §1.4 的分类规则跑一遍，库级占比必须仍是 36% ± 抽样误差 |

⚠️ **DL-02 与 DL-08 是本 spec 最要紧的两条**：前者是法律与工程纪律的交界，后者是「AI 降级是否诚实」的唯一可机判形式 —— 与 M3 的 AI-M3T-03 同源，**都必须先造负样本证明能红**。
