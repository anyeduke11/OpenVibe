## 1. 目的

本仓同时存在两层「上下文」，历史上两者各自演进、互不知情，导致同一事实被多次定义：

- **产品上下文**：标准包渲染出的文件，以及各平台真正读进模型的那一批内容。
- **研发上下文**：本仓协作所需的文档与登记。

本规范给出两者共用的四条纪律（定义、边界、生命周期、命名），并把可机判的部分交给 `pnpm context:check`。**本规范不新增产品行为**；凡涉及产物字节的调整一律走 A 级变更流程，不得以「治理」为名绕过。

## 2. 定义标准

一条信息要被称为「上下文」，须同时满足：

1. **会被读取**：存在明确的读取方（产品侧是某个平台或某个 adapter；研发侧是某一轮开工前必读）。没有读取方的文件不是上下文，是历史。
2. **有唯一出处**：同一事实只允许一处权威定义，其余位置只能引用。判据 J1（见复盘报告 §1）。
3. **可判定过期**：能说清「什么时候它就不对了」。说不清的，必须补上触发条件（见 §4）。

### 2.1 权威层级（产品侧）

| 层   | 位置                                   | 允许承载                             | 禁止承载                       |
| ---- | -------------------------------------- | ------------------------------------ | ------------------------------ |
| 契约 | `packages/shared/src/pack-contract.ts` | 类型、文件名常量、标记字面量、纯函数 | I/O、来自数据库的取值          |
| 编排 | `packages/core/src/**`                 | 组装、校验、状态机                   | `@openvibe/adapters` 的 import |
| 适配 | `packages/adapters/src/**`             | 各平台产物路径与 frontmatter 差异    | 业务规则                       |
| 执行 | `apps/server/**`、`apps/cli/**`        | I/O、展示、交互                      | 重新定义契约常量               |

### 2.2 权威层级（研发侧）

| 层     | 位置                                | 允许承载                 | 禁止承载                     |
| ------ | ----------------------------------- | ------------------------ | ---------------------------- |
| 约束层 | `CLAUDE.md`、`DESIGN.md`            | 每轮必读的硬约束         | 会漂移的计数（改为复算命令） |
| 计划层 | `docs/dev-plan.md`、`docs/tasks.md` | 排期、任务状态           | 规格正文                     |

## 3. 传递边界

| 约束                                                   | 作用                                       | 校验方式 |
| ------------------------------------------------------ | ------------------------------------------ | -------- |
| `packages/shared` 不 import `core`／`adapters`         | 契约不能反向依赖实现                       | C-3      |
| `packages/core` 不 import `@openvibe/adapters`         | 适配经 `AdapterBundle` 注入，否则无法替换  | C-3      |
| `packages/adapters` 不 import `@openvibe/core`         | 同上，双向禁止                             | C-3      |
| 注入的副作用只允许出现在 `apps/**`                     | 保证 dry-run 的「零写入」是结构保证        | 代码评审 |
| 契约常量只允许在 `shared` 定义，其他包只能引用         | 消除字面量重写                             | C-1、C-2 |
| 平台兼容矩阵的 `reads` 必须是某 adapter 的真实产物路径 | 防止展示面与实现脱节                       | C-4      |
| 需求编号（`CM-*`）与规格条目（`FR-*`）必须双向对得上   | 防止「需求清单、追溯表、规格」三处各说各话 | C-6      |

## 4. 生命周期

每条上下文都必须能回答四个问题。缺任一项即视为「未登记」，新规格不得合入。

| 阶段 | 要求                                                                      |
| ---- | ------------------------------------------------------------------------- |
| 创建 | 规格文件必须在头部写明上游与下游；无下游时写「无」并说明理由              |
| 复用 | 被第二次引用前，先确认它不是「已经开始漂移的抄写」——能引用原文就不复制    |
| 更新 | 事实变更时，改权威出处；引用方不复制，只跟随                              |
| 复审 | 计数类事实每轮触及即复算；不可复算的计数不允许出现在文档里                |
| 退役 | 产物被移除时，删除引用它的规格条目并在 `DEV_LOG` 留一笔；不得只留空壳文件 |

**A 级变更的边界**：任何会改变四根主文件字节、`files[]` 清单或指纹的调整，先由 owner 裁定并分配 D 编号，再 `schemaVersion + 1`、先改 golden 再改实现。**「统一实现」不是绕过该流程的理由**——本轮 `PLAYBOOKS.md` 清单补齐即按此登记为 A-1，未直接实施。

## 5. 命名规范

| 对象         | 规则                                                                         | 示例                                         |
| ------------ | ---------------------------------------------------------------------------- | -------------------------------------------- |
| 里程碑规格   | `m<N>-<slug>.md`，一个里程碑多份时用 `-` 区分主题，禁止同名两份              | `m6-standard-pack.md`、`m6-cli-injection.md` |
| 横切规范     | 直接以主题命名，不带 `m` 前缀                                                | `theme.md`、`output-validation.md`、本文件   |
| 报告         | `docs/<topic>-<YYYYMMDD>.md`                                                 | `docs/context-governance-review-20261103.md` |
| 方案         | `docs/<topic>-plan-<YYYYMMDD>.md`                                            | `docs/context-governance-plan-20261103.md`   |
| 版本批次规格 | `v<版本号>-<字母>-<主题>.md`，只用于该批次内部；批次结束后不再新增           | `v023-c-consolidation.md`                    |
| 常量         | 产品侧文件名一律 `PACK_FILE_*`／`PACK_CONTEXT_*`；契约层之外不得出现裸文件名 | `PACK_CONTEXT_AUX_FILES`                     |

补充约定：

- **不重命名历史文件**。改名的收益是整齐，代价是打断相对链接、历史登记与外部引用，不划算。命名规则自本规范生效日起对新文件生效。
- 计划类内容不进 `docs/specs/`。规格回答「做成什么样」，计划回答「什么时候做」，两者混放会让 spec 的版本行失去意义。**既存例外**：`docs/specs/m9-dev-plan-2026-10.md` 是计划而非规格（头部已写明「判据与人日以规格为准」），暂留原处以免打断既有链接与历史登记；新增计划一律放 `docs/`。

## 6. 跨模块共享约束

1. **一套词表一个概念**。若两个词表描述的问题不同（例如「要不要覆盖」与「与锁是否相符」），保持分离并在各自文件注明差异；只在语义确实重合时才合并。
2. **新增共享常量必须同时给出消费方**。无消费方的契约字段视为缺陷（登记在优化方案 A-2）。
3. **禁止在消费方复制清单**。清单只能由契约层给出，消费方按需过滤，且过滤条件必须写清「为什么排除」。

## 7. 校验机制

`pnpm context:check` 与 `pnpm docs:check` 并列，判据见优化方案 §2。**运行位置以 `.github/workflows/ci.yml` 为准**（`verify` 作业的 `Docs check` 之后紧跟 `Context check`，三平台矩阵各跑一次）。本规范自身受其约束：

- C-1 标记单一出处
- C-2 清单单一出处
- C-3 分层纪律
- C-4 兼容矩阵一致
- C-5 上下游闭合（**棘轮**：超上界判红；下降只提示下调，不自动改基线）
- C-6 需求 ↔ 规格追溯闭合（CM ↔ FR）

**文档闸**（`docs:check`）的判据总数保持 8 条以内，新增不得靠调松旧判据腾位；`context:check` 的 C-1～C-6 是另一套、另计，两者不共用配额。

### 7.1 C-6 的边界

- **追溯源文档只有一处**：`docs/context-management-requirements-20261103.md` 的 §4 需求清单与 §10 双向追溯表。别处不得再开第二张追溯表（判红）。
- **定位押在锚点，不押在节标题**：两处表各带一枚 HTML 注释锚点 —— 需求清单是 `<!-- c6:reqs -->`，追溯表是 `<!-- c6:trace -->`。节标题是**给人看的措辞**，随时会改；锚点是**给机器的标记**。⚠️ **改节标题不必动脚本；改锚点才需要**（那是刻意的行为变更，应同时改脚本与本文）。
- **两级指针口径**：普通 `FR-N` 按**家族号**命中（目标文件有同号标题或 `FR-N.M` 子标题即算——`docs-governance-check.md` 只有 `FR-11.2` 标题，指 `FR-11` 是正当形态）；条款指针 `FR-N.M` 必须**解析到具体条款**（精确标题／显式标签／父标题下第 M 条三者之一真实存在），指到空处判红。⚠️ 与文档闸 FR-11.2.1 的分工：那条管「否定断言的凭据指针」且跨文件子编号不判；追溯表的条款指针归本判据，必须判。
- **链接目标存在不归它管**：相对链接的目标是否存在由文档闸 FR-3.4 判；C-6 只断「被引用的**标识**在目标文件里是否真实存在」。
- **反向闭合**：规格标题里写了「（CM-*）」的条目，其 CM 必须在需求清单里，且追溯表那一行必须指回这个 FR 与这个文件。
- **归属列必须写得出锚点**：每行的「归属」至少要有一个 `FR-*` 或判据 `C-*`。⚠️ **只写散文**（「见某文件的某节」）的归属**机器验不了** ⇒ 那行等于没有追溯 ⇒ 需求与规格脱节时无人报警。散文可以补在锚点后面，但**不能只有散文**。
- **锚点粒度与需求范围一致**：需求只覆盖某个 FR 的**一部分条款**时，写条款指针 `FR-N.M`（「FR-N 的第 M 条」），不许笼统指整节。C-6 会解析到具体条款：显式标签 `- FR-N.M` 或父标题下的第 M 条**必须真实存在**，指到空处即判红。普通 `FR-N` 指整节（家族口径照旧）。⚠️ 同一 FR 被两条需求引用、而需求各要其中一条（如 m11 FR-3 的 CM-B2／CM-B5）时，**必须**用条款指针区分，否则两行语义相同、追的是什么看不出来。
- **条款指针必带名锚 `FR-N.M:关键词`**，判定是**首行等值**：关键词必须**等值等于**该条款**首行**的某个粗体短语（`**…**`）；首行没有粗体短语（裸编号行）时退化为「关键词出现在首行」。匹配目标是**首行**而非整个条款区域（区域含续行与嵌套内容，关键词只在续行里出现会假绿）。⚠️ **等值而非包含**：包含会让「共同子串」碰巧命中——认的是那条的标题短语本身。为什么必填：规格在 FR 节内**增删条目**后，序号会静默漂到另一条款，光数条目看不出来；缺名锚判红、等值失配判红（报错列出首行短语清单，照着改指针）。关键词字符到 `、`／`（` 即止，**允许空格**（短语可含空格，如「不改变任何既有 adapter 的默认行为」）。普通 `FR-N` 的名锚可选，给了就按标题行同样判。
- **指针失配的报错必带「受影响的行」反向清单**：同一指针被哪几行锚定，一次列全（CM 编号 ＋ 追溯表行号）。为什么：一处短语改动往往同时废掉多行，只报「哪一行坏了」会修一行红一行、直到修完才知道全貌；列全才能一遍改齐。
- **共锚自检（只报数，不判红）**：同一指针（文件 ＋ `FR 标识`）被多行锚定、而**名锚写得不一样**时列出（指针 ＋ 各行行号 ＋ 各自名锚）。⚠️ 判红面只在失配时报警，**全绿时**这种分叉无人看见——而「名字不同、指针相同」正是分叉的结构指纹。只报数是因为它可能是**正当多面**（同一条款的两个侧面各锚各的）也可能是**语义分叉**（表里看着像指了两个东西）——判定留给人。同指针同名锚的复用是正常态，不报。**分级**：行尾带「验收 ID 有交集：…」的**优先看**（两行共用同一验收结论却写两个名字＝更像分叉）；不带即各行验收 ID 互不重叠（更像正当多面）。**趋势落盘**：每轮运行把结论写 `test-results/context-check.json`（字段闭集：`at`／`errors`／`c5`／`c5UpperBound`／`c5OverBy`／`c5SuggestLowerBound`／`coAnchors`／`coAnchorItems`；写失败不改退出码），并**追加**一轮计数到 `test-results/context-check-history.json`（schema 1，保留最近 50 轮；**只存计数、不存 `coAnchorItems`** —— 明细含绝对行号会漂且体积随共锚数增长；每条带 `source`＝本机 `local` / CI `ci-<平台>`）。**跨机器合并**：`pnpm context:history:merge -- --from <artifact 解出的 history.json>` 把外部历史按 `at` 去重合并进本机（排序最旧→最新、上限 50 轮、坏项逐条丢弃）；**每次合并留一条 `merges` 记录**（`at` ＋ 来源文件名 `from` ＋ `accepted`／`dropped`／`added` 净增数，保留最近 50 条）—— 事后能查到「这几轮是从哪个文件合进来的」；`context:check` 追加轮次时**必须保留 `merges`**（否则下一次运行就清空清单）。CI 侧由 `Restore context history (cross-run)` 步下载上轮同名 artifact 做底再追加，于是 artifact 自身就是跨 run 累积的历史。趋势**只比 `coAnchors` 计数**，明细只作当轮排障。**CI 轮次归档**（`ci.yml` 的 `Context check` 之后两步，形态照抄 preflight 证据步）：job summary 显示该 JSON ＋ 按 run 上传 `context-check-<平台>` artifact（现含日报与历史两个文件），均 `if: always()`（**判红那轮最该存档**）＋ `continue-on-error`（归档是证据不是闸）；跨轮比对＝两次 run 的 artifact 各读 `coAnchors` 求差值。

### 7.2 C-5 棘轮与结论可见面（2026-11-05 落地，对应 `context-management.md` FR-4）

- **基线入仓**：`docs/context-check-baseline.json`，字段闭集 = `note`／`c5UpperBound`（上界）／`c5Items`（上界对应的条目快照）／`c5History`（上界变更留痕，末项 `value` 必须等于上界）。
- **判红三条（全部可证伪）**：① 基线缺失或不可解析（删掉基线等于拆掉棘轮）；② 基线自身不自洽（上界 ≠ 条目数，或上界 ≠ 留痕末项 `value` —— 上调/下调都必须追加一条含日期与理由的历史）；③ 本轮计数 > 上界（报差值并列出新增条目）。
- **只降不升**：本轮计数 < 上界 ⇒ **不判红**，只提示「上界可下调到 N」，并把该建议作为 `c5SuggestLowerBound` **随结论落盘**（终端那一行会淹在 CI 日志里，落盘后面板可直接展示）。闸**只报不写**：改基线是显式动作且必须留痕（与 `docs:check` §6.1 同精神）。
- **落盘字段扩展**：`test-results/context-check.json` 增 `c5UpperBound`（基线缺失时 null）、`c5OverBy`（超出条数）与 `c5SuggestLowerBound`（**数字 = 建议下调到的目标值；null = 无须下调；字段缺省 = 旧产物没写**）。趋势主指标仍是 `coAnchors`。
- **结论可见面**：`GET /api/context-governance`（只读端点，`reportRoute(..., 'filesystem', 理由)`）把上述几份文件合成为面板读数（含 `history`：最近 10 轮，面板画最近 5 轮；含 `merges`：最近 10 条合并清单）；设置页「上下文治理」区只读渲染，合并清单放在原生 `<details>` 折叠区（时间 / 来源文件 / 读入 / 净增 / 丢弃），并先给一块**按来源聚合**的概览（次数 / 累计净增 / 累计读入 / 累计丢弃 / 最近时间，**全量口径**、跨窗口，按累计净增降序），**聚合行可点选**：点击某来源 ⇒ 端点按 `mergesFrom`＋`mergesOffset` 返回**该来源的明细**（跨窗口分页：offset = 从最新往回跳过多少条，页大小 50；出参 `mergesTotal` = 文件内记录总数），逐条表只显示该来源并出现「取消筛选」入口，再点恢复全部；筛选态以 `mergeFrom` URL query 承载（刷新/切页不丢，取消即清除参数），翻页以 `mergesOffset` 承载。⚠️ **窗口边界必须如实标注**：端点只给最近 10 条窗口（`merges`），另给**全量按来源统计**（`mergesBySource`，跨窗口，含全量最近时间）⇒ 筛选提示同时写「全量 N 条，当前显示 M 条」，并在窗口外仍有记录时标注「另有 X 条更早的合并记录不在本窗口内」——不说清会被读成「该来源只合并过这么几次」。⚠️ **明细分页必须可操作**：筛选态下明细按页返回，还有更早记录时给「显示更早的 X 条」按钮（`mergesOmitted` = 更早还有多少条，服务端权威计算，不由前端从 `mergesBySource.count` 推断——该口径可能已被合并日志上限截掉而不全），offset > 0 时给「回到最近」；空页用 `mergesTotal` 区分「已到最早」（total > 0）与「该来源没有记录」（total = 0）。⚠️ **筛选态下不得消失**：即使端点按来源返回空（该来源已不在合并日志里），折叠区与「取消筛选」入口必须保留，否则用户被困在筛选态里出不来。⚠️ 没跑过 `context:check` 时端点返回 `available: false`，面板必须显示「先运行」而不是渲染成一串 0 —— 假的 0 会被读成「全绿」，比不显示更坏。

### 7.3 本地闸同源（2026-11-05 落地，对应 `context-management.md` FR-6 本地侧）

- **同一条入口**：`scripts/hooks/pre-commit` 的闸四直接调 `npx tsx scripts/context-check.ts`，与 CI 的 `Context check` 步**同一个脚本、同一套判据**；不另写一份、不裁剪判据。
- **失败即阻断**：非零退出 ⇒ `exit 1`，并原样打印脚本输出（**判据编号 C-x ＋ 文件位置 ＋ 新增条目**都在其中），另外指向 `docs/specs/context-governance.md` 与 `docs/context-check-baseline.json` 两个处置入口。
- **不得放宽**（规格 FR-6.3）：调用行不得挂 `|| true`，也不得改成「只提示不拦」；由 `tests/pre-commit-hook.test.ts` 的文本判据钉住（接线存在 / 不放宽 / 处置入口齐备）。
- **代价**：它扫全仓一致性（395 个源文件），无法像排版闸那样只查暂存文件；实测约 1 s。跳过某一次的入口仍是 `git commit --no-verify`（与其它三道闸同一后门）。
