## 第 0 章 · 一句话与三条目标

> **v0.2.4 不增加能力，只把已有能力的三条闭环补成「要么完整发生、要么完全没发生」：确认与副作用同界、路径校验以真实路径为准、未知状态不冒充通过。**

| 目标                    | 内容                                                                                                                 | 北极星（机器可判）                                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **G1 提交边界闭合**     | 回流裁决、导出落盘、注入写入、清理删除：校验、确认、副作用落在**同一次提交**里，失败可重试且不产生残留/重复          | 四组边界探针在修复后**全部不再复现**（断言反转）；注入临时触发器后重试，业务行恒为 1                        |
| **G2 路径与语义权威**   | 路径以 `realpath` 为准（含 symlink）；`enabled` 对所有 provider 选择分支生效；提取按项目绑定；UI 预览 = 实际待发内容 | symlink 两臂均返回 `out_of_project`；`enabled=false` 时 `createExtractRunner` 返回 `null`（默认/显式两路）  |
| **G3 证据诚实与分发闸** | 「未知」单独成态；测试不得把「提前返回」计为通过；发布验证与产品价值验证分开跟踪                                     | `probedOnline=false` 不再给出「完全一致」的默认解读；`pnpm test` 0 失败且无静默跳过；CI 出 tarball 安装冒烟 |

**次序不可换**：G1 是数据安全的前提；G2 是「同意」二字成立的前提；G3 是前两者能被持续验证的前提。G3 不前置为「先发布」，发布本身仍由 owner 决定（见第 8 章）。

## 第 2 章 · 第一性原理：这个产品的最小闭环是什么

### 2.1 一句话价值

> **把一个人踩过的坑，变成任何 AI 助手都读得懂、可核验、可回滚的标准，并且只在他确认后进入知识库。**

价值不在「存了多少条」，而在**从经验到 AI 行为的传递是否可信**：写得进去、读得准确、改得回来。

### 2.2 如果只保留三件事

| 保留 | 能力               | 最小实现                                      | 去掉它产品还剩什么                      |
| ---- | ------------------ | --------------------------------------------- | --------------------------------------- |
| ①    | **生成并注入标准** | `renderPack` + 确定性指纹 + 锁/备份/回滚      | 只剩一个本地笔记库                      |
| ②    | **核验偏离**       | `verify` / `diff`：磁盘、lock、包记录三方比对 | 无法回答「AI 现在读到的还是我认可的吗」 |
| ③    | **人工确认回流**   | `agent_ingests` → 人工裁决 → 业务表 + 台账    | 经验无法进入知识库，飞轮断开            |

其余能力（语言学习线 M9、AI 提取、问答、MCP、看板）都是**围绕这三件事的放大器**。放大器可以有缺陷，但①②③的闭环不能假。

### 2.3 由第一性原理导出的四条不变量

| 不变量 | 表述                                                         | 当前是否成立（证据）                                                                            |
| ------ | ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| **I1** | **一次确认 = 一次完整提交**：确认后的所有副作用同生共死      | **不成立**：P-A（先写盘后拒）、P-B（状态与业务行分离）                                          |
| **I2** | **信任边界以真实为准**：真实路径、真实启用状态、真实项目绑定 | **不成立**：P-D（symlink）、P-C（`enabled` 被忽略）、提取不传 `projectId`                       |
| **I3** | **未知必须显式**：不可达、未执行、未覆盖不得读作「通过」     | **部分不成立**：离线 verify 仍可为 `CONSISTENT`（既有测试 **有意**如此）、测试提前返回不算 skip |
| **I4** | **所见即所发**：确认界面展示的必须等于实际发出的内容         | **部分不成立**：提取预览截断 400 字、向导可从旧定义导出、失败无提示                             |

### 2.4 结构判断：不是「文件太大」，是「边界不在一次提交内」

四路审查（核心、服务端、CLI/交付、Web）各自从不同入口出发，收敛到同一句话：

> **校验、确认与副作用没有始终落在同一个提交边界；而「已确认」「已校验」「已一致」这些词，在实现里常常只是某一个局部检查通过。**

因此 v0.2.4 的重构对象不是目录结构，而是四个**深模块**（第 5 章）：提交边界、路径权威、证据状态、确认载荷。拆分文件不解决任何一个已复现缺陷。

### F1 · 回流状态机与业务写入不在同一提交

**E0 证据（`boundary-probes.json` → `B_ingest`）**

| 臂             | 第一裁决结果                         | 业务行 | 重试后           |
| -------------- | ------------------------------------ | ------ | ---------------- |
| `normal`       | published                            | 1      | 仍 1（幂等成立） |
| `reject_first` | rejected → published **成功**        | **0**  | 仍 0（永不出库） |
| `update_abort` | 业务行已插入，状态更新失败 ⇒ pending | **1**  | **2（重复）**    |

**机制（E1）**

- `packages/core/src/services/agentService.ts:436-450`：只有 `to==='published' && before.status==='pending'` 才分发；分发返回失败则把记录改为 `rejected`；否则直接调 `ingests.review`。
- `packages/core/src/repos/agentIngest.ts:165-185`：`review` 只拦 `conflict`，**任何其他状态迁移都允许**（含 `rejected → published`），且只更新状态行。
- 分发（插业务表）与状态更新之间**没有事务**。P-B 用临时触发器精确制造「业务行成功、状态更新失败」，重试即重复。
- `rejected → published` 跳过分发，于是状态说「已发布」，业务表说「没有」。

**为什么现有缓解不足**：幂等键保证「同键不重复入库」，但**重试路径**是同一 pending 记录再次分发——幂等键在业务层并没有阻止第二次插入（P-B 实测两行同载荷、entry_no 1/2）。测试只覆盖了正常臂（`reviewIngest` 的常规用例），没有覆盖中止臂。

**影响**：用户在面板看到「已发布」，资产库里却没有；或同一条日志出现两次编号不同的条目。属于**静默数据错误**。

**验收判据**

1. 状态迁移表生效：`rejected → published` 返回 409（需重新 ingest），`published` 为终态。
2. 发布路径在单个 SQLite 事务内完成「插业务行 + 更新状态」；注入中止触发器后，状态仍为 pending 且业务行为 0，重试后**恰好 1 行**。
3. 新增红→绿测试：先复现 P-B 两臂，再断言修复后不复现。

### F2 · 导出先写盘，后判不可变

**E0 证据（`A_export`）**

| 臂        | 目录导出结果               | writer 调用次数 | 导出记录       |
| --------- | -------------------------- | --------------- | -------------- |
| unchanged | `idempotent`               | 1               | 复用原记录     |
| changed   | **抛 `VERSION_IMMUTABLE`** | **1（已写）**   | 原记录指纹不变 |

**机制（E1）**：`packages/core/src/services/packService.ts:63-86` 的顺序是「单调版本检查 → `renderPack` → `writeDirectoryExport` → `packs.recordExport`」。`VERSION_IMMUTABLE` 由 `recordExport` 抛出，此时目录已写入**当前渲染内容**，与已存记录的指纹不一致。

**真实 writer 的边界（E1）**：`apps/server/src/lib/pack-export.ts:21-40` 在写之前会先拒绝「同名文件内容漂移」，因此在**目录里已存在同版本旧内容**时会更早失败（报错文案要求用户先移除或备份）。但目录为空、或旧文件与本次文件名不冲突时，写盘仍先于 `recordExport` 的不可变判定——P-A 用内存 writer 复现的正是这个窗口，不是「任何情况下都会写」。

**为什么现有缓解不足**：`packages/core/src/services/packService.test.ts:150` 只覆盖「版本更旧 ⇒ 拒绝且不写」，该路径在写入前就返回；**同版本不同指纹**这一臂没有用例（P-A 首次覆盖）。「有哈希、有不可变记录」证明的是数据库里的记录不可变，不是磁盘上的文件没被换掉。

**影响**：用户在导出历史里看到的是旧指纹，磁盘目录里却是新内容；下游 `verify` 以 lock 比对时会报磁盘漂移，但根因在导出侧。反复重试会反复覆盖。

**验收判据**

1. 导出前置校验：读已有记录，若同版本且指纹不同，**在 render/write 之前**抛 `VERSION_IMMUTABLE`；`recordExport` 的检查保留为兜底。
2. writer spy 在拒绝臂调用次数为 **0**；原记录、原指纹、原 `bundleJson` 均不变。
3. 保留并新增测试：单调拒绝（既有）＋ 同版本异指纹（新）。

### F3 · 待确认回流在 UI 上没有「发布」入口

**E1 证据**

- `apps/web/src/components/agent/PendingIngestList.tsx:128-130`：只有 `isConflict` 时渲染 `ConflictActions`；pending 行没有按钮。
- `ConflictActions` 的两个动作都发送 `to: 'rejected'`（`PendingIngestList.tsx:166-186`）：保留先到者 / 接受本条并改幂等键重试。
- 全仓检索：`to: 'published'` 只出现在类型声明与 hook 入参（`apps/web/src/hooks/useAgentIngests.ts:86`），**没有任何 UI 调用点**；CLI 也没有 review 子命令。

### F4 · 词法路径校验不等于真实边界

**E0 证据（`D_path`）**：普通文件、文件 symlink、目录 symlink 三臂中，后两臂的 `real_target_outside=true`，而 `readSnippet` 均返回项目根外的合成内容；词法 `../sibling/sample.txt` 三臂都被拒（`out_of_project`）。

**机制（E1）**：`packages/core/src/source-ai/snippet.ts:119-142` 先做词法与 `resolve` 校验，随后 `statSync` / `readFileSync` **跟随 symlink**。同类风险适用于 `.openvibe` 目录与备份根：`packages/core/src/inject/sync-lock.ts:183-186` 直接 `mkdirSync(dirname)` + `writeFileSync`，未校验父目录是否为 symlink；`apps/cli/src/commands/sync.ts:393-410` 的备份写入同样只做词法 `resolveWriteTarget`。

**为什么现有缓解不足**：词法守卫挡住了最容易想到的 `../`，测试也只测了它。symlink 是**真实文件系统**里的路径，不是字符串问题。

**影响**：在用户项目里放一个指向外部的 symlink，提取读取可越界；锁/备份写入可落到项目外。属于**边界穿透**（需要本地可控文件系统，非远程攻击）。

**验收判据**

1. 统一入口 `resolveInside(root, rel)`：词法校验 + `realpath(root)`/`realpath(target)` 包含性校验；不存在的目标校验最近存在祖先。
2. 写路径对末级组件使用 `lstat` + `O_NOFOLLOW`；`.openvibe`/备份根为 symlink 时拒绝并给出明确错误码。
3. 三臂测试（普通/文件 symlink/目录 symlink）全部 `out_of_project`，并保留词法 `../` 用例。

### F10 · 单用户本机信任模型（假设，不是缺陷）

`apps/server/src/plugins/auth.ts:20-47`：Host 必须回环；带 Origin 的浏览器请求必须 localhost 白名单；无 Origin 的程序请求必须 Bearer token（或 `Sec-Fetch-Site: same-origin/none`）。因此：

- 任何**持有本地 token** 的进程（CLI、脚本、其他本机应用）都可翻转 AI 总闸、裁决回流；

### F11 · 幂等身份不含项目与类型

**E1 证据**

- `packages/core/src/db/migrations/0021_ai_extract.sql:19`：`idempotency_key TEXT NOT NULL UNIQUE`——全局唯一，不含 `project_id`、`kind`。
- `packages/core/src/repos/agentIngest.ts:110-135`：先按 `idempotency_key` 全局查重；命中且载荷相同时返回 `duplicate` 与**先到者的 id**；载荷不同时把**先到者**标成 `conflict`。

**机制**：键是 agent 自选的。若两个项目用同一个键（例如都写 `requirement-1`），会出现两种结果：

| 第二项目的载荷 | 实际结果                               | 第二项目的数据 |
| -------------- | -------------------------------------- | -------------- |
| 与先到者相同   | 返回 `duplicate`，指向第一个项目的记录 | **静默丢失**   |
| 与先到者不同   | 第一个项目的记录被标 `conflict`        | **未入库**     |

**为什么现有缓解不足**：`UNIQUE` 保证「同键只有一行」，但没人保证「键在一个项目内唯一」；冲突面板又会把**先到者**（另一个项目的记录）标成异常，用户看到的是错的那一行。

**影响**：跨项目误判重复或误标冲突；第二种情况下两个项目各丢一半。属于**静默数据归属错误**，不产生报错。

**验收判据**（条件批次，见 R7 / D-c）

1. 唯一性改为 `(project_id, kind, idempotency_key)`；两项目同键各自入库，同项目同键仍判冲突。
2. 迁移在真库副本上演练：行数、内容指纹、`created_at` 不变；旧全局索引被替换而非并存。
3. 新增用例覆盖上表两行：第二项目同键同载荷 ⇒ 新记录（不是 `duplicate`）；异载荷 ⇒ 第二项目 `conflict`，先到者不变。

### F12 · 目录导出没有版本清单，跨版本靠人工清空

**E1 证据（代码）**

- `apps/server/src/lib/pack-export.ts:21-40`：写之前先比对同名文件哈希，内容不同即抛 `VERSION_IMMUTABLE`，文案要求「请先移除或备份」；随后 `mkdirSync` + `writeFileSync`。
- 全目录检索：导出路径没有清单文件、没有旧文件回收逻辑（`pack-export.ts`、`packService.ts` 内无 `unlink`/`rm`）。

**E2 边界（行为未执行）**：本会话没有真的对同一目录连续导出两个版本，因此「旧版独有文件会残留多少」属未验证假设，不当作已实测缺陷。

**机制**：目录通道以「一个目录装一个版本」为隐含约定，但目录里没有机器可读的清单说明哪些文件属于当前导出。于是：

- 同名内容变了 ⇒ writer 抛错，用户必须手工清空或换目录；
- 旧版独有、新版没有的文件 ⇒ 不会被识别，也不会被清理；
- `verify` 只认 `pack.lock` 的受管清单，无法判断目录里多出来的文件属于哪个版本。

**为什么现有缓解不足**：哈希漂移检查保护的是**单个文件不被覆盖**，不是**目录组成与版本一致**；错误文案把一致性责任交给用户手工操作。

**影响**：导出目录可能混合两个版本的文件；用户要么被拦下手工清理，要么得到一份「看起来成功但含旧文件」的目录。属**运维一致性**问题，不直接污染数据库。

**验收判据**（条件批次，见 R8 / D-h）

1. 导出时在目录写清单（版本、指纹、文件与各自 sha）；下一次导出若清单版本不同，默认拒绝并列出差异文件。
2. 仅当显式 `--replace`（或等价确认）时清理「旧清单内、且不在新清单」的文件；**清单之外的用户文件一个都不删**。
3. 用例：v1→v2 无确认 ⇒ 拒绝且目录零改动；有确认 ⇒ 目录内容与清单逐字一致；未列入清单的文件保留。

### 5.2 四个深模块（设计约束，不是文件清单）

**① `CommitBoundary`（提议：`packages/core/src/kernel/commit.ts`）**

```ts
// 语义草案，不是实现
type Transition = { from: Status[]; to: Status; effect?: (tx) => void }
// 所有状态迁移必须查表；effect 与状态更新在同一 SQLite 事务内
commitTransition(db, { table: 'agent_ingests', id, to, reason, effect })
```

约束：

- 业务写入（`dev_log_entries` / `requirements` / 草稿表）与状态更新同事务；
- 事务外只允许**可重试**的副作用（如导出写盘），且必须先完成不可变前置校验；
- 任何 effect 失败 ⇒ 整体回滚，状态不变，错误可重试。

**② `PathAuthority`（提议：`packages/core/src/fs/path-authority.ts`）**

```ts
resolveInside(root, rel) // 词法 + realpath 双重校验，返回真实绝对路径
openInside(root, rel, flags) // 对末级组件 O_NOFOLLOW；父链逐级校验
assertDirInside(root, rel) // .openvibe / 备份根专用
```

约束：`snippet`、`sync-lock`、`backup`、`clean`、`verify` 的读/写/删全部经此入口；错误码保持既有 `out_of_project` / `PATH_ESCAPE` 语义，避免破坏 CLI 输出。

**③ `EvidenceVerdict`（提议：扩 `packages/core/src/inject/verify.ts`）**

```ts
type VerifyState = 'CONSISTENT' | 'PARTIAL' | 'ORPHAN' | 'DISK_DRIFT' | 'STALE_LOCK' | 'UNVERIFIED'
// UNVERIFIED：本地三项干净，但服务端最新版本未核（probedOnline=false）
```

约束：`UNVERIFIED` 不得被折叠为 `CONSISTENT`；CLI 退出码与 Web 徽章同步；旧 JSON 消费方按新增枚举处理（向后兼容策略见第 12 章）。

**④ `ConfirmPayload`（提议：shared 类型 + Web 组件）**

```ts
type ConfirmPayload<T> = { payload: T; sha256: string; truncated: false }
// 确认屏与请求体从同一对象渲染；截断则 truncated=true 且必须显式提示
```

约束：发布、提取、导出三个确认面共用；禁止在确认组件内二次拼装文案/载荷。

### 5.3 `agent_ingests` 状态机（提议）

| from      | to        | 触发                | 副作用                             | 允许                    |
| --------- | --------- | ------------------- | ---------------------------------- | ----------------------- |
| pending   | published | 人工确认            | 分发业务行（同事务）；失败整体回滚 | 是                      |
| pending   | rejected  | 人工否决            | 无                                 | 是                      |
| pending   | conflict  | 同键异载荷          | 无（等待二次裁决）                 | 是                      |
| conflict  | rejected  | 保留先到 / 改键重报 | 无                                 | 是                      |
| rejected  | published | —                   | —                                  | **否**（需重新 ingest） |
| conflict  | published | —                   | —                                  | **否**                  |
| published | 任意      | —                   | —                                  | **否**                  |

### 5.4 导出提交序（提议）

```
preflight: 读已有记录 → 同版本且指纹不同 ⇒ 立即 VERSION_IMMUTABLE（不渲染、不写盘）
render    → 计算指纹
write     → 目录通道写盘（可重试，内容由指纹确定）
record    → 写导出记录（保留既有唯一约束作兜底）
```

**残余窗口的诚实说明**：若 `record` 因数据库错误失败，磁盘已写入与记录同指纹的内容；重试会再次写同内容并补记录，不产生不一致。**不宣称文件系统与数据库的跨介质原子性**——那是分布式事务，超出本版本。

## 第 14 章 · 计划外增强需求（X1–X4）与准入规则

> 本章承接本次审查收尾时提出的四项增强。它们不是审查中已复现的缺陷，而是「修完闭环后仍会留下」的结构性缺口。每项给出为什么、怎么做、怎么验收；对应的发现编号与批次见括号。**新增候选的准入见 14.2；不满足者进 14.3 观察池，不得以增强名义登记。**

### X1 · 幂等身份含项目与类型（F11 / R7 / D-c）

- **为什么要考虑**：键由 agent 自选，跨项目同键并非异常用法。现状下同键同载荷会把第二个项目判成 `duplicate`（第二项目**静默丢失**），同键异载荷会把**先到者**标成冲突（标错了行）。这类错误不报错、不崩溃，只让数据悄悄归错项目。
- **如何实现**：先跑 U7 在临时库复现两臂；确认后新增迁移，把全局 `UNIQUE(idempotency_key)` 换成 `(project_id, kind, idempotency_key)`；保留旧索引导出的重建脚本以便回滚；真库副本演练行数与内容指纹。不改列语义、不改 HTTP 契约。**项目内同键同类型仍判重复是幂等语义本身**，不引入键命名空间或运行时校验；只在 agent 协议文档补一句「键应在项目内稳定且唯一」。
- **验收标准**：两项目同键各自入库；同项目同键仍判 `conflict`；同一项目同键同载荷仍 `duplicate`；真库副本演练前后行数、内容指纹、`created_at` 一致；回滚脚本能把索引还原；协议文档补上键约定，且不新增校验分支。

### X2 · 目录导出清单与显式替换（F12 / R8 / D-h）

- **为什么要考虑**：目录通道隐含「一个目录一个版本」，但目录里没有清单。换版本时，同名内容变了会被 writer 拦下并要求手工清理；旧版独有文件则无人识别。用户要么被反复拦，要么得到一份混合目录。
- **如何实现**：导出成功后在目录写清单（版本、指纹、文件与 sha）；下次导出若清单版本不同，默认拒绝并列出差异；仅当显式 `--replace` 时删除「旧清单内、且不在新清单」的文件。**清单之外的文件永不删除**。不做自动清理，不新增后台任务。
- **验收标准**：v1→v2 无确认 ⇒ 非 0 退出且目录零改动；有确认 ⇒ 目录内容与清单逐字一致；清单外的用户文件哈希不变；清单缺失（历史目录）时按「未知目录」处理，只报不删。
- **平台前提**：跟随 D-e，只验收 Linux + macOS；若 D-e 后续把 Windows 纳入 R6 范围，R8 需补大小写不敏感文件系统与 CRLF 下的同名判定用例，未补前不宣称 Windows 可用。

### X3 · 测试早退不计为通过（F13 / R0 / D-i）

- **为什么要考虑**：`reportedPassed=2438` 里混有「没跑」的用例。环境缺失（如无 Go）被读成覆盖率，CI 绿灯因此不可信；这与本文 G3「未知必须显式」直接冲突。
- **如何实现**：所有环境门控改 `it.skipIf` / `ctx.skip()`；新增元测试静态扫描两类形态：`it(`/`test(` 函数体内的裸 `if (!…) return`，以及包住 `it(`/`describe(` 的外层条件分支；`pnpm test` 输出 passed/failed/skipped/todo 数；`baseline.json` 口径改为「执行并通过」。
- **验收标准**：
  1. 人为早退的用例在报告中显示 skipped；
  2. 元测试对上述两类静态形态各有一个故意样例，且必须报红；
  3. `it.todo` 不得计入 passed，必须单列或计入 skipped；
  4. 全量输出四数齐全；无新增失败。
- **已知不可静态检出**：helper/fixture 内部提前返回、运行时短路造成的「未执行但无标记」——这两类不纳入元测试承诺，改由「测试必须显式 skip」的 review 约定约束，并登记在 §14.3 观察池 O2。

### X4 · 共用 provider 配置的同源提示（F14 / R5）

- **为什么要考虑**：提取与问答读同一份 provider 配置，但界面分成两个功能区。用户改一处会同时改变另一处的出网凭据/端点，出错时难以定位。
- **如何实现**：两区各加一句同源提示（i18n 文案，复用现有 aside 样式）；删除/改键的确认弹窗点名受影响的功能。不改配置存储结构，不新增设置项。
- **验收标准**：两区提示同时存在（组件测试）；删除/改键确认弹窗包含两个功能名；不影响既有设计 token 闸与可读性闸。

## 附录 C · 术语

| 术语                        | 含义                                                         |
| --------------------------- | ------------------------------------------------------------ |
| 提交边界（commit boundary） | 一次用户确认所对应的全部副作用，要么全部生效，要么全部不生效 |
| 真实路径（real path）       | `realpath` 解析 symlink 后的路径，而非字符串拼出的路径       |
| 未核验（UNVERIFIED）        | 本地检查通过但依赖的远端检查未执行/不可达，不能读作「一致」  |
| 确认载荷（confirm payload） | 确认界面展示、并原样进入请求体的对象；展示与发送同源         |
| 推理边界（inference limit） | 一次实验能证明什么、不能证明什么的明确声明                   |
| 红→绿                       | 先写能复现缺陷的失败用例，再修实现使其通过                   |
