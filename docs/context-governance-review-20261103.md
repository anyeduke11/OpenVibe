## 1. 方法与判据

盘点不靠通读，靠四条可证伪的判据。每条都给出「怎么判」与「判红的证据形态」：

| #   | 判据     | 问的问题                                             | 判红证据                       |
| --- | -------- | ---------------------------------------------------- | ------------------------------ |
| J1  | 单一出处 | 同一事实（文件名、标记、阈值、计数）是否只写一处？   | 两处字面量各自可改、会漂移     |
| J2  | 边界清晰 | 跨包依赖是否单向？谁可以 import 谁？                 | 出现反向 import 或循环         |
| J3  | 生命周期 | 每条上下文是否写明何时创建、何时更新、谁负责、何时废 | 规格里查不到更新/退役规则      |
| J4  | 可机验   | 该约定错了会不会有人发现？                           | 只有人读，闸不覆盖；或闸只报数 |

J4 是本轮的关键：本仓已有 8 条文档判据（见 `scripts/docs-check.ts` 头注），但**「约定写在哪」这件事本身没有被任何判据覆盖**。

盘点手段：两条只读探索线（产品链路、研发文档）产出 file:line 级证据，随后**逐条回读原始文件复核**。复核推翻了 3 条初判（见 §4.3），这是必要的——不复核就等于把子代理的措辞当成事实。

## 4. 根因分析

### 4.1 五类根因

| 根因         | 机理                                                       | 命中问题         |
| ------------ | ---------------------------------------------------------- | ---------------- |
| 清单抄两份   | 「哪些文件算上下文」是业务事实，却分别写在消费方而非契约层 | P-01             |
| 字面量重写   | 同一条标记协议在两个包内各写一份，靠人眼保持一致           | P-02             |
| 数字写死     | 把「会随迭代变化的计数」写进散文，漂移无人发现             | D-01、D-02、D-03 |
| 登记单向     | 下游声明了上游，上游不声明下游，改一处不会想起另一处       | D-04、D-06       |
| 生命周期缺位 | 只规定「写什么」，不规定「谁维护、何时退役」               | D-08             |

### 4.2 为什么「建闸」比「逐条修」更重要

存量条目修一次就过期（D-02 的「八份」当年是对的）。本仓已用同一手法处理过文档治理（`docs:check`），本轮沿用：**能机判的写成判据，不能机判的写成规范条文**。

### 4.3 复核推翻的三条初判（不修，避免制造新债）

| 初判                                          | 复核结论                                                                                                                                                                                       |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/cli` 声明了 `@openvibe/server` 但未使用 | **误报**：`serve.ts:7` 真实引入 `bootstrap`，`openvibe serve` 依赖它。移除会直接打断命令                                                                                                       |
| `{path,content,sha256}` 三元组重复定义        | **误报**：core 的 `PackFileWithHash` 是**输入**契约，shared 的 `PlannedFileOut` 是**输出** schema。键相同是因为描述同一份数据，但边界不同，合并会把输入耦合到输出结构                          |
| 同一文件四套状态词表应当合并                  | **待评估**：四者描述的是不同问题——注入决策（要不要覆盖）、一致性（与锁是否相符）、核验结论（文件是否还在）、退役（是否该删）。概念不同则词表不同，强行合并会丢失区分度。本轮不合并，登记待评估 |

## 5. 结论

1. 产品链路的**结构**是健康的：单向依赖、无环、契约集中在 shared。问题集中在「同一事实写两处」与「规格与实现不同步」。
2. 研发上下文的**层级**是健康的，问题是「易漂移的数字被写死」与「上下游登记不闭合」。
3. 可以立即整改的（不改产物字节）共 **7 项**（L-1～L-7），本轮**已全部落地**；必须走 A 级变更流程的 **1 项**（P-01／A-1），**待签收，未实施**；原列为 A-2 的 P-05 经复核**撤回**（字段受 FR-6.3 约束且有单测消费），改按产品决策处理（R-4）；需 owner 裁定或产品决策的共 **3 项**（P-04／R-1、P-06／R-2、P-05／R-4）；登记待评估 **1 项**（P-07／R-3）。另有 1 项（D-05）因 owner 既有裁定「原样保留」**按规则不动**，见 §3 表。
4. 新增一道 `context:check` 判据闸，把「单一出处」「分层纪律」「兼容矩阵一致性」「规格上下游闭合」变成能红能绿的检查——否则本轮修完，下一轮还会漂。
