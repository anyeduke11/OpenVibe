## 0 怎么用

- **四组 21 条**，逐条回答「是 / 否 / 不适用」。
- 回答「否」的条目，**必须给出去向**（既有验收项 / 决策台账 / 观察池），不得留空。
- 本清单**不是新增强**，而是把 PRD v0.2.4 §14.2 的四条准入测试**前移到规划阶段** —— 收尾时才想到的，应该在定稿前就想到。
- 与收尾格式的关系见 §3。

## D 组 · 可验证性（4 条）

| #   | 检查项                                                                    | 为什么                                           | 不通过时的去向     |
| --- | ------------------------------------------------------------------------- | ------------------------------------------------ | ------------------ |
| D1  | 每条验收标准是否**可测**（有具名用例 ID，而非「体验良好」这类主观表述）？ | 不可测的验收等于没有验收                         | 并入本批次验收标准 |
| D2  | 判据是否**不依赖实现细节**（不依赖行号 / 排版 / 内部函数名）？            | 依赖实现细节的判据会随重构大面积失效             | 并入本批次验收标准 |
| D3  | 证据是否**可复算**（给出命令与预期输出，而非「已验证」）？                | 不可复算的证据无法在下一轮被信任                 | 并入本批次验收标准 |
| D4  | 是否有**反向验证**（变异 / 证伪：故意改坏实现，确认判据会红）？           | 永不失败的断言比没有断言更危险（本仓已出现多次） | 并入本批次验收标准 |

## 1 与收尾格式的衔接

本清单的产物，按 **PRD v0.2.4 §14.2** 的四条准入测试分配落点：

| 准入测试 | 问题                                      | 不通过时的去向             |
| -------- | ----------------------------------------- | -------------------------- |
| **来源** | 是否落在某条已声明不变量 × 某个既有表面？ | 新想法 → 非目标 / 观察池   |
| **证据** | 是否有可复现证据？                        | 纯推测 → 观察池            |
| **去重** | 是否已是某批次的验收项？                  | 并入该批次验收，不另立条目 |
| **范围** | 是否服务核心价值？                        | 否 → 非目标                |

**落点只有三处**：既有批次的验收标准 / 决策台账 / 观察池。

### 建议的收尾格式调整

CLAUDE.md 现行三段格式中，第三段标题为「未考虑且需要增强的需求」，且规定「计划外的改进想法不得默默省略，必须进第三段」。**这条规定的初衷是防止遗漏，但客观效果是强制每轮产出一批新待办。**

建议改为：

```
3. **计划外候选与准入判定** —— 本轮收尾发现的候选，逐条给出：
   - 准入判定（通过 / 并入既有验收 / 进观察池 / 不成立）
   - 落点（既有验收项 / 决策台账 / 观察池）
   - 未通过哪条测试（若未通过）
   允许「本轮无候选」—— 不产生候选不等于遗漏。
```

## 3 已知边界

- 本清单**不能穷举**所有场景 —— 闸与工具在「被使用时」才暴露的缺口属客观规律，不应被规则压制（见复盘报告 §4.4）。
- 清单条目本身**会随实践增补**；每次增补需在本文档加版本行并记 DEV_LOG。
- **未验证**：本清单尚未在真实批次上跑过一遍；首个使用批次应回写「哪些条目无用 / 哪些缺失」。

## 4 循环管理与终止（2026-11-13 新增）

本清单解决「规划端」的完整性，但**收尾端**会自造任务：第三段候选 ⇒ 下轮任务 ⇒ 下轮第三段候选。2026-11-13 实测 16 轮（DEV-0249…DEV-0264）全部如此，零产品代码改动。终止机制的单源是 `CLAUDE.md`「任务循环管理」（P1–P5），本节只登记它与四组 21 条的关系：

| 机制        | 与本清单的关系                                                                                               |
| ----------- | ------------------------------------------------------------------------------------------------------------ |
| P1 批次化   | 同源候选合并执行，**不合并验收标准** —— D 组（可验证性）仍逐条判，每条候选单独给具名用例 ID                  |
| P2 终止条件 | DoD 四项与本清单 **D 组**同源：`docs:check` error 0 即 D3「证据可复算」的制度化；观察池清零即 B6 的落点清空  |
| P3 对象切换 | 连续 3 轮无产品改动 ⇒ 切到 PRD 能力；切换后的**规划输入**正是本清单的 A 组（场景）与 B 组（非功能）          |
| P4 候选合并 | 合并的是**执行批次**；本清单「落点只有三处」的约束不变，每条候选仍须独立归入既有验收 / 决策台账 / 观察池之一 |
| P5 预算上限 | 文档面每 4 轮最多 1 轮；超出部分进观察池（本清单 B6 的落点），**不计欠账**                                   |

**批判性补充**（每条候选必答）：这条候选会不会**制造**未来的不一致？若是「修一处暴露一处」链条上的一环，它不是终点 —— 要么一次修完同类，要么承认它是持续成本（进观察池）。

**第一性原理补充**（每条候选必答）：如果这条**不做**，用户会损失什么？答不出具体损失 ⇒ 属「文档自洽」而非「核心价值」，进观察池，不占执行批次。
