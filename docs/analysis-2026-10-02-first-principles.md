## 第 0 章 · 结论摘要与阅读方式

### 0.1 一句话诊断

> **OpenVibe 的工程质量与写盘安全性已达专业水准，但它的价值逻辑被设计成「资产管理器」，而它实际在做的事是「把人类意图编译成 AI 可用的项目上下文」——这两者需要的架构、指标与界面完全不同。**

现有系统的形状来自 MVP 时期的四个合理简化：整文件管理、单包托管、五类资产同构 CRUD、一个界面服务所有水平的人。这四个简化在「把飞轮转起来」的阶段是正确取舍；但当飞轮已经转起来（种子 109 术语 / 21 提示词 / 7 流程模板、73 个 API、531 条测试、三平台 CI 全绿）之后，它们变成了**四堵墙**——每一堵都挡在「从新手到专家」这条路上。

### 0.3 本文的分析方法（可被审阅、可被否证）

**第一性原理在这里的操作定义**：不是「从零重想一个产品」，而是——**把每一个既有设计决策拆到它成立所需的最小前提，然后逐条检验那些前提今天是否还成立**。前提仍成立 ⇒ 不动（哪怕它看起来笨）。前提已变 ⇒ 该设计从「合理简化」变成「历史包袱」，进建议清单。

为此本文对每条结论强制附三件：**(1) 可复算的证据**；**(2) 它依赖的前提**；**(3) 前提失效的判据**。第 10 章专门写「本文可能错在哪里」，列出会让我的建议**反过来有害**的 8 种情形——这份方案的价值不在我说对了什么，而在它写清了自己在什么条件下应当被推翻。

**「健壮」在本项目语境下的五个可测量维度**（后文所有建议都归到这五维之一）：

| 维度 | 定义（本项目语境） | 现状量具 |
|---|---|---|
| R1 写入健壮 | 任何时刻中断/并发/异常，用户磁盘与 lock 台账都不会进入无法自证的中间态 | 三道防线 + `sync.lock` + `atomic-write`；**缺**：崩溃后三方一致性核验 |
| R2 契约健壮 | 契约字符串与实现之间不会静默漂移 | `design §7/§8` 冻结 + golden + zod；**缺**：出参侧运行时校验 |
| R3 演化健壮 | 数据/契约能升级，且用户盘上的既有产物有确定的迁移路径 | `schema_migrations` 5 个迁移，**无 checksum、无 down**；无用户盘迁移概念 |
| R4 验证健壮 | 「我们说它能工作」与「机器能证明它能工作」的差值可量化且单调缩小 | 521 用例 / 三平台 CI；**缺**：Web 关键路径、D15 左半、看板拖拽 |
| R5 治理健壮 | 文档/队列/版本链的一致性由机器保证，而非由人肉记忆 | `decisions.md` + §13-8 同族限定；**缺**：机器校验，已两次计数错报 |

### 0.4 本文的边界（先说清不做什么，避免被读成一份新 PRD）

- **不重写技术栈**。Node 22 + Fastify + better-sqlite3 + React + zod 这组选型在 9 包规模下是恰当的；本文只动**依赖的边界与形状**，不动技术选型。
- **不推翻 5 类资产的划分**。J2 要求的是给它们**不同的生命周期**，不是合并或重划。
- **不进 A 级契约面**（除 J5 那一条，且它必须由 owner 裁定后才动）。`design §7/§8` 的冻结继续有效。
- **不新增网络面**。所有新信号都是本机数据；遥测白名单三事件、默认关、关闭即零外联**一字不改**。
- **不与既有治理流程冲突**。本文不修改 `decisions.md` / `DEV_LOG.md`，不占用队列编号；它是一份**待裁定的输入**（§12 给出接法）。

### 1.3 现状的形状问题（七个结构性观察，不含数字）

1. **没有服务层**。业务规则住在三个地方：server 的 route 文件里（`packs.ts` 的导出通道分支、`settings.ts` 的种子摘要成形）、CLI 的 `index.ts` 里（519 行 = 入口 + 全部命令编排 + 6 组渲染函数）、web 的 hook 里。同一个规则存在两份实现：包渲染在 `server/lib/pack-assemble.ts`，而 CLI 侧 `pack-source.ts verifyPack` 自己重算一遍校验。
2. **常量有多个真源**。`SYNC_STATES`（`cli/output.ts`）与 `INJECT_STATUSES`（`core/inject/planner.ts`）是同一样东西的两份声明，且推导出一个「`clean` 的汇总键不能叫 `counts`」的隐式契约（`cli/index.ts:405` 把它写成了注释里的约定）。
3. **`shared` 是一个扁平杂物袋**。13 个 `export *` 把 zod schema、数据表（`TERM_ROADMAP`）、字符串构造器（`interviewPrompt`）、错误码、id 前缀混在同一出口；135 处引用全部拿到整个面。`sideEffects:false` 因此救不了 tree-shaking——`constants.ts:47` 的注释已经手工把 `TERM_ROADMAP` 搬出去过一次，这正是同一问题的**人工补丁**。
4. **全局性质的迁移机制**。`runner.ts` 对**每一个**迁移都关掉外键（为了 `0004` 的表重建），于是「需要外键约束的迁移」无法声明自己的需求；`schema_migrations` 只存 `(version, applied_at)`，**改一个已应用的 `.sql` 无法被检测**（只有注释在禁止）。
5. **入口体积是一条单点命脉**。门禁断言 `index.html` 恰好只有一个 `<script>`——这把「拆入口」结构性地判死（㉗ 已把它记为「为什么不成立」），同时 `i18n/zh.ts`（786 行，全仓第 4 大文件）被 **52 个文件**硬引用、必然进入口。
6. **Web 的机器证据密度最低**。看板拖拽零自动化证据；`ProjectDetailPage` 317 行、`KanbanBoard` 348 行、`PackWizard` 411 行、`FlowTemplateEditor` 407 行、`TermEditorDrawer` 348 行——五个最大的交互面合计 1,831 行，只有 `PortsPanel` 与 `Dialog` 有 DOM 断言。
7. **文档体系在承担它设计时没预料到的角色**。`DEV_LOG.md` 从「开发日志」长成了 851 KB 的**法证档案**（96 条登记、`decisions.md` 的计数要靠它复算、队列 ㉙ 的断号问题就出在这里）。它的信息价值极高，但检索成本与维护成本背离。

## 第 3 章 · 第一性原理重建

> 这一章不引用任何既有设计文档的结论，只从「用户为什么打开这个软件」出发重推一遍。第 4 章的所有建议都必须能追到本章的一条命题。

### 3.1 这个系统实际在做什么（重新定义）

**旧定义（现文档口径）**：vibe coding 的标准化工作台——把提示词、Skill、术语、技巧和项目流程变成可管理、可复用、可分发的工程标准。

**新定义（本文口径）**：

> **OpenVibe 是一个「人类意图 → 项目上下文」的编译器，外加一个分发器和一个反馈回路。**
>
> - **编译器**：把散落的人类知识（怎么说话、叫什么、怎么做、什么时候怎么做）编译成 AI 助手在特定项目里能消费的确定性文本。
> - **分发器**：把编译产物无冲突地落到 N 个平台契约上，并保留可验证的落地台账。
> - **反馈回路**：把项目里产生的经验，编译回库里的新资产。

这个重定义不是文字游戏——它立刻改变了三件事的优先级：

| 问题 | 「资产管理器」口径下的答案 | 「编译器」口径下的答案 |
|---|---|---|
| 什么最重要？ | 库的覆盖度（术语够不够多） | **产物的有效性**（编译结果进到 AI 上下文里，有没有改变 AI 的行为） |
| 什么最危险？ | 数据丢失 | **静默的语义漂移**（产物说 A，用户以为说的是 B；或 AI 实际没读到） |
| 什么最该优化？ | 录入体验 | **编译与再编译的往返成本**（改一条资产 → 全项目同步一轮的代价） |

### 3.2 从第一性原理推出的六条命题

#### P1 · 上下文是稀缺资源，它的价值不由「库里有多少」决定，而由「进到 AI 注意力里的密度」决定

AI 助手的上下文窗口是有限且**被计费**的资源。把一个 800 行的 `CLAUDE.md` 塞进每次对话，前 700 行是噪声时，剩下一百行的效力也被稀释。

**推论**：系统必须能回答「我这一包塞了多少 token、其中多少条真的被用过」，并支持**裁剪建议**。这直接给了 G3 一个可实现的形态：不是加一个「使用次数」计数器（那可以刷），而是让产物**本身**带上可回收的信号（见 §4.3 的两次编译对照）。

#### P2 · 不同资产的衰变率不同，生命周期必须分层

| 资产 | 衰变触发 | 半衰期量级 | 现在怎么管 | 应该怎么管 |
|---|---|---|---|---|
| 提示词 | 模型能力变化 / 技术栈换代 | 月 | `draft/active/deprecated` + 版本历史 | 加**效果反馈**（这条提示词在哪次任务上产出被采纳） |
| 术语 | 生态改名 / 概念澄清 | 年 | 同上 | 加**生态版本锚**（`Next.js 15 的 RSC`） |
| Skill | 外部工具发布/弃用 | 月 | 已有 `latest_version_id` + 远端跟踪 | 加**弃用预警**（上游 6 个月未更新即标） |
| 流程模板 | 团队习惯变化 | 年 | `builtin` 只读 + 复制 | 加**阶段完成度遥测**（哪一步总被跳过 ⇒ 该步设计有问题） |
| 标准包 | 版本制 | 随包 | semver + 指纹 | 加**用户盘迁移**（旧 lock → 新契约的升级路径） |

**推论**：J2 的建议不该是「给所有资产加一个 `level` 字段」（那是把同一个笼子换了个牌子），而应是**让每类资产携带它自己的时效语义**，并在 UI 上用不同的视觉语言呈现（提示词显示「最后验证于」、术语显示「生态版本」、Skill 显示「上游活跃度」）。

#### P3 · 「新手到专家」的本质是**权威的转移**，不是功能的解锁

一个真问题：新手的界面和专家的界面差在哪？

- 新手需要**系统替他行使权威**（照做，别让我选）。
- 专家需要**系统把权威交还给他**（别替我决定，给我原始信息和批量通道）。

这是一个**双对偶**，不是「功能多少」的差别。同一个人在不同的任务上处于不同的阶段：同一位专家，第一次配 Cursor 规则时也是新手。

**推论（这是 §5 全部设计的根据）**：

- 阶段**不能是账号属性**（不能「你被永久标记为新手」），必须是**（用户 × 资产类型 × 任务）的当前状态**。
- 阶段判定必须**可解释、可覆盖**：界面永远显示「为什么现在是这个视图」+ 一个「我要看全部」的出口。
- 专家退化的形式是**信息密度与快捷键**，不是功能的隐藏再显示——**永远不隐藏数据，只重排与预填**（这条是硬约束，写进 §5.3）。

#### P4 · 验证能力是产品价值，不是内部治理成本

一个会写用户文件的工具，最难卖的从来不是功能，是**信任**。信任 = 可预测 + 可核验 + 可回退。

现有系统已经有完整的原料（指纹、lock、三重保护、备份），但把它当成了**内部安全措施**，没有当成**对外主张**：

- `diff` 报到 2 就结束，用户拿到的是「有漂移」，不是「哪几段漂了、漂成什么样、我该怎么办」。
- 用户无法在注入后自问「我的磁盘现在和台账一致吗」。

**推论**：J4 的核心动作是把「三重保护」升级为**三层保证模型**（§4.4），并把它做成第一个用户可见的信任面。**凡「维护成本」与「验证收益」冲突，一律倒向验证**——这是本文唯一一条价值排序上的硬规定。

#### P5 · 治理的成本必须随项目规模**次线性**增长，否则项目会死于自身流程

一个可测的事实：项目现在有 23,481 行源码 + 851 KB 开发日志 + 约 15 KB 决策队列 + 5,016 行规格文档。**每一笔改动要带的文档量在增长**，而这个增长是**线性**的（改一行代码 → 写一段登记 → 更新队列 → 同步计数 → 可能升版 → 更新版本链）。

第一性原理：治理的目的是**防止真错误**，不是**记录所有真话**。当治理成本超过它防止的错误成本时，理性行为是**降低治理粒度**，而不是加大纪律。

**推论**：把「人肉保持一致」的项转成「机器校验」，把「必须写的散文」压缩成「必须填的结构化字段」（§4.11）。目标不是更少的记录，而是**同样多的记录、更少的维护工时**。

#### P6 · 系统的边界应当是「可自证的」，而不是「被信任的」

对 `~/.openvibe/` 与用户项目目录这两个写面，系统的每一次写动作都应该能回答：**我写了什么、依据是什么、怎么撤**。

现状：写有备份、有 lock，但**没有一个命令能回答「现在磁盘、lock、包内容三者一致吗」**。`diff` 只比「磁盘 vs lock」两方（`inject/lock.ts` `diffPackLock` 只认 clean/drifted/missing）。三方一致性（包内容 / lock 期望 / 磁盘实际）是更强的性质，而且**实现它几乎不需要新算法**——三方哈希都在手上。

### 3.3 边界声明：这个系统不该做什么

第一性原理的另一半是**划出不做的事**。以下四条我建议写进产品纪律（若采纳）：

1. **不做云端账号体系**（除非推翻「本地优先 + 只听回环」这条根设定——那是一次产品身份变更，不是一次功能开发）。
2. **不做 AI 自动改用户的资产**。系统的 AI 能力只用于**起草候选**（术语/提示词/技巧草稿），落库必须人工确认。理由：资产是标准，标准被悄悄改掉比没有被更危险。
3. **不做双向同步**（AI 助手改文件 → 回写库）。理由：助手产出的是**使用**，不是**标准**；把使用混进标准会污染信号（P1 的密度度量会因此失真）。若确实需要，走**明确的「上收」动作**（用户显式点「把这段提取为资产」），而不是后台同步。
4. **不做全量文件覆盖作为默认**。默认应倒向「保留本地 + 显示块级差异」（这也正好与 `DESIGN.md` 已写、队列 ㉕ 待裁的方向一致）。

### 4.2 D1 · 运行时依赖：把「零原生依赖」变成架构的可选项

**现状**：CLI 发布包唯一外部依赖 `better-sqlite3`（`scripts/build-cli.ts:139` 硬编码 `external`）。这是事实正确（`.node` 不可 bundle），但把「让用户 30 秒跑起来」赌在预编译产物 + 平台 ABI 匹配上。README 已记两处摩擦：pnpm 10 的 `approve-builds`、以及「装后跑通五命令未在干净机复验」。

**张力（P6）**：系统的进入门槛应当尽可能只依赖 Node 本身。

**候选**：

| 方案 | 说明 | 代价 |
|---|---|---|
| (a) 现状 + 文档 | 把平台/ABI 要求写进 README 与首启报错 | 最低，但不解决核心机（无工具链的机器） |
| (b) 换纯 JS 存储 | 换 `sql.js`（WASM）/ JSON 文件 | 推翻 FTS5 触发器 + WAL + `busy_timeout` 这一整套已测语义；性能与并发语义退化 |
| (c) **抽 `Store` 端口** | `core` 定义窄接口（`query/exec/tx/fts`），SQLite 为首选实现；保留一个「单文件 JSON + 内存索引」的降级实现，仅在原生模块不可用时启用（只读 + 显式警告） | 要动 `repos/` 全部（10 模块 2,432 行）的注入点；收益是**第一条命令不再可能失败** |

**建议：(c) 但分两步，且第二步可选。** 第一步只做「端口化 + 失败时的可读诊断」——即 `better-sqlite3` 载入失败时，不再抛原始 ABI 错误，而是给出「你的平台/Node 版本 + 三条修复路径」。第二步（降级实现）**留待真的有用户卡住再做**——避免为假想用户写一个平行存储。

**影响面**：`packages/core/src/db/index.ts`（36 行）+ 10 个 repo 的构造注入。**可逆性**：高（端口是新抽象，SQLite 路径逐字节不变）。**判级**：B。

### 4.3 D2 · 本地事件台账：用「不上报的埋点」解决 D15

**现状**：队列 ⑱ 判定 D15 左半「工作台真实使用 ≥10 次」**无机读源**，因为前端零发射（这是「关闭即零外联」承诺的**正确**结果）。同时 `injections` 表只记 `(pack_id, pack_version, project_path, injected_at)`。

**张力（P1/P6）**：度量有效性的前提是有信号；而信号采集不能削弱隐私承诺。

**关键洞察**：**「不开埋点」与「没有信号」不是同义词。** 系统每天都在产生信号（用户点了什么、注入了什么、回流了什么），只是没往本地记。**本机事件台账**与**遥测**是两件完全不同的事：前者不出网、不进白名单、可随时清空，后者才是 D13 管的那个面。

**建议**：

1. 新增 `local_events` 表（append-only）：`id / kind / subject_type / subject_id / project_id / payload_json / created_at`。
2. `kind` 首版**闭集**（与遥测三事件严格不同名，避免混淆）：`asset_created` / `asset_reflowed` / `pack_composed` / `pack_exported` / `injection_confirmed` / `injection_conflict_resolved` / `stage_advanced` / `checklist_item_checked` / `flow_template_run` / `stage_view_switched`。
3. 写入点集中在**服务层**（D9）而非散落各处——这正好是 D9 的第一个收益。
4. 一个只读端点 + 一个「本机统计」页：`GET /api/local-events/summary`（按 kind/day 聚合）。
5. **隐私声明一字不改**：该表只在 `~/.openvibe/data/openvibe.db` 内，无网络路径；设置页新增一句「本机统计：只在本机，永不上报」，并给「一键清空」。

**为什么这比「加前端埋点」好**：① 不触 A/B 级隐私承诺面；② 覆盖 CLI 侧（用户可能全用 CLI，前端埋点抓不到）；③ 是 D15 左半的直接解 —— `stage_view_switched` + `flow_template_run` 就是「工作台真实使用」的机器可数形式。

**影响面**：新迁移 `0006_local_events.sql`、`core/repos/localEvents.ts`、`server/routes/localEvents.ts`、`web/src/pages/SettingsPage.tsx` 加一节。**可逆性**：高（停止写入即可）。**判级**：B（新表 + 新端点；不动任何白名单）。

### 4.4 D3 · 写入事务性：从「三重保护」到「三层保证」

**现状**：写盘有备份 + `sync.lock` + `atomic-write`（符号/硬链接解链重建）。**没有**：崩溃/中断后的三方一致性核验；没有「一次注入要么全成要么全不成」的事务语义（逐文件写，中途失败会留下部分新部分旧）。

**张力（P6）**：「可自证」要求系统能回答「三者一致吗」。

**建议（三层保证模型，逐层可独立交付）**：

| 层 | 保证 | 实现 | 用户可见形式 |
|---|---|---|---|
| L1 **完整性** | 每一次写都有前置备份，且备份可定位 | 已有（`.openvibe/backup/<utc>/`） | `sync` 报告里印出备份路径 |
| L2 **可恢复性** | 中断后能回到一致态 | ① 写入顺序固定：**先写 backup → 再写 `pack.lock.json` 的 `.tmp` → 逐文件写 → 最后原子替换 lock**；② 新增 `openvibe verify <dir>`：三方比对（**包内容** vs **lock 期望哈希** vs **磁盘实际**），输出 `CONSISTENT / PARTIAL / STALE_LOCK / ORPHAN` 四态 + 一键修复建议；③ `sync` 开始时先跑一次内部 verify，若上一轮**部分完成**（lock 与磁盘同时偏离包），提示「上次注入可能中断」并给 `--resume` | `openvibe verify` + Web 项目页的「一致性」徽标 |
| L3 **可解释性** | 用户能看懂「为什么是这个决策」 | 复用 `planner` 已有的五态，但把理由**渲染成人话**（现在只有状态名）；块级（D4 落地后）显示到段 | 冲突处置屏：每文件一行「为什么：lock 记的哈希是 X、磁盘是 Y、包是 Z」 |

**注意（这条很重要）**：L2 的「三方一致性」**不需要新算法**——三个哈希都已存在（包内 `fileSha256`、lock `files[].sha256`、磁盘实时计算）。它现在是「信息都在但没人把它们放在一起看」。

**影响面**：`core/inject/`（新增 `verify.ts`）、`cli` 新增 `verify` 子命令、`server` 新增 `GET /api/projects/:id/consistency`、Web 项目页徽标。**可逆性**：高（纯增量）。**判级**：B；**若** decide 把一致性状态写进 `pack.lock.json`（新键），则升为 **A**——本文建议**不写进 lock**（保持 lock 契约冻结），而是每次现算。

### 4.5 D4 · 块级受管标记：把已有标记升为契约（本文唯一 A 级建议）

**现状**：产物首尾已有 `<!-- openvibe:pack=<name>@<version> begin (regenerate: npx openvibe-cli sync) -->` 与 `<!-- openvibe:end -->`；`design.md §7.3` 明文「MVP 按整文件管理……标记为 P1『块级合并/双向同步』预留，现在就写入」。`planner` 的五态判定按**整文件 sha**。

**张力（P4/J5）**：0.6% 的极差触发 100% 的决策成本。

**建议**（分三档，可分批交付，第 1 档不触契约）：

| 档 | 内容 | 是否触 A |
|---|---|---|
| 4-a | **段级差异展示**（只读）：把 `diff` 的输出从「文件级 DRIFT」细化为「段级：工作流程变了 2 行、术语表未变、行为规则新增 1 条」。**不改契约、不改写入行为**，靠对比「包渲染的段文本」与「磁盘上按标记切出的段文本」实现 | **否（C/B）** |
| 4-b | **段级选择**：DRIFT 文件的三选一细化为「行为规则：以包为准 / 保留本地；工作流程：以包为准…」，默认仍是整文件决策 | **否（B）**——写盘结果多了一种组合，但 lock 形状不变 |
| 4-c | **段级受管 + 契约升级**：产物内每段带 `<!-- openvibe:section=<key> -->`，段外区域成为用户的自由区；`schemaVersion` 1→2、golden 重基、C25/D25 那条 A 级流程 | **是（A）** |

**建议：4-a 立刻做，4-b 视 4-a 的实测收益决定，4-c 与队列 ㉘ 的 `schemaVersion` 1→2 合并成一次 A 级动作。** 理由：㉘ 已经因为改名要动 `schemaVersion` 与 golden，如果把 4-c 并进去，**一次重基换两个能力**（改名 + 段级），而不是两次让用户盘漂移。这与队列 ⑥ 立的「升版段须可复核、别拆成多次无独立态的动作」是同一条纪律。

**影响面**：`pack/composer.ts`（段切分与标记）、`inject/planner.ts`（段级比较）、`design.md §7.3`（契约原文）、`tests/golden/*`（重基）。**可逆性**：**低**（对外契约，一旦发出只能向前兼容）。**判级**：4-a = B，4-c = **A（须 owner 签字 + 独立复核）**。

### 4.6 D5 · 包的三层生命周期

**现状**：库里的包版本不可变（同版本重导指纹不一致 → 409）；项目 `pack.lock.json` 是**单包结构**（换包即整包替换，不支持多包叠加）；`clean` 是唯一的退场；**没有 `update`**（标记已预埋）。

**张力（P2/P6）**：包的「版本」概念现在只活在库侧，用户盘上的包没有升级路径。

**建议**：明确三层，并给每层一个动词。

| 层 | 语义 | 已有的动词 | 应补的动词 |
|---|---|---|---|
| **库版本** | 不可变、可复现、可分发 | `compose` / `export` / `preview` | 无（已完整） |
| **项目 lock** | 可复现的当前状态 | `sync` / `diff` / `clean` | **`verify`（D3）** |
| **部署** | 可演进的落地 | — | **`update`**：`diff` 出「包新版本 vs 当前 lock」的**变更集** → 预览 → 段级应用（复用 D4） → 写新 lock；`rollback`：从 `.openvibe/backup/` 回到任一历史注入点 |

**为什么现在值得补**：队列 ② 的发布路径、㉗ 的入口拆分、㉘ 的改名都指向同一件事——**对外的版本演进开始发生**。没有一个 `update`，用户面对新版本只能 `clean` + `sync`，而 `clean` 会**删掉他手改过的文件的受管部分**（`--force` 时）或整体保留（默认），两种都不是「升级」。

**影响面**：`cli` 新命令 + `core/inject/` 的计划器扩展；**不改 lock 形状**（升级后仍写同形状的新 lock）。**可逆性**：高（纯增量）。**判级**：B（新命令 = 新行为面，但不改既有契约）。

### 4.7 D6 · adapter 契约：从「文档矩阵」到「夹具 + 探针」

**现状**：adapter 实现极薄（4 个 11 行 + cursor 26 + trae 32），契约依据写在 `design.md §8` 的表格里，证据方式是真机探针（Trae 二进制级）。**这是好习惯**，但它是**一次性**的：探针脚本跑过就留在 `devlog-evidence/` 里，没有「平台契约变了会自动红」的机制。

**张力（P4/R2）**：adapter 的价值全在「写对地方、配对壳」；写错了不会崩，只会**静默无效**（AI 读不到规则）。

**建议**：

1. 每个 adapter 增加一份**产物夹具**（期望输出快照，进 golden 体系）——现在 golden 只覆盖 3 个 manifest，不覆盖各平台产物文件的**形状**（frontmatter 键、路径、大小写）。
2. 一份 `docs/specs/adapter-matrix.md` 由 `compat.ts` **生成**（而非手写），保证「文档说的平台覆盖」与「代码里的矩阵」永远同源。
3. 真机探针脚本**保留在仓库里、可复跑**（现在在 `docs/devlog-evidence/DEV-0016/`，是证据而非工具），并在发布说明里注明「上次真机复跑时间」。

**影响面**：`packages/adapters/` + `tests/golden/`。**可逆性**：高。**判级**：B。

### 4.8 D7 · 入口体积：先收回 17 kB，再改门禁的形态

**现状**：入口 299,978 B / 上限 300,000 B → **22 B**。`i18n/zh.ts` 786 行被 52 个文件静态引用；`bundle-check.ts:43` 断言 `index.html` 恰好一个 `<script>`。

**张力（J4/P5）**：一条余量 0.007% 的闸，等于把「所有并行会话的提交」绑在一个随时会断的线上。

**建议（三步，第 1 步立刻可做）**：

1. **i18n 懒加载**（队列 ㉗ 已裁「拆按需 chunk」，此处补充**具体形态**）：把 `zh.ts` 按**路由命名空间**切成 `i18n/zh/{common,library,terms,skills,flows,projects,packs,settings}.ts`，每个页面 `import()` 自己的命名空间（页面本来就是 `React.lazy`，所以**不新增任何网络往返**）；保留一个 `zh.common` 同步加载（约 2 kB）供 AppShell/Toaster/Dialog 用。
   - 类型安全做法：以 `zh` 为**类型真源**（`type Dict = typeof zh`），各命名空间文件声明 `satisfies Partial<Dict>`，缺键在编译期报错——不引入 i18n 库、不引入运行期 `t()`。
   - **为什么不是「拆整个入口」**：`bundle-check` 的单 `<script>` 断言把那条路判死了（㉗ 已记）。要么改门禁，要么换手段——改门禁是**削弱闸**，换手段（命名空间懒加载）是**不削弱闸的等价解**。
2. **门禁形态升级**：`bundle:check` 的失败信息从「超了 X kB」升级为「**本笔 vs 上一笔的差值 + 归因到文件**」（复用 vite build 的 `metafile`/`sourcemap`，`DEV-0082` 已经用过一次这个手法）。这样余量本身变成一个**可见的、每笔更新的数字**，而不是一个只在打红时才被想起的阈值。
3. **余量治理规则**（写成 DoD 一行）：凡新增进入口的依赖或文案，须在本笔登记里报出实测差值。这条是 C 级，但它把「22 B 事件」变成制度。

**影响面**：`apps/web/src/i18n/`（拆 8 个文件）、52 个引用点、`vite.config.ts`、`scripts/bundle-check.ts`。**可逆性**：高。**判级**：B（构建行为 + 全量引用点，但不触对外契约）。

### 4.9 D8 · 校验边界：出参侧只补三条，不做全局环绕

**现状**：入参 zod 全覆盖；**出参 0 校验**。㉖ 的实证是「此刻不炸的唯一原因是出参侧没有闸」。

**张力（R2/G5）**：给所有响应包一层 `.parse()` 是性能与噪音的双输；不补则下一次「顺手加个校验」就炸。

**建议**：只在**三条边界**上加运行时断言，其余保持类型级：

| 边界 | 为什么是它 | 形式 |
|---|---|---|
| **pack manifest / bundle** | 直接写用户磁盘、跨机器传输、有指纹校验语义 | 已部分有（CLI 侧重算 `verifyPack`）；补服务端侧 `PackManifestSchema.safeParse` 并断言 |
| **API 出参（仅 Web 依赖的字段）** | Web 的 `apiJson<T>` 是裸 `as T`（`api/client.ts:50`），契约漂移对 Web 完全不可见 | 只在**开发模式**（`import.meta.env.DEV`）包一层 safeParse + console.error，生产零开销 |
| **DB 行 → 领域对象** | 当前 repo 直接把 JSON 列当数组用（`parseJsonColumn` 容错）；脏数据会静默变成 `[]` | 仓储出口处对关键列加断言，失败按 `未知` 处理而不是 `空` |

**影响面**：`packages/shared/src/schemas/` 的使用点、`apps/web/src/api/client.ts`、若干 repo 出口。**可逆性**：高。**判级**：B（不新增键，但改变失败行为——**凡把「静默空」改成「显式未知」的行为变更按 B 记**）。

### 4.10 D9 · 薄服务层：让业务规则只有一个家

**现状**：无服务层。同一规则两处实现（包渲染：`server/lib/pack-assemble.ts` ↔ CLI `pack-source.ts verifyPack`）；路由文件里藏编排（`packs.ts` 的导出通道分支、`settings.ts` 的种子摘要）。

**张力（P5）**：每次改动要在两处保持一致，是文档量与错误率的乘数。

**建议**：在 `packages/core/src/services/` 建薄服务层，**只承载「一次用户意图」级的编排**（不是重写 repos）：

- `services/packService.ts`：组包 → 预览 → 导出 → 校验（把现在 server/CLI 各写一半的流程合一）
- `services/injectService.ts`：计划 → 决策 → 应用 → 核验（D3/D4 的落点）
- `services/growthService.ts`：信号 → 阶段判定 → 建议（§5 的落点）
- `services/statsService.ts`：本机统计聚合（D2 的落点）

server 的 route 变成「解析 → 调 service → 序列化」；CLI 的 command 变成「解析 → 调 service → 渲染」。**约束**：service **不得**依赖 fastify / commander / 任何 HTTP 与 TTY 概念（继续用 `eslint-plugin-import-x` 的 zone 钉住，与现有 R1–R4 同法）。

**影响面**：约 15 个文件的搬迁 + 两个 zone 规则。**可逆性**：高。**判级**：C（纯重构，行为不变）——但**它是 D2/D3/D4/D12 的前置**，建议优先。

### 4.11 D11 · 治理即代码：把「人肉保持一致」换成「不一致即红」

**现状（J6/G6）**：队列 29 项 / 5 状态，单行可达 2 KB；`decisions.md` 自称唯一事实源，但已发生 2 次计数错报 + 1 次断号（㉙）；`DEV_LOG.md` 851 KB / 96 条；版本链靠人肉维护。

**张力（P5）**：治理的成本是线性的，项目的复杂度是指数的，两条线必然相交。

**建议（四件，全是「新增校验」，不改产品）**：

| # | 动作 | 收益 | 判级 |
|---|---|---|---|
| 11-a | **队列转结构化**：`docs/decisions.md` 的表格拆成一份 `docs/queue.yaml`（每项：`id / title / state / evidence /落点 / 阻塞`）+ 由脚本渲染回 md。**人只读渲染产物，单源在 yaml** | 计数由脚本算 ⇒ 计数错报 structurally impossible；断号可校验 | C |
| 11-b | **`docs:check` 脚本**：① 每条 `[DEV-NNNN]` 连续且唯一；② 队列状态枚举合法 + 净状态计数与表格一致；③ 每个「单源」声明（如「以 §7 标题为准」）能真的从被指文件里取到值；④ 文档里的版本链单调递增 | 现在靠人复算的四件事全部机器化 | C→B（新增门禁进 CI） |
| 11-c | **登记的结构化必填字段**：`DEV_LOG` 每条固定 5 段（问题/思路/变更/验证/风险）已被 `README.md` 规定，但无校验。加一条 grep 级校验（段落标题齐不齐、`验证` 段是否含**可复算命令**） | 把「有实现零用例」「超时腿无断言」这类缺口在提交时暴露 | C |
| 11-d | **A 级变更模板**：任何触 A 契约的改动，必须有独立复核记录（现在 `DEV-0043` 有过一次，做法很好但没变成制度） | 把一次性的好做法制度化 | C |

**重要边界**：这一节**不减少记录量**，只减少维护工时。P5 的推论是「同样多的记录、更少的维护」，不是「少记一点」。**任何以「治理太重」为由删除既有登记的动作，都不在本文建议内。**

### 4.12 D10 · 常量与模块面：把 `shared` 从杂物袋变成契约层

**现状**：`shared` 13 个 `export *`，混 zod schema + 数据表（`TERM_ROADMAP`）+ 字符串构造器（`interviewPrompt`）+ 错误码 + id 前缀。135 处引用拿到整个面。`cli/output.ts` 的 `SYNC_STATES` 与 `core` 的 `INJECT_STATUSES` 是同物两名，并衍生出「汇总键不能叫 `counts`」的隐式约定。

**建议**：`shared` 拆成三个出口面（**不拆包**，只拆入口）：

```
@openvibe/shared          → 契约面：zod schemas / errors / ids / 纯工具（无数据、无文案）
@openvibe/shared/content  → 内容面：TERM_ROADMAP / 受控词表 / interviewPrompt / 文案模板（可懒加载）
@openvibe/shared/constants→ 常量面：状态枚举、文件路径常量（单源；SYNC_STATES 与 INJECT_STATUSES 合一）
```

**收益**：入口 chunk 不必再靠「手工把 `TERM_ROADMAP` 搬到另一个文件」来避免被拉进入口（`constants.ts:47` 现在的注释就是这个补丁）；`INJECT_STATUSES` 只有一个家。

**影响面**：135 处引用 + `package.json` 的 `exports`。**可逆性**：高。**判级**：C（纯组织）。

## 第 5 章 · 成长路径设计（核心章节）

> 这是本文与既有文档差异最大的部分。现存文档对成长只有零散提及（PRD 2.1 画像表三行、proposal §4 三行为主），**没有阶段模型、没有信号、没有披露规则**。本文给出完整设计。

### 5.1 四阶段模型（定义在「用户 × 资产类型 × 任务」上，不是账号属性）

| 阶段 | 代号 | 用户的心智 | 系统该替他行使的权威 | 明确的毕业信号（可机器判定） |
|---|---|---|---|---|
| **F0 跟随者** | Follower | 「别让我选，告诉我做什么」 | **替他决定**：一套默认标准包、一条命令、一个流程模板 | 完成 1 次端到端注入 + 勾完 1 个阶段的清单（`injection_confirmed` ×1 且 `checklist_item_checked` ≥ 阶段项数） |
| **F1 实践者** | Practitioner | 「我想知道为什么，我想挑」 | **给他选项与解释**：条款级开关、术语路线、模板对比 | 改过 ≥1 次资产内容 + 用过 ≥2 个流程模板（`asset_updated` ≥1 且 `flow_template_run` 覆盖 ≥2 模板） |
| **F2 作者** | Author | 「我要写自己的标准」 | **给他创作工具**：复制模板、批量编辑、自定义清单、组自己的包 | 自建过 ≥1 个资产（`asset_created` 且 `source != seed`）且导出过 ≥1 个非预置包 |
| **F3 定标者** | Standard-setter | 「我要定义别人怎么判断」 | **给他元规则**：检查项的设计权、评审流、使用统计 | 团队共享（M7）或 ≥3 个项目共用同一包（`pack_exported` 被 ≥3 个项目引用） |

**三个关键设计决定**：

1. **阶段是三维的，不是一维的**。`(用户, 资产类型, 任务)` 三者共同决定视图。一个人在「提示词」上是 F2（写了很多）、在「Skill」上可能还是 F0（刚扫第一次）。实现上用**按模块维护的阶段向量**（`{prompts: F2, terms: F0, skills: F0, flows: F1, packs: F1}`），而不是一个全局级别。
2. **阶段单调递增但可显式回退**。毕业信号只升不降（避免「今天手滑降级了」的挫败），但用户随时可以点「切换视图」回到任一阶段，且设置页有「重置我的阶段」。
3. **升级点必须是一个可感知的瞬间**。阶段不是静默切换的——升级发生在一次**任务完成之后**（注入成功 / 阶段清空 / 首次导出），以一张一次性卡片出现：「你现在可以直接改模板了，要不要看看怎么改？」（复用 `TelemetryAskCard` 与 `OnboardingBar` 的既有形制，**不新造交互语言**）。

### 5.2 信号采集（复用 D2 的事件台账，零新增网络面）

| 阶段判定所需信号 | 事件 | 现有能力 | 需新增 |
|---|---|---|---|
| 走了几圈飞轮 | `pack_exported` / `injection_confirmed` / `asset_reflowed` | 部分（`injections` 表、`linked_asset_ids`） | ✅ 统一事件台账 |
| 用过什么 | `flow_template_run` / `stage_advanced` | Web 侧零信号 | ✅ |
| 改过什么 | `asset_created` / `asset_updated` / `asset_deleted` | repo 层可埋 | ✅（在 D9 服务层埋，一处） |
| 冲突怎么解的 | `injection_conflict_resolved`（带策略） | `planner` 有决策，无记录 | ✅ |
| 看过什么 | `stage_view_switched` | 零 | ✅ |
| 卡在哪 | `injection_failed`（带错误码） | CLI 有错误码 | ✅ |

**隐私边界（必须写死在实现里）**：这些事件与遥测的 `pack_injected` / `flow_template_used` / `project_active` **不同名、不同表、不同出口**。遥测关闭时的行为一字不变。设置页两节并排：「本机统计（永不出网）」与「匿名统计（默认关，三类事件）」。

### 5.3 渐进披露规则（硬约束）

```
规则 1 · 永不隐藏数据       只有排序、预填、折叠默认值的差别，「查看全部」永远一键可达
规则 2 · 永不隐藏错误       任何阶段都必须看到失败、漂移、冲突（不为了「简单」而吞错）
规则 3 · 阶段可见可解释     界面上永远有一句「为什么你现在看到这个」（可点开）
规则 4 · 一键越级           任意页面可切到「专家视图」，且记忆该选择（按模块）
规则 5 · 升级不打断         升级提示是一次性卡片，不是模态框；拒绝后不再打扰（同 telemetryAskState 形制）
```

**各阶段的差异实现**（示例，非穷举）：

| 界面 | F0 默认 | F1 | F2/F3 |
|---|---|---|---|
| `/library` | 21 条精选，按「场景」分组，无版本面板 | 全部 + 标签/文件夹 + 版本历史 | 批量导入导出、raw diff、CLI 命令直接给 |
| `/terms` | 术语路线图默认展开（`TermRoadmapView`），只显示第 1 站 | 全部 4 站 + 搜索 | 受控词表编辑、批量改 tag |
| `/packs/new` | 五步向导，每一步都预填（默认包选择） | 向导 + 可跳步 | 直接编辑 selection JSON / CLI 一行 |
| `/projects` | 阶段条 + 清单（看板折叠） | 全开 | 键盘优先、批量操作 |
| 冲突处置 | 「推荐：保留本地」（见下方说明）+ 一句人话解释 | 显示三方哈希 + 段级差异 | 原始 JSON、`--strategy` 脚本化 |

**顺带回答队列 ㉕**：DESIGN.md 已写「保留本地」预选、`planner` 默认 `overwrite`、m6a FR-7 要求同屏高亮一个默认。本文的建议支持 **(a) 只改 Web 预选**（即 ㉕ 的 (a) 案），并补一条 §3.3 的边界声明：**默认倒向保留本地**——因为「不静默覆盖用户手改」是这个产品对外的头号承诺（README FAQ 第一条），而 CLI 的 `--yes` 是无交互语义，两者的默认本来就可以不同，只要同屏如实标注。

## 第 6 章 · 业务流与全流程设计

### 6.1 端到端目标流程（改造后）

```
① 装        npx openvibe serve --open            ← 首启：播种 + 组装 default 包 + 打开向导
              │
② 见效      openvibe sync ~/my-project --pack default
              │   ← 干跑预览 + 「为什么这样写」逐文件说明（D3-L3）
              ▼
③ 确认      .openvibe/pack.lock.json + 8 个产物文件 + 备份 + 本机事件 injection_confirmed
              │
④ 工作      项目工作台：阶段条 → 清单 → 看板 → DEV 日志（F0 只露阶段+清单）
              │       ↑ 本机事件：stage_advanced / checklist_item_checked
              ▼
⑤ 变更      改资产 → 组新包版本 → 导出
              │       ↓
              │   openvibe diff（现在报：段级差异）→ openvibe update（D5 新命令）
              │       ← 段级选择（D4-4b）→ 写新 lock + 备份
              ▼
⑥ 回流      日志选段 → [存为术语/提示词/技巧候选] → 草稿 → 人工确认入库
              │       ↑ 本机事件：asset_reflowed
              ▼
⑦ 核验      openvibe verify（三方一致性）+ 一致性徽标（D3）
              │
⑧ 退场      openvibe clean（不变）／ openvibe rollback（D5 新）
```

**与现状的差异（逐条）**：

| 步 | 现状 | 改造后 | 依据 |
|---|---|---|---|
| ① | 首启向导 3 步 | 不变（形制很好，**不动**） | — |
| ② | sync 给预览表 + 冲突三选一 | 增加「为什么」解释层（D3-L3） | P4/P6 |
| ③ | 写 lock + 文件 | 不变 + 本机事件 | D2 |
| ④ | 全功能一次性呈现 | F0 折叠看板、只露阶段+清单，可一键展开 | P3/§5.3 |
| ⑤ | `diff` 报漂移；无 `update`；改一行要全文件决策 | 段级 diff + `update` + 段级选择 | J5/D4/D5 |
| ⑥ | 一键回流（M1/M3），M4 无承接 | 三路回流（含技巧，M4 已在 T12） + 确定性候选提取 | C4 / `m4-playbook` |
| ⑦ | 无核验命令 | `verify` + 徽标 | D3 |
| ⑧ | `clean` 一个退场口 | + `rollback` | D5 |

### 6.2 冲突处置路径（改造后，这是最高频的摩擦点）

```
openvibe diff <dir>
  │
  ├─ CONSISTENT（三方一致）→ 退出码 0，无事发生
  │
  └─ 有差异 → 逐文件、逐段列出：
        CLAUDE.md
          ├─ 工作流程        段：包 = v1.2，磁盘 = 你改过（2 行）   [以包为准 | 保留本地 | 跳过]
          ├─ 行为规则        段：一致
          └─ (段外自由区)                                       [永不触碰]
        TERMS.md             整文件一致
        .cursor/rules/openvibe.mdc   ⚠️ 手工新建的文件（FOREIGN，绝不删）
```

**默认值**：F0/F1 → `保留本地`（保护手改）；F2/F3 可通过 `--strategy` 显式脚本化。CLI 无 `--yes` 的交互式预选与 Web 预选**一致**；`--yes` 的语义仍是「按 `--strategy`」，无 `--strategy` 时维持现状（避免改已发布的 CLI 语义）。

### 6.3 退场路径（改造后）

```
openvibe clean <dir>      现状不变（默认只删未改动的受管文件，删前备份；--force 连改过的一起删）
openvibe rollback <dir>   新增：从 .openvibe/backup/<utc>/ 回到任一历史注入点
openvibe verify <dir>     新增：只读核验，不改盘
```

**为什么 `rollback` 值得有**：备份目录已经在产生（每次覆盖前），但**只有 `clean` 会用它**。用户真正需要的动作是「我升到新版本后发现问题，回到上一版」——这是 `rollback`，不是 `clean`。

## 第 7 章 · 阶段式迁移路线

> 排期原则：**先解锁被堵住的路，再做新能力**。P0 只做「不削弱任何闸、且立刻解除阻塞」的事。

### Phase 0 · 立即解除阻塞（建议本周）

| # | 动作 | 为什么是 P0 | 门禁判据 | 判级 |
|---|---|---|---|---|
| 0-1 | i18n 按命名空间懒加载（D7 步 1） | 入口只剩 22 B，所有并行会话的提交都踩在这根线上 | `bundle:check` 入口回落 ≥ 15 kB；`pnpm test` 全绿；52 个引用点无遗留 | B |
| 0-2 | `bundle:check` 失败信息升级为差值报告（D7 步 2） | 让余量成为每笔可见的数字 | 故意加 1 kB 文案 ⇒ 报出「+1.0 kB，归因 zh.ts」 | B |
