## 第 0 章 · 一句话与三条目标（Goal）

> **重构方案的骨架已经走了三分之二：Phase 0（止血）五项全落地，Phase 1（写盘自证）六项里三项已绿；剩下的账分三类——已解锁待执行的（服务层收敛 + adapter 矩阵）、卡在 owner 签字的（A 级契约定型）、卡在实测走查的（成长线撤回判定）。重构 goal = 按「先收便宜账 → 合并 A 级重基窗口 → 走查定成长线」的顺序清账，让重构线在 v0.3.0 中台线全面开工前回到「契约定型完成」状态。**

### 3.2 顺序理由（为什么是这个序，三条递进）

1. **W-0 在最前**：D32 签字缺漂移形态统计这张证据（§10-2 明文要求「没有它，D32 签字就是无据签字」）；adapter-fixtures 的快照矛盾不回填，W-1 的 1-4 就没有开工依据。**证据先行，零代码，成本最低。**
2. **W-1 在 W-2 前**：服务层不收敛（routes 28 处直写），A 级改契约时每处直写都是潜在的遗漏点；先收敛成单一落点，重基的爆炸半径才可控。这是「先解锁被堵住的路」的直译。
3. **W-2 合并窗口是本计划唯一的效率主张**：D32（段级标记）、4-2（schemaVersion）、N3（hooks 字段）、N4（m11 产物）四件事各自触发同一条 A 级链（golden 重基 + 双 reviewer + schemaVersion+1）。**分四次走 = 四次重基；合并 = 一次重基换四个能力。** 代价（合并后 golden diff 无法分开归因）与替代（分次，每件多走一次完整流程）都已在 ㉛ 行写明同款先例——是否合并是 **owner 的裁定点 ①**，本文只登记主张与代价，不代裁。

**本计划不做**（防止蔓延）：不重写技术栈；不引入 i18n 框架/第二语言；不做云端账号/云同步；不做后台常驻与文件监听；不做 LLM 推断式候选提取；不做双向同步；不为「治理太重」删除既有登记；**不逐条修分析文 §8.1 的历史漂移**（顺序裁定：先建校验再修存量，PRD §10.2 表末注已裁）。

**否证机制（㉝ 的执行形态）**：分析文 §10 十条触发器在**每个批次收口时逐条复查**（W-5 做全表总复查）。与本计划直接相关的三条：
