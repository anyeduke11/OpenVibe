## 1. 一句话提案

> 做一个**本地优先的自部署工作台**：把 vibe coding 的五类资产（提示词 / Skill / 术语 / 技巧 / 项目流程）沉淀为带版本的标准库，组装成「标准包」一键注入真实项目，并把项目复盘的产出回流成新资产——**转起「沉淀 → 分发 → 使用 → 回流」的标准化飞轮**。

## 2. 为什么做

### 2.1 问题真实存在（PRD 1.2）

1. **资产散落**：提示词躺在聊天记录与收藏夹，规则散落在 `.cursorrules` / `CLAUDE.md` / `AGENTS.md`，换项目、换工具、换人即失效。
2. **没有标准**：同一团队每人喂给 AI 的规则质量天差地别，AI 输出质量随人而变。
3. **知识流失**：踩过的坑、发明过的词没有沉淀载体，新人重新踩一遍。
4. **流程随意**：AI 编码项目缺统一的需求→实现→复盘流程，质量靠运气。

### 2.2 市场是空白（competitive-research.md 核心结论）

- PromptHub（1.7k★）占「个人资产管家」；BMAD / spec-kit 占「流程模板」；skills.sh 占「skill 分发」。
- **无人做「资产 + 知识 + 流程」的标准化闭环**；术语库、技巧库、团队标准包分发三块近乎无人区。
- 策略：避开资产管家正面战场（不与 PromptHub 拼全功能），占空白（术语/流程/标准包），打闭环。

### 2.3 为什么是现在

vibe coding 已是主流开发方式，而各 AI 编码平台的规则/技能目录契约（`CLAUDE.md`、`.cursor/rules/*.mdc`、`~/.claude/skills`…）已趋稳定且均接受纯 Markdown——**用一套纯文件标准适配所有平台的窗口期已经打开**；平台原生同步能力一旦补齐，纯文件搬运的价值会缩水，但「流程与知识」的价值锚不受影响（PRD 第 9 章风险表）。

## 3. 做什么（MVP 范围）

### 3.1 范围裁定（继承 PRD 3.3，经第一性原理审查收敛）

**MVP = M1 完整 + M5 完整 + M6 完整 + M3 瘦身 + M2 瘦身**

| 模块 | MVP 投入 | 一句话交付 | 规格 |
|------|----------|-----------|------|
| M1 提示词库 | 完整 | CRUD、`{{变量}}`、标签/文件夹/全文搜索、版本快照与回滚、平台标记、导入导出（含 `.cursorrules`/`CLAUDE.md` 反向导入） | [specs/m1-prompt-library.md](./specs/m1-prompt-library.md) |
| M2 Skill 中心 | 瘦身 | 本地目录扫描发现 + 手动登记与版本记录（分发/生态源导入后移 P1） | [specs/m2-skill-registry.md](./specs/m2-skill-registry.md) |
| M3 术语库 | 瘦身 | 预置 ≥100 词条、CRUD、中英/别名全文搜索、一键生成 `TERMS.md`（提案审核流后移 P1） | [specs/m3-glossary.md](./specs/m3-glossary.md) |
| M5 项目与流程 | 完整 | 项目工作台、3 套流程模板、阶段检查清单、简化看板、DEV/CHECK 开发日志、复盘回流快捷入口 | [specs/m5-project-flow.md](./specs/m5-project-flow.md) |
| M6 标准包与注入 | 完整 | 组装向导、纯 Markdown 文件生成、`openvibe sync` 注入（dry-run/冲突备份/指纹漂移检测） | [specs/m6-standard-pack.md](./specs/m6-standard-pack.md)、[specs/m6-cli-injection.md](./specs/m6-cli-injection.md) |
| 种子内容 | 必交付 | ≥100 术语、3 流程模板、20 精选提示词，开箱即用 | [specs/seed-content.md](./specs/seed-content.md) |
| 开箱体验 | 必交付（澄清 D4 新增） | 预置演示标准包 + 可跳过 ≤3 步首启向导 + 飞轮统计面板 | [specs/onboarding.md](./specs/onboarding.md) |

**明确不做（MVP 外，防蔓延）**：M2 完整版（生态源导入、多平台 skill 分发、冲突检测 UI）、M4 技巧库、M7 团队协作与评审、AI 测试场、复盘候选自动提取（MVP 用人工快捷入口替代）、双向同步、桌面端/浏览器扩展。

### 3.2 核心交付形态

```
┌── Web 工作台（localhost 自部署）──┐      ┌── CLI（npx openvibe-cli）──┐
│ 资产库 / 流程看板 / 标准包组装向导  │ ───► │ scan 扫描登记            │
└────────────────────────────────┘      │ sync 注入（dry-run+备份）│
                 本地 SQLite（FTS5）     │ diff 漂移检测            │
                                         └──────────┬──────────────┘
                                                    ▼
                                    目标项目：CLAUDE.md / AGENTS.md / CODEBUDDY.md /
                                    MINI.md / .cursor/rules/*.mdc / .trae/rules / TERMS.md / CHECKLIST.md
```

### 3.3 标准化飞轮（产品价值闭环，也是 MVP 验收口径）

```
①建库（M1/M2/M3 录入或导入） → ②组装标准包（M6） → ③CLI 注入真实项目
→ ④按流程开发（M5 看板/清单/日志） → ⑤复盘回流（日志一键转术语/提示词草稿） → ①
```

MVP 验收 = 这一圈在真实项目上端到端走通（见 §6 与 tasks.md DoD）。

## 4. 为谁做（用户与关键旅程）

| 画像 | 优先级 | MVP 关键旅程 |
|------|--------|--------------|
| 独立 vibe coder（同时用 2-5 个 AI 编码工具） | P0 | 导入散落规则 → 组包 → 新项目 10 分钟完成「配环境」 |
| 团队 Tech Lead（1-10 人） | P1（架构预留） | 定义标准流程与检查清单 → 打包分发（MVP 单机自用，多人评审 P2） |
| AI 编码新手 | P1 | 术语库查词 + 抄精选提示词 + 照内置流程走 |

三条用户故事对应 PRD 2.2 的 1、2、5；术语/技巧场景（故事 3、4）在 MVP 以 M3 检索 + M2 登记部分满足。

## 5. 交付物清单

1. **软件**：pnpm monorepo——`apps/web`（SPA）、`apps/server`（API + 静态托管）、`apps/cli`（`npx openvibe-cli`）、`packages/core`（领域模型 + 存储标准包生成器，Web/CLI 共用）、`packages/adapters`（平台目录契约适配）、`content/seed`（种子内容）。
2. **内容**：≥100 术语、3 流程模板、20 精选提示词（质量标准见 [specs/seed-content.md](./specs/seed-content.md)）；词条允许 60 条首发、seed 幂等热补至 100（D14）。
3. **文档**：本套规划文档（proposal / specs / design / tasks）+ 用户 README + 标准包文件契约（design.md §7，独立评审对象）。
4. **验收证据**：E2E 飞轮一条龙的自动化测试（**2026-09-23 D21 裁定不引入 Playwright**，原写法作废）——实际形态：vitest 集成 + CLI 临时目录 + 真 serve 子进程的主链 `E2E-FLOW-01`（八腿，DEV-0020 已收），加裸 CDP 浏览器走查驱动器；三条冒烟（导入→复制 / 术语搜索→TERMS.md / 开箱向导三步）的**真实用户动作**证据**已收（2026-09-24）**：驱动器 `docs/devlog-evidence/DEV-0025/three-smokes.mjs` 用真鼠标点击 + 真中文输入 + 进程外剪贴板反查跑通三条场景（**有头 FAIL=0 SKIP=0**；无头下两条系统剪贴板腿按设计记 SKIP，不记 PASS）。数字与限制单源在 dev-plan §15.4b。

## 6. 成功度量

**产品侧（PRD 1.4 v0.2 双层口径，MVP 发布后 3 个月观察）**——遥测层（下界，仅统计开启遥测用户）：注入 ≥100 次、周活跃项目 ≥10、按模板执行项目占比 ≥50%、提示词复用率 ≥30%、自建词条 ≥50；生态层（代理）：GitHub stars ≥300、npm 月下载 ≥500（建议值可调）；北极星 = 飞轮圈数，落地为产品内统计面板（不上报）。

**工程侧（MVP 发布即验收，pass/fail）**：

1. 飞轮 E2E：建库 → 组包 → `sync` 注入临时真实项目 → 手工改动文件后 `diff` 报漂移 → 日志回流创建术语草稿，全程无手工干预失败。
2. 冲突保护三重奏：dry-run 零写入；覆盖前自动备份；非交互模式（CI）可用策略旗标。
3. 种子内容数量与 schema 校验脚本通过。
4. 冷启动 ≤ 3 条命令：`npx openvibe-cli serve` → 打开浏览器 → `npx openvibe-cli sync <path>`。

## 8. 关键风险与对策（精选，全表见 PRD 第 9 章）

| 风险 | 对策（本提案落地方式） |
|------|------------------------|
| 平台目录契约频繁变化 | adapter 层隔离（design.md §8）；标准包纯 Markdown 底线不失效 |
| 术语库冷启动死 | 预置 ≥100 词条开箱即用；复盘回流做成一键草稿（人工只确认） |
| CLI 写用户文件的信任问题 | dry-run 默认、自动备份、显式确认三重保护（specs/m6b 验收标准覆盖） |
| 被评价「又一个资产管理器」 | 差异化锚在流程+知识+闭环；M1 不追求 PromptHub 级全功能 |
