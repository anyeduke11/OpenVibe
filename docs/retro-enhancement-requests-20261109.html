关键观察

增强需求几乎不碰产品契约，全部集中在「判据与工具」层。这说明两件事：① 产品架构的前瞻性其实不差（契约稳定）；② 所谓「频繁出现的增强需求」，本质是质量保障层的持续补强，而不是一次次的产品设计返工。这个区分很重要 —— 它决定了改进方向是「收紧产单」而非「重做架构」。

链条上每一环都逻辑自洽：每一项都是对前一项「未覆盖面」的合理补强。问题不在单项的对错，而在于：

  • 没有「收口」的终点。每修一个洞，就露出相邻的另一个洞，且新洞看起来与前一个同等重要。
  • 没有「准入门槛」。三段格式里，第三段是必填的 —— 这等于制度上要求「每轮至少想出一件事」。
  • 没有「落点收敛」。增强项直接进入下一轮执行队列，而非先判断是否属于既有批次的验收面。
自我繁殖机制

三段格式要求「未考虑且需要增强的需求」不得省略（CLAUDE.md 原文：「计划外的改进想法不得默默省略，必须进第三段」）。这条规定的初衷是防止遗漏，但客观效果是强制每轮产出一批新待办 —— 一个不产生增强项的轮次反而违反格式。这是「频繁出现」的结构性根源。

03根因分析

从需求调研、架构设计、评审流程三个维度定位。结论：三个维度里，调研与架构不是短板，评审流程的执行闭环才是。

3.1 需求调研维度：覆盖标准缺失，但不是主因

维度现状评价
用户画像 PRD 第 0 章有目标用户与场景；社区新用户画像（P0） 充分
竞品调研 9 类竞品对比 + PromptHub 深挖 + 空白地带分析 充分
场景覆盖 有用户故事；但缺乏「异常场景 / 边界场景 / 对抗场景」的显式枚举 部分缺失
非功能需求 性能、安全、兼容性散见各 spec，无统一清单 部分缺失
假设管理 PRD 第 0 章假设表 + 决策台账（D1–D25） 充分

判定：调研覆盖面中等偏上，不是增强需求的主要来源。增强需求里几乎没有「用户场景没想到」的类型，绝大多数是「判据没覆盖到」。

3.2 架构设计维度：前瞻性足够，契约稳定

证据

近 3 个月的 194 条 DEV 里，增强需求触及已冻结契约（design §7/§8、SCHEMA_VERSION）的次数为 0。产品分层（api / components / hooks / i18n / data）与契约（标准包、adapter 清单）在 P0 冻结后保持稳定。架构前瞻性不是问题。

唯一的架构级事件是 DEV-0019 的「已发布版本再导出必然指纹漂移」—— 这是契约级缺陷，不是设计不足，且已修复。

3.3 评审流程维度：规则已立，但未绑定收尾格式 主因

已有的成熟机制

  • 验收-测试映射表（dev-plan §9）：每条任务对应具名用例 ID（UT-/IT-/CLI-/E2E-/GOLDEN-）
  • 契约变更分级（dev-plan §0.3）：A 冻结契约 / B 行为规格 / C 文档，三级各有处理流程
  • 决策台账（decisions.md）：每条裁定有编号、有状态、有落点
  • 增强准入规则（PRD v0.2.4 §14.2）：四条测试 + 三处落点 + 观察池

断点在哪

断点

PRD v0.2.4 §14.2 的四条准入测试，其适用范围被写死在该轮审查的上下文中（「本轮四条候选按此全部不构成新增强」）。它是一份局部规则，从未被提升为项目级收尾规范。而 CLAUDE.md 的三段收尾格式是项目级的 —— 两者没有连接。

结果：收尾时仍然可以「想到什么列什么」，四条测试形同虚设。

验证：规则若生效，近 8 条里有多少会被拦下？

按 §14.2 四条测试（来源 / 证据 / 去重 / 范围）逐条回测近 8 条 DEV 的收尾项：

回测结论：8 项中 4 项会被判「并入既有验收」（即：不另立增强条目，而是补进既有闸的验收标准），只有 4 项真正通过准入。若规则生效，产单量大约减半 —— 且「并入既有验收」的那 4 项并非不做，而是换一种更省的登记方式。

根因判定

这不是「规则缺失」，而是规则的适用范围没被提升。修复成本因此很低：不需要重新设计准入标准，只需要把它接到 CLAUDE.md 的收尾格式上，并配一份前期用的检查清单。

04优化方案

三件事：收紧产单口（收尾端）、前移覆盖检查（规划端）、给正常迭代留门（区分机制）。

4.1 方案 A：增强需求准入规则上收为项目级规范

做什么：把 PRD v0.2.4 §14.2 的四条测试与三处落点，写进 CLAUDE.md 的收尾规范，作为第三段的强制前置。

四条准入测试（候选必须同时通过，否则不得以增强名义登记）：

测试问题不通过时的去向
来源是否落在某条已声明不变量 × 某个既有表面？是「已声明但未覆盖」的缺口？新想法 → 非目标 / 观察池
证据是否有可复现证据（实测 / 探针 / 日志）？纯推测 → 观察池
去重是否已是某批次的验收项？并入该批次验收，不另立条目
范围是否服务核心价值？否 → 非目标

落点收敛为三处（「新增一个增强条目」不再是默认选项）：

  1. 既有批次的验收标准 —— 最常见，成本最低
  2. 决策台账（decisions.md）—— 需要 owner 裁定的
  3. 观察池 —— 有疑问但无证据的，登记不排期

格式配套修改：第三段标题从「未考虑且需要增强的需求」改为「计划外候选与准入判定」，并要求逐条写明「落点」与「未通过哪条测试」。允许该段为「本轮无候选」 —— 取消「必填即必产」的隐含约束。

4.2 方案 B：需求完整性验证检查清单（前期）

做什么：在批次/PRD 定稿前跑一份检查清单，把「异常场景 / 边界场景 / 非功能需求」从隐式变显式。详见配套文件 docs/requirement-completeness-checklist.md。

做什么：为「契约级变更」设一道独立评审，避免局部修复侵蚀全局一致性。本仓已有 A/B/C 三级变更控制（dev-plan §0.3），需要补的是评审的触发与留痕。

4.4 方案 D：给「正常迭代」留门（区分机制）

重要

不是所有增强需求都该被消灭。闸与工具在「被使用时」才暴露缺口，这是客观规律，前期无法穷举。方案 A 的目的不是「零增强」，而是让每条增强都经过准入判定、有明确落点 —— 把「无限产单」变成「受控登记」。

区分标准：

  • 应鼓励 有证据、落在既有不变量上、能并入既有验收的 —— 这是质量投资
  • 应收紧 无证据、纯推测、与既有验收重复的 —— 这是产单噪音
