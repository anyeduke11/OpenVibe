# 上下文治理优化方案（2026-11-03）

> 上位依据：[上下文管理规范](./specs/context-governance.md)（本轮新建）、[复盘报告](./context-governance-review-20261103.md)。
> 分级口径：**L 级**＝不改任何产物字节、不改公开契约，可直接实施；**A 级**＝改变产物字节或规格契约，须走 A 级变更流程（owner 裁定 → 附录新增 D 编号 → `schemaVersion + 1` → 先改 golden 再改实现）；**R 级**＝需 owner 或产品裁定，本轮只登记不实施。

## 2. 新增质量校验机制：`pnpm context:check`

新增 `scripts/context-check.ts`，与 `docs:check`、`ownership:check` 并列，**只管上下文约定的单一出处与边界**，不重复文档闸已有的职责。

| 判据 | 名称                | 判红条件                                                                                                                                                                                                                                                                                                                                        | 为什么必须是它                                                 |
| ---- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| C-1  | 标记单一出处        | `<!-- openvibe:end -->` 在 `packages/**/src`、`apps/**/src` 中出现于非 shared 文件                                                                                                                                                                                                                                                              | 标记解析分叉会让注入静默失效                                   |
| C-2  | 清单单一出处        | 四个辅助文件名（`TERMS.md` 等）在 shared 之外以裸字面量出现                                                                                                                                                                                                                                                                                     | 清单分叉正是 P-01 的成因                                       |
| C-3  | 分层纪律            | `packages/core/src` 出现 `@openvibe/adapters`；`packages/shared/src` 出现 core/adapters；`packages/adapters/src` 出现 `@openvibe/core`                                                                                                                                                                                                          | R2 是架构红线，不能靠约定                                      |
| C-4  | 矩阵一致            | `COMPAT_MATRIX` 任一 `reads` 不在 `ADAPTER_MAIN_PATH` 的值集内                                                                                                                                                                                                                                                                                  | 兼容矩阵是展示面，错了只有人看得出                             |
| C-5  | 上下游闭合（报数）  | 声明了下游但对方未在「上游」里回指                                                                                                                                                                                                                                                                                                              | 只报数不判红：历史规格存在单向登记，一次性判红会逼人改历史     |
| C-6  | 需求 ↔ 规格追溯闭合 | 需求清单（`CM-*`）与双向追溯表、与规格实存的 `FR-*` 三者对不上（缺行、多行、FR 不存在、条款指针 `FR-N.M` 解析不到具体条款、条款指针缺名锚或名锚与首行粗体短语不等值、验收编号不存在、规格声明的 CM 没指回来、锚点缺失、归属列无可机验锚点）。**另带一个只报数的面**：共锚自检（同指针不同名锚列出供人判；上下游未回指是独立判据 C-5，不属本行） | 三张表一旦各说各话，需求与实现就会静默脱节；人工核对三个月必漂 |

实现约束：

- 纯静态扫描 + 一次 `import`（取 `ADAPTER_MAIN_PATH`），不读网络、不写盘。
- 例外面写死在脚本顶部（测试文件、golden 夹具、本报告与规范自身），不放正则通配。
- 输出格式与 `docs:check` 一致：`error` 决定退出码，`warning` 只打印。

验收：手动改坏三处（标记、清单、矩阵）各一次，三次都必须报红；恢复后转绿。

## 3. 实施顺序

1. L-1、L-2、L-3、L-4（代码，互不依赖，一次改完再跑类型检查）。
2. L-5、C-1～C-6（脚本与 `package.json` 登记，同时在 `dev-plan` §1.5 登记脚本，满足 FR-13）。
3. L-6、L-7（文档）。
4. 四闸：`pnpm typecheck` / `pnpm lint` / `pnpm docs:check` / `npx prettier --check .`，外加 `pnpm context:check`。
5. 失败即停：不跳过、不注释，报在收尾的「未完成」段。

## 4. 不做的事（避免过度设计）

- 不重命名任何既有 spec 文件（改文件名会打断全部相对链接与历史登记，收益不抵成本）。
- 不对 `DEV_LOG` 做号段回填（等于替当年未登记的改动背书）。
- 不把四套状态词表合并（见 R-3）。
- 不为 `context:check` 加配置文件（判据固定 5 条，改判据就改代码）。
