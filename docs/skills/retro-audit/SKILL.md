# retro-audit — 独立复盘审计（vibe coding 工作流）

对目标工作（一个版本 / 一个批次 / 一段任务）做**独立**对账。你的价值在于找出开发者自报与仓库事实的偏差，不是复述开发日志——**以怀疑立场核证，未复算的数字不写结论**。

## 一、四面对账（思考模型的第一层）

1. **spec 验收表 vs 实现**：逐条找实现与测试证据（grep 代码、跑单支测试、查登记表）；spec 标 ✅ 的抽查至少两条是否真有用例背书；未标的判断实际状态。
2. **登记声称 vs 仓库**：DEV_LOG 声称的关键交付（文件/迁移/命令/用例数）逐项复算；声称的复算命令抽跑 2–3 条。
3. **PRD 层验收**：区分「已实现 / 已实现但等外部条件 / 未实现」。
4. **横向一致性**：登记表 vs 文档清单；快照 vs 实际导出；文档表述 vs 代码行为。

## 二、固定六节产出骨架（`retro-schema: 1`，缺节会被 vibe:retro 拒绝）

报告**第一行**写 `retro-schema: 1`，之后六节标题**逐字**：

```
retro-schema: 1
# <对象> 复盘（<日期>）

## 总评          ← 一句话判定 + 可信度自估（核了多少/漏了什么），≤5 行
## 逐批判定      ← 每批 ✅/◐/⏸ + 每态至少一条可复算证据（命令与实得值）
## 声称对照      ← 声称数字/文件/命令 vs 实得值的偏差表；零偏差也显式写「相符」
## 遗留清单      ← 三级分诊：真缺陷（本版必修）/ owner 待办 / 按设计延后
## 数字复算      ← 每个引用数字一行：| 数字 | 命令 | 实得 |
## 复盘自评      ← 本复盘可能错在哪（抽检率/环境差异/归属假设），≥2 条
```

## 三、回流（OpenVibe 闭环）

```bash
pnpm vibe:retro --file <报告.md> --project <id|目录>
```

全部落 **pending**（agent 判断永不为事实源），owner 在 Web 工作台确认后入库；确认后的日志可再跑「提取候选」沉淀为资产。完整协议：仓库 `docs/vibe-retro.md`。

## 四、纪律

- 不修改任何被审文件；跑测试可以。
- 「✅」只给有用例/命令背书的条目；抽查发现虚报 ⇒ 总评降级并写明。
- 环境差异要识别（CI runner 用户名/平台/工具链——本地绿 ≠ 远端绿）。
