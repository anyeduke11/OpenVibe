# 复合主键表与仓级静态守卫：两个只有真跑仓级测试才暴露的坑

Type: pattern-anti

**一句话**：这两条都在「**按文本匹配判代码**」或「**按单列取行**」的边界上；类型检查与自己的单测都不会报，只有仓级静态守卫与真实的语义问法才现形。

## 一、带静态守卫的仓里写 SQL 字面量

OpenVibe `tests/order-determinism.test.ts` 是仓级静态守卫，用纯文本正则抽 SQL 字面量（`/(['"])(?:...)\1/g`）。本轮实测两个坑：

**① 注释里用反引号包 SQL 片段 ⇒ 守卫把注释当代码。**
我在注释里写「DISTINCT lang ORDER BY lang 的末键是 lang」并用反引号包住 ⇒ 那段注释被抽成一条 SQL 判据 ⇒ 报「无兜底排序键」。
⇒ **注释里别用反引号包 SQL 片段**（用「」或纯文本）。这是「注释也会被静态检查」的通病，与「文档里的版本行会被内容扫描命中」同族：**元信息行不是豁免区**。

**② 复合主键表不能写 ORDER BY**（当守卫的兜底键白名单只认单列唯一键时）。
守卫判「ORDER BY 末键 ∈ {id, rowid, entry_no, version_no}」。复合主键表（如 PK = (topic_id, prereq_topic_id)）两列单独都不唯一 ⇒ SQL 里写 ORDER BY 必红。
⇒ **把排序放 JS**（`rows.sort(...)`），确定性等价，**且不必改那条仓级契约** —— 改白名单/加豁免是**契约改动**，该由 owner 签收，不是实现方顺手改。
同理 `DISTINCT x ORDER BY x` 也会红；改用 `GROUP BY x ORDER BY x` 走守卫的聚合豁免（分组键覆盖排序键 ⇒ 排序确定），语义等价。

**共同根**：两条都是「**按文本匹配判代码**」的固有代价 —— 判据认不出「这段是注释」与「这个键其实不唯一」。⇒ 写这类仓的代码时，**先跑一遍仓级静态守卫**（别只跑自己包的测试），它比自己的单测更早暴露「我写的形状不对」。

**apply when**：在有 SQL 文本静态守卫的仓里新增/修改含 SQL 的源文件；注释里要引用 SQL、命令、正则片段时；给复合主键表加确定性排序。

## 二、复合主键表按单列查 ⇒ 命中「第一行」⇒ 静默串行

在**复合主键**表上按其中一列查（例如 `lang_topic_profiles` 主键 `(topic_id, profile)`，只按 `topic_id` 过滤），拿到的是「该 topic_id 的**第一行**」—— 而同一个实体在**另一个维度**上还有别的行 ⇒ 结论**静默串到别的维度上**。

本轮实测：`isRequiredIn(profile, topicId, rows)` 写成 `for (r of rows) if (r.topic_id === topicId) return isRequiredRow(profile, r)` ⇒ 问「速成是不是必学」，返回的却是**精通那行**的 required ⇒ 「精通必学」被误判成「速成不必学」。**它不报错，只是答错。**

**通法**：
- 复合主键表上按实体查，**必须同时匹配全部键列**（`r.topic_id === id && r.profile === profile`）；
- 查表前先问一句「**这个实体有几行？我拿的是哪一行？**」；
- ⚠️ 谓词**只写一处**时，别把「判定所需的全部条件」藏进调用方的循环里 —— 把条件拆成 `isRequiredRow(profile, row)`，循环里只负责**选行**，否则「判定式只出现一次」这条口径闸会**误以为**自己守着唯一口径。

**为什么它没被静态检查抓到**：类型上完全合法、SQL 也合法、测试也能跑通。只有「拿到的行是不是我要的那一行」这条**语义**对不对。

**apply when**：任何在**主键含两列以上**的表上按单列过滤的代码；任何「遍历行集合、命中即返回」的写法（`find` / `for` ＋ `return`）。

**同族**：与「SQL 静态守卫误伤复合主键表的 ORDER BY」是同一张表的两种坑 —— 一个管**排序**，一个管**选行**。
