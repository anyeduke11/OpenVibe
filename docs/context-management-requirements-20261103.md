## 1. 问题定义

### 1.1 「上下文」在本文指什么

**某平台的 AI 在一次会话中真正读进 token 窗口的那部分内容**——不是包的全部文件，也不是磁盘上的全部产物。这个定义把三件事分开：

| 层     | 对象                               | 回答的问题                    | 现有承载                                                              |
| ------ | ---------------------------------- | ----------------------------- | --------------------------------------------------------------------- |
| 资产层 | 包（规则／术语／清单／技巧／参考） | 「我写了什么」                | `ResolvedPack`（`packages/shared/src/pack-contract.ts`）              |
| 落盘层 | 注入产物（主文件 ＋ 辅助文件）     | 「装进项目里的是什么」        | `verifyPack` → `planInjection` → `applyDecisions` ＋ `pack.lock.json` |
| 消费层 | 平台实际读取的文件集合             | 「AI 到底读了什么、读了多少」 | `ADAPTER_MAIN_PATH` ＋ `PACK_CONTEXT_AUX_FILES`；`LoadPlan` 仍是草案  |

### 1.2 现状的五个断点（承接复盘结论，不重复其清单）

1. **口径不齐**：体量有字节（`footprint.bytes`）、token 估算（`perTarget.approxTokens`）、密度（`density`，仍是 v0.9 草案且分母口径未裁）三套读数，缺一份「哪个数回答哪个问题」的成文规则。
2. **作用域不一致**：服务端按「主文件 ＋ 四类辅助文件」估算，CLI 的 `--target` 只写三类 ⇒ 预览里算进去的内容，注入时可能不落盘（登记为 A-1，待签收）。
3. **加载协议未定**：`LoadPlan`、adapter 能力位、L0／L1／L2 只在 [m11-context-loading.md](./specs/m11-context-loading.md) 的 v0.1 草稿里；能否成立取决于 U10（平台是否真读二级文件）。
4. **状态词表分裂**：注入五态、一致性四态、核验六态、退役四态各自成立，但没有一张映射表说明「同一文件在四个视角下分别是什么态、该做什么处置」。
5. **研发期治理只到仓库侧**：单一出处、分层纪律、上下游闭合已有 `pnpm context:check` 与 CI；但这些纪律尚未反向约束产品需求（例如新字段该不该有第二个出处，靠人记）。

## 3. 场景（每条场景都要能在验收里被判定）

- **S1 组包前**：作者想知道「这 200 条规则会让 AI 读多少 token」，并知道哪 5 条最占地方 ⇒ 需要 A3＋A4＋B 组的口径。
- **S2 同步后**：同事手改了受管块外的内容，再同步不能把他的改动冲掉，且能看出「漂在受管块还是自由区」 ⇒ 需要 A5＋A6。
- **S3 规则变多**：规则从 8 条涨到 128 条时，主文档线性膨胀，但其中大部分未必被读到 ⇒ 需要 B 组；若 U10 证明多数平台不读二级文件，正确结论是「不做」（见 m11 的未验证面登记）。
- **S4 改契约**：维护者要给 `sizeEstimate` 加字段，必须知道这算不算 A 级、要不要先改 golden ⇒ 需要 A3 的口径边界与 A 级流程条款。

## 5. 验收口径

一条需求算「完成」必须同时满足：

1. **可机判判据绿**（能用命令或 CI 步骤判定的，必须有那条命令）；
2. **人工判据有留档**（只能人看的，写进 `DEV_LOG` 或证据目录）；
3. **未验证面显式登记**（学 m11 的做法：未验证的情形单独列出，不得读成已通过）。

| 层     | 可机判                                            | 人工／留档                   | 未验证（不得读成已通过）                       |
| ------ | ------------------------------------------------- | ---------------------------- | ---------------------------------------------- |
| 产品   | `pnpm context:check`、`pnpm docs:check`、既有测试 | A 级变更四要素、备份恢复演练 | 各平台真实读取行为（U10）、模型跟随行为（U11） |
| 加载   | E-6 逐字节对照、索引行三要素、能力位 grep         | owner 对 D-v25-1 的裁定      | 索引化后的真实收益                             |
| 研发期 | CI 六步闸、pre-commit（待接）                     | 基线清理决定、退役签收       | 闸是否长期有效（需要趋势数据，见 §8）          |

## 7. 不做的事

1. **不新建任务组、不改 spec**：本方案只是需求清单；开工仍走 Spec 先行（No spec, no task）。
2. **不把「能省字节」当收益**：分层加载的价值取决于 U10／U11，未证之前不承诺。
3. **不合并四套状态词表**：只要求映射表，不要求并表——四者描述不同问题，合并会丢区分度。
4. **不用治理之名改产物字节**：任何改变四根主文件字节、`files[]` 或指纹的需求，一律走 A 级。
