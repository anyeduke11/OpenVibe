## 第 3 章 · rulesync 能力全量对齐

### 3.1 rulesync 能力面（实查，2026-11-12）

来源：[rulesync README](https://github.com/dyoshikawa/rulesync)（1,600★，最近提交 2026-11-09，TypeScript CLI，MIT）。

**九特性闭集**：

| 特性          | 含义           | OpenVibe 现状（初判）                        |
| ------------- | -------------- | -------------------------------------------- |
| `rules`       | 规则主文件     | ✅ 标准包主文档                              |
| `ignore`      | 忽略文件       | ❌ 无（rulesync 自身已弃用，迁 permissions） |
| `mcp`         | MCP 服务器配置 | ✅ MCP 桥（DEV-0247）                        |
| `commands`    | 自定义命令     | ❌ 无                                        |
| `subagents`   | 子代理定义     | ❌ 无                                        |

### 3.4 60+ 工具对齐：路径裁定（**已签收**，2026-11-12）

#### 3.4.1 冲突事实

`docs/design.md` §8 明确：

> 新增平台 = 新增一个 Adapter 模块 + 注册，其余零改动（风险表「平台契约变化」的隔离解法）。

而 §8 的 adapter 清单是 **MVP 六个**（claude-code / cursor / generic-agents / codebuddy / trae / minicode）+ P1 三个（windsurf / gemini / copilot），另有**兼容矩阵**（不新增 adapter，直接读产物文件）：Codex / OpenCode / Cline / Qwen Code / Trae CN / zcode / Kimi Code / CLAUDE.md 兼容代理。

`docs/PRD-v0.2.5-v0.9-20261029.md` 头表进一步明确：

> 凡触碰 design §7 冻结包契约（节序、manifest `schemaVersion`、`targets` 枚举、`files[]` 清单）的条目一律走 A 级：owner 裁定 ＋ 附录编号 ＋ `schemaVersion+1` ＋ 先改 golden 再改实现。

⇒ **「全量对齐 60+ 工具」若照字面执行，需要新增约 50 个 adapter，每个都是一次 A 级动作**（裁定 + 附录编号 + `schemaVersion+1` + golden）。这在单用户本机的定位下**不成立**。

#### 3.4.2 三条替代路径（请 owner 裁一条）

### 3.6 与 OpenVibe 定位的冲突说明（必须如实写）

rulesync 是**面向团队的规则同步工具**（60+ 工具、global 层、插件打包），OpenVibe 是**单用户本机的上下文管理工作台**。两者**部分能力重叠、整体定位不同**：

- **重叠**：`rules` / `mcp` / `skills` / `dry-run` / `import` / `export` —— 这些 OpenVibe 已有或可补。
- **不重叠**：`commands` / `subagents` / `hooks` / `global` / 插件打包 / 60+ 工具 —— 这些是 rulesync 的**团队与多工具**属性，与 OpenVibe 的单用户本机定位**张力明显**。

⇒ 本文的「全量对齐」**不是**把 rulesync 的每个特性都做成 OpenVibe 功能，而是**把它的能力面逐条摆开，让 owner 看清哪些该补、哪些不该**。§3.3 的「⛔ 不做」项就是这个判断的产物。
