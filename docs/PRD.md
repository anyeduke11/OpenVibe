## 第 1 章 · 产品概述与目标

### 1.1 一句话定位

> **OpenVibe 是 vibe coding 的标准化工作台：把提示词、Skill、术语、技巧和项目流程变成可管理、可复用、可分发的工程标准。**

> **v0.2.0 起本句的读法见 §10.1（D27）**：句中的「可管理」是**手段不是目的**，本产品的三段实质是「意图 → 项目上下文的编译 / 分发 / 反馈回路」。**本句不改字**——它是 D2 权重裁定的产物，改它等于重开 D2；改判只落在读法上。

### 1.2 背景与问题

vibe coding（用自然语言与 AI 结对完成编码）已成为主流开发方式，但配套的「工程化」严重缺位：

1. **资产散落**：提示词躺在聊天记录和收藏夹里，规则散落在 `.cursorrules` / `CLAUDE.md` / `AGENTS.md`，换项目、换工具、换人即失效；
2. **没有标准**：同一个团队每个人喂给 AI 的规则质量天差地别，AI 输出质量随人而变；
3. **知识流失**：踩过的坑（技巧）、发明过的词（术语）没有沉淀载体，新人重新踩一遍；
4. **流程随意**：AI 编码项目缺少统一的需求→实现→复盘流程，质量靠运气。

现有工具各占一角（详见 `competitive-research.md`）：PromptHub 管个人资产、BMAD/spec-kit 管流程模板、skills.sh 管 skill 分发——**无人做「资产 + 知识 + 流程」的标准化闭环**。

### 1.3 核心目标（3 个）

| # | 目标 | 衡量方式 |
|---|------|----------|
| G1 | **资产标准化**：五类资产一处沉淀、版本化、多平台一键分发（Claude Code / Cursor / Windsurf / Codex 等） | 标准包分发次数；资产复用率（被引用次数/总量） |
| G2 | **流程标准化**：AI 编码项目从启动→开发→复盘有模板、有检查清单、有日志 | 按模板执行的项目占比；复盘产出条数 |
| G3 | **知识标准化**：术语统一（团队说同一种语言）、技巧结构化沉淀（坑不重踩） | 术语库覆盖率（会话高频词入库率）；技巧库月新增 |

> **权重定案（2026-09-20 澄清 D2）**：G1 + G2 为主目标——社区传播**双钩子** = 标准包一键注入（机制独特性）+ 可视化流程模板（对比 BMAD 只发文件，我们是可裁剪工作台）；G3 为支撑目标，术语以 TERMS.md 随包分发出场，不独立主打。

### 1.4 成功指标（MVP 发布后 3 个月；2026-09-20 改双层口径）

**遥测层（下界口径）**——仅统计主动开启匿名遥测的用户，代表真实量的下界：
- 标准包注入 ≥ 100 次；周活跃项目 ≥ 10；按模板执行的项目占比 ≥ 50%
- 提示词复用率 ≥ 30%（产品内面板口径）；用户自建词条 ≥ 50

**生态层（代理指标）**——本地优先产品的公开健康度信号：
- GitHub stars ≥ 300；npm 月下载 ≥ 500（建议值，owner 可调）

**内容层**：术语库预置词条 ≥ 100（全量目标；v0.1.0 允许 60 条首发、经 seed 幂等热补至 100——D14 审校进度决定，见 specs/seed-content.md 与 tasks §3 变体③）

**北极星指标**：**「标准化飞轮完整走完的圈数」**（沉淀资产 → 组装标准包 → 注入项目 → 复盘回流新资产）。落地形态 = 产品内用户可见的**飞轮统计面板**（留存玩法，本地统计不上报，见 specs/onboarding.md）。

## 第 2 章 · 用户画像与场景

### 2.1 用户画像

| 画像 | 描述 | 核心诉求 | 优先级 |
|------|------|----------|--------|
| 独立 vibe coder | 资深全栈开发者，同时用 2-5 个 AI 编码工具 | 资产多平台同步，不再翻聊天记录找提示词 | P0 |
| 团队 Tech Lead | 1-10 人团队的负责人 | 给团队定一套 AI 编码规范并强制落地 | P1 |
| AI 编码新手 | 刚入坑 vibe coding 的开发者 | 学术语、抄技巧、照流程走，少走弯路 | P1 |
| 社区新用户 | 开源发布后的首次安装者（D1 新增） | 3 条命令 / 5 分钟内体验「注入 + 流程模板」双钩子 | P0 |

### 2.2 核心使用场景（用户故事）

1. **作为独立开发者**，我希望把散落在各项目的提示词和规则文件统一导入管理，并在新项目启动时一键注入，以便 10 分钟完成过去 2 小时的「配环境」。
2. **作为 Tech Lead**，我希望定义团队的标准开发流程（需求→PRD→实现→复盘）与各阶段检查清单，并打包成「标准包」分发给所有成员的项目，以便团队 AI 输出质量有统一底线。
3. **作为团队成员**，我遇到「AI 改了不该改的代码」「规则漂移」等问题时，希望能查到统一术语的定义和对应的应对技巧，以便与 AI 高效沟通。
4. **作为 Skill 收集者**，我希望在一个地方管理 skill 并分发到我用的所有编码代理，以便统一升级、避免版本混乱。
5. **作为新手**，我希望通过术语库 + 技巧库 + 流程模板快速上手 vibe coding 方法论，以便直接站在团队经验上工作。

### 2.3 使用频率预估

| 频率 | 场景 |
|------|------|
| 每天 | 项目工作台（看板、检查清单、复制提示词、记日志） |
| 每周 | 资产整理（打标签、归档、review 新技巧） |
| 事件驱动 | 新项目启动（注入标准包）、项目复盘（CHECK 报告、技巧回流） |

## 第 3 章 · 功能模块设计

### 3.1 模块总览

```
┌─────────────────────────── OpenVibe ───────────────────────────┐
│  资产层   M1 提示词库   M2 Skill 中心   M3 术语库   M4 技巧库     │
│  流程层   M5 项目与流程管理（模板/看板/检查清单/开发日志）          │
│  交付层   M6 标准包与注入（标准化出口，Web↔CLI↔目标项目）          │
│  协作层   M7 团队协作（Phase 2）                                  │
```

依赖关系：M1–M4（素材）→ M6（打包分发）；M5 ↔ M6（项目引用标准包版本）；M7 横切所有模块。

### 3.2 模块明细

#### M1 提示词库（P0，MVP 核心）

| 功能 | 说明 | 优先级 |
|------|------|--------|

| 平台适配标记 | 标记适用平台（Claude Code / Cursor / CodeBuddy / 通用…），同一定义多平台变体 | P0 |

## 第 4 章 · 系统架构设计

> **[假设]** 技术选型以下述为默认方案，owner 可在评审时替换；「Web + CLI 伴侣」的双形态不是假设而是审查修正的硬约束（见第 9 章）。

### 4.1 架构图（文字）

```
┌─ Web UI (SPA: React + TS + Vite) ─┐        ┌─ CLI (Node.js, npx openvibe-cli) ─┐
│  资产管理 / 流程管理 / 标准包组装    │        │  sync 注入 / scan 扫描 / diff   │
└──────────────┬────────────────────┘        └───────┬────────────────────────┘
               │ REST/JSON                        读写│ (本地文件)
┌──────────────▼────────────────────┐        ┌───────▼────────────────────────┐
│  API Server (Node.js)             │ 标准包  │  目标项目目录                    │
│  资产/流程/标准包/版本/搜索服务      │◄──────►│  CLAUDE.md AGENTS.md .cursor/  │
└──────────────┬────────────────────┘  导出   │  TERMS.md skills/ CHECKLIST.md │
               │                            └────────────────────────────────┘
┌──────────────▼────────────────────┐
│  存储 SQLite(个人) / PostgreSQL(团队)│   分发目标 = 各 AI 编码平台的规则/skill 目录
│  FTS5 全文搜索 / 附件对象存储        │   （Claude Code、Cursor、CodeBuddy、Trae、MiniCode、zcode、Kimi Code、Codex…）
└───────────────────────────────────┘
```

### 4.2 关键设计决策

1. **标准包是纯文件契约**：Markdown/YAML，不发明私有格式。保证资产可迁移、可 git 版本化、工具锁定为零——生态多变环境下的生存策略。
2. **CLI 是 MVP 硬依赖**：浏览器无法写本地项目文件，「注入」必须由 CLI 完成；CLI 从 API 导出的标准包工作，也支持完全离线（本地文件模式）。
3. **平台适配层**：各目标平台的目录与文件格式（`.claude/skills`、`.cursor/rules/*.mdc`…）抽象为 adapter 表，平台契约变化只改 adapter。
4. **本地优先**：MVP 单用户数据全在本地（SQLite 文件），天然规避隐私问题；团队同步 Phase 2 再做。

### 4.3 文件结构（Monorepo，示意）

```
openvibe/
├── apps/
│   ├── web/          # SPA
│   ├── server/       # API Server
│   └── cli/          # npx openvibe-cli
├── packages/
│   ├── core/         # 领域模型 + 标准包生成器（web/cli 共用）
│   ├── adapters/     # 各平台目录契约 adapter
│   └── shared/       # 类型与工具
├── content/
│   └── seed/         # 预置术语/流程模板/精选提示词
└── docs/             # PRD、竞品调研、决策记录
```

### 4.4 外部依赖

- 无强制外部服务（MVP 可全离线跑；遥测默认关闭，关闭时零外联）
- P1：可选匿名遥测上报端点（**默认关闭**；公开事件仅三类：注入成功、流程模板选用、活跃项目去标识计数；不含任何路径/内容/用户标识；实现与端点选型见 design.md §11）；首次注入成功后一次性 opt-in 询问（D13，见 design.md §11.5 与 specs/onboarding.md FR-4.2）
- P1：GitHub API（skill 源拉取）、skills.sh 源、LLM API（测试场/草稿生成，用户自配 Key，AES-256-GCM 加密存储）

## 第 7 章 · 数据模型设计

### 7.1 核心实体（字段摘要）

```
Prompt          { id, title, content, variables[], tags[], platform_marks[],
                  status[draft|active|deprecated], owner_id, created_at, updated_at }
PromptVersion   { id, prompt_id, version_no, content, changelog, created_at }
Skill           { id, name, description, source[local|github|skillssh|manual],
                  latest_version, sha256, installed_targets[] }
SkillVersion    { id, skill_id, version, path, sha256, installed_at }
Term            { id, zh, en, aliases[], definition, example, related_term_ids[],
                  source, tags[], status }
TermProposal    { id, term_id?, proposed_term, proposed_change, status, reviewer_id }
Playbook        { id, title, scenario, problem, solution, anti_pattern,
                  link_prompt_ids[], link_skill_ids[], link_term_ids[],
                  score, verified_count }
Project         { id, name, local_path, flow_template_id, status, health,
                  standard_pack_id, standard_pack_version }
FlowTemplate    { id, name, kind[light|spec_driven|retro|custom],
                  stages[{ name, checklist[], artifacts[] }] }
Task            { id, project_id, stage_name, status, title, assignee_id, order }
DevLogEntry     { id, project_id, type[DEV|CHECK], entry_no, body,
                  evidence{ file, command, result }, created_at }
StandardPack    { id, name, version,
                  manifest{ prompt_ids[], skill_ids[], term_ids[], playbook_ids[],
                            flow_template_id }, artifacts_fingerprint }
User            { id, name, email, role }              // Phase 2
TeamMembership  { user_id, team_id, role[owner|member|reviewer] }  // Phase 2
```

### 7.2 实体关系

- Prompt 1—N PromptVersion；Skill 1—N SkillVersion
- StandardPack N—N (Prompt / Skill / Term / Playbook)，N—1 FlowTemplate（manifest 内引用，带版本快照）
- Project N—1 FlowTemplate，N—N StandardPack（按 version 锁定）
- Playbook N—N（Prompt / Skill / Term）——技巧可反向链接到资产
- Project 1—N Task、1—N DevLogEntry
- DevLogEntry.evidence 是复盘回流（5.4 节）到 Playbook 的数据来源

### 7.3 数据流转路径

```
资产录入 → DB(版本化) → manifest 组装 → 文件生成器 → StandardPack 导出
→ CLI 注入 → 项目目录(git 可追踪) → 项目使用/复盘 → 回流候选 → 资产层
```

现测（口径：`python3` 逐行匹配 `^\| (\S+) \|` 取到 33 行；字节按 UTF-8 编码长度；「可复算命令」= 反引号跨度内含 `grep|git|gh|awk|sed|wc|stat|npm|pnpm|node|ls|cmp|sha256sum|SELECT|find|curl` 之一）：

1. **分析文的「单行 ~2 KB」代理对中位数成立**（2,106 B）、**对均值低估 26%**、对最重的 ⑦ 行低估 **7.5 倍**；17/33 行超过 2048 B。⇒ 该代理可用，但必须标明它是**中位数**不是均值。
2. **可复算命令的分布是 `[0×18, 1×2, 2×4, 3×3, 4×1, 7×2, 9×1, 18×1, 29×1]`**：**18/33 行行内一条复算命令都没有**（复审者无从就地复核，只能另起一轮考古），而 93 条中的 29 条（31%）挤在 ⑦ 一行。⇒ 排期用的数不该是「平均一行多久」，而该**按两类分行**：有就地复核路径的 15 行与没有的 18 行——两类的复审动作根本不同，取平均会把两者都算错。
3. **「2 次计数错报」这个代理只数了一个类**：同类第二次由队列自己标注（`decisions.md` 部分授权 bullet 内「**2026-10-01 第二次撞上同一条**」）；但同文件底部另有**第二个类**——`[DEV-0085]` 补记二就地修的两处：「净状态『已裁已落 17』实为 **18**」与「第五态『已裁待落』在口径行与表格里都有、净状态少了它那一格」。⇒ **已登记的计数错报是 4 处、分 2 类**，RF0-4 的 `docs:check` 立项依据按 **4 处**写，不按 2 处写。
